# TokTier 0.2.0

TokTier 0.2.0 is a session-seed performance and error-reporting release.
Existing 0.1.1 Python and Rust calls remain source-compatible, and
`Session::seed` / `append`, snapshot and patch contracts, store-format-v1
bytes, the HF fallback and fail-closed semantics, and the shipped fatbin
and kernel ABI (seven architectures plus the PTX fallback) are unchanged.
Relative to 0.1.1 this release adds the Python `from_pretrained()` entry
point, the `crates/toktier` Rust preview API, and
`RuntimeBuilder::seed_digest_overlap`, and corrects selected error
classifications (below). Every certified source identity was regenerated
and re-evidenced on this release tree.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.0. The public API version,
registry schema version, store format version, kernel ABI version, and
certification suite version do not move. The `crates/toktier` Rust crate
is published to crates.io with this release; it leaves the `0.0.1`
source/workspace preview number behind and follows the package version
(axis 1) from here on.

## Behavior changes (diagnostics)

- **`explain()["backend"]` now reports the backend that actually
  returned the last result on the routed encode lane**, matching what
  README.md has always promised. It previously reported the planned
  backend, so a per-input safety fallback (below the GPU crossover, an
  added-token literal routed to HF) was visible only under
  `runtime_policy.last_execution.executed_backend`. Two companion keys
  make the field self-describing: `backend_basis` is `"last_execution"`
  once anything has run and `"plan"` before that, and `planned_backend`
  reports the plan either way, so no information is lost. Callers that
  want the plan should read `planned_backend` (or `Tokenizer.plan`).
  One lane is not covered yet: a session append served by boundary
  repair keeps the previous routed record in the headline and in
  `runtime_policy.last_execution` until 0.2.1, while
  `session_repair.last` reports the repair (see Known behavior below).
- **`explain()["certification"]` now headlines the GPU delivery that
  runs.** `certification.state` and `certification.backend_status.gpu`
  previously repeated the backend-level registry row, which is the
  `certified_source` JIT view, even with the judged `certified` prebuilt
  image loaded. They now report the loaded (or selected) delivery's own
  status, and `certification.gpu_delivery` names it. The per-delivery
  and per-architecture detail under `certification.deliveries` and
  `kernel_deliveries` is unchanged. `probe.kernel_delivery` is refreshed
  from the loader as well, instead of reporting the pre-load `null` of
  the construction-time snapshot beside a top-level `prebuilt`.

## Behavior changes (error reporting)

- **`ArtifactHashMismatch` is now reserved for true content-hash
  failures.** Previously, a tokenizer artifact whose hash check had
  already passed could still be reported as `ArtifactHashMismatch` when a
  later parse or load step failed. Callers that match on this error code
  observe the corrected codes below:
  - GPU table construction that fails to parse `tokenizer.json` now
    reports `KernelIncompatible` (`crates/toktier/src/gpu_data.rs`, two
    sites);
  - a frozen oracle that cannot load an already-verified artifact now
    reports `Internal` (`crates/toktier/src/runtime.rs`; unreachable
    through the public surface by construction).
- **The fail-closed JIT refusal carries its facts in the message.** An
  explicit `device="cuda"` request that the certified planner closes on
  the JIT toolchain boundary now names the observed NVCC / torch-runtime
  CUDA / PyTorch triple and the certified constraint in the message
  itself, as README.md and `docs/gpu-jit.md` describe, instead of only
  in `details.reason`.
- **CLI `--json` now covers the failure path.** A command invoked with
  `--json` that fails writes one JSON object
  (`{"error": {"code", "message", "details"}}`) to standard error
  instead of the human line; the exit code (`2`) and the plain-text
  behaviour without `--json` are unchanged
  (`docs/contracts/errors.md` Section 4).
- **`_atomic_write` now fsyncs both the file and its directory**
  (`src/toktier/facade/store.py`). An empty or half-written state file can
  no longer be observed within a crash window.
- **`.pyi` alignment**: `corrupt_node_for_tests` exists only under the
  testing feature; the type stub and documentation now say so.

## Added

- **`toktier.from_pretrained(repo_id, *, revision=None, ...)`** (Python):
  the model-repository entry point. It resolves and hashes the exact
  tokenizer content and admits acceleration only for audited identities;
  unknown or changed content executes on the HF reference route
  (`docs/contracts/facade.md` Section 1).
- **`crates/toktier` Rust API**: the Python-free serving facade
  (artifact acquisition, runtime, sessions; `docs/rust-api.md`).
- **crates.io publication**: `toktier` and its five workspace crates
  (`toktier-gigatoken-core`, `toktier-store-core`, `toktier-cuda-driver`,
  `toktier-routing-core`, `toktier-store-sqlite`) are published at
  0.2.0, so `cargo add toktier` resolves from the registry rather than a
  path or git dependency. The crate carries the same package data as the
  wheel, including the multi-architecture fatbin, so a registry consumer
  builds the prebuilt GPU path without a CUDA toolchain. The internal
  PyO3 binding (`toktier-py`) is marked `publish = false`; it is a build
  input for the wheel, not a registry crate.
- **`RuntimeBuilder::seed_digest_overlap(bool)`** (Rust API, default
  off). When enabled, a seed's content digest (personalized-BLAKE2b
  endpoint plus geometric checkpoints) runs on the shared bounded Rayon
  pool concurrently with the seed encode. Digest bytes, validation
  ordering, error codes, and failure atomicity are identical to the
  default serial path; only wall-clock scheduling changes. Measured on
  real hardware (31 fresh processes per cell):
  - EPYC CPU 4 MiB seed (store shape): off 26.473 ms, on **21.466 ms**
    (-18.9%);
  - RTX 5090 GPU 4 MiB public seed: off 11.078 ms, on **10.081 ms**
    (-9.0%; the measured hidden window is about 1.0 ms on this host);
  - four concurrent seeds and a 40-round long run show no throughput
    loss and byte-identical RSS at start and end. The default remains
    **off**.

  The CPU rows, the concurrency and long-run cells, and a pre-release
  confirmation of the same pair are in
  [`readings/seed_digest_overlap_cpu.json`](../../readings/seed_digest_overlap_cpu.json);
  the GPU rows are the `seed_digest_overlap` block of
  [`readings/rust_zero_copy_seed_w5.json`](../../readings/rust_zero_copy_seed_w5.json).

## Performance

Same-host, same-protocol contrasts against the previous certified tree,
31 fresh processes per cell, with a post-timing exact-ID check against
the frozen Hugging Face reference in every process (no sample rejected).
Hosts: the RTX 5090 rows are an Intel Core Ultra 9 285K host with a
GeForce RTX 5090 (driver 595.84); the EPYC rows are a 2x AMD EPYC 9115
host. The machine-readable reading is
[`readings/rust_zero_copy_seed_w5.json`](../../readings/rust_zero_copy_seed_w5.json),
measured on a source-equivalent pre-release commit; the released tree's
direct confirmations, each with its own measured values, are
[`readings/rust_zero_copy_seed_w6prep.json`](../../readings/rust_zero_copy_seed_w6prep.json)
and, after the crates.io manifest change and its recertification,
[`readings/rust_zero_copy_seed_batchd.json`](../../readings/rust_zero_copy_seed_batchd.json).

- **GPU public in-memory 4 MiB seed (RTX 5090 host)**: 59.739 ms to
  **11.145 ms p50 (-81.3%)**; 67.717 ms to **12.010 ms p95 (-82.3%)**.
  GPU ID-only encode: 5.181 ms to 4.113 ms (-20.6%). The explicit
  offsets/state contrast is 15.820 ms against the former 39.047 ms
  known-ID span-bridge contrast (2.47x lower). SQLite-backed seed:
  98.309 ms to 45.743 ms. These cells are the pre-release
  source-equivalent recertification; the release tree directly measured
  11.277 ms p50 / 12.890 ms p95 for the in-memory seed and 50.956 ms
  for the SQLite-backed seed (`rust_zero_copy_seed_w6prep.json`), and
  11.080 / 12.315 ms and 45.190 ms on the crates.io-ready tree
  (`rust_zero_copy_seed_batchd.json`).
- **CPU public seed (EPYC host)**: 67.395 ms to **26.465 ms (-60.7%)**;
  SQLite-backed 115.325 ms to 70.142 ms. The corrected-CPU engine itself
  is unchanged (47.454 ms before, 47.209 ms now; control cell).
- **Span bridge**: the known-ID full pair bridge became a one-pass SoA
  bridge, and the seed critical path now uses lazy spans. Direct EPYC
  measurements: 21.7 ms (pair bridge) to 4.5 ms (SoA) to about 1.1 ms on
  the seed critical path (lazy). The GPU host shows the same order of
  reduction.
- **Incremental append hashing**: the sealed prefix keeps a running
  hasher; the append-shape commit hash went from 4.9 ms to 0.002 ms with
  bit-identical digests.
- **Seed-path copy elimination**: the router full-row clone, the seal
  prefix clones (twice 9.39 MB of IDs plus 4.19 MB of text), and the
  final `Encoding` copy are gone; resident span memory for a 4 MiB row
  went from 18.8 MB to 13.8 KB per session.
- **256/1,500-character appends (Python public surface, same-day
  old/new wheel contrast, 21 samples)**: first 256-char append 11.495 ms
  to 8.903 ms (-22.6%); warm 256-char p50 11.445 ms to 8.697 ms
  (-24.0%); first 1,500-char append 14.775 ms to 11.525 ms (-22.0%);
  warm 1,500-char p50 12.826 ms to 9.417 ms (-26.6%); persistent-store
  appends improved 15-22%. Cold, batch, and content-hit cells are level
  or slightly better. No cell regressed.
- The SQLite durable tier is now metered as its own column
  (`public_seed_sqlite`); its semantics and store-format-v1 bytes are
  unchanged.

## Internal (no public API change)

- The three source-identity tools share one implementation
  (`tools/source_identity_common.py`) with coverage cross-checks and a
  routing-core new-file guard; the build-script manifest lists are
  single-sourced.
- Confirmed-dead code was removed and the fs/digest helpers merged, a
  net reduction of about 850 lines in the Rust product tree.
- `Registry::load()` moved from a compile-time embedded table to
  `OnceLock`.
- Payload hashing and record encoding feed 16 KiB stack-buffer chunks;
  bytes are unchanged.
- The pytest configuration is single-sourced (`pytest.ini`) with a
  `slow` marker tier.

## Recertification

All certified source identities were regenerated and re-evidenced on the
release tree:

- corrected-CPU differential: 11 unique artifacts / 12 model families,
  1,437,469 documents / 4,437,141,060 characters, zero mismatches in
  both full-encode and repair probes (oracle `tokenizers==0.22.2`);
- prebuilt GPU differential: `sm_89` (RTX 4090) and `sm_120` (RTX PRO
  6000 Blackwell), 14 families each, 15,437,450 documents /
  49,185,005,184 characters, zero mismatches; the shipped fatbin was
  re-verified byte-for-byte, not rebuilt;
- the Rust API matrices (cpu / `sm_89` / `sm_120`) and the direct-JIT
  `sm_120` matrix replay cleanly under the certified policy;
- `generate_registry.py --check` and `--release-check` report zero
  problems (the checks need `jsonschema` and a built or installed
  `toktier._native` to read the native-host identity from; README.md
  states the prerequisites); wheel self-containment, packaging, and the
  air-gap recipe all pass.
- RTX 5090 installed-wheel acceptance: a 4 MiB cold seed through the
  prebuilt GPU route, then 256 / 1,500 / 100,000-character appends
  through CPU repair, each returning exact HF IDs; batch, content hit,
  restart recovery, added-token fallback, wrong-family errors, and the
  closed/experimental JIT paths all pass; the GPU hardware suite reports
  13 passed / 101 deselected.

## Unchanged

Existing 0.1.1 Python and Rust call signatures and semantics remain
source-compatible; 0.2.0 is additive (`from_pretrained`, the Rust preview
API, `seed_digest_overlap`) with the corrected error classifications
recorded above. `Session::seed` / `append`, snapshot, and patch
contracts; store-format-v1 bytes; HF fallback and fail-closed semantics;
and the fatbin and kernel ABI (seven architectures plus the PTX fallback)
are unchanged.

## Known behavior

- **Session-append headline staleness on the native lane.** After a
  session append served by boundary repair on the native request path
  (`runtime_policy.request_path: "rust_native"`), the headline
  `backend` and `runtime_policy.last_execution` keep the record of the
  previous full routed encode -- typically the session's seed --
  because the native runtime records only routed executions. The
  append itself is exact, and it is reported honestly under
  `session_repair.last` and the store's `append_paths` counters. The
  accounting correction is scheduled for 0.2.1; it touches the
  certified Rust routing core, so it is not being patched on the
  release itself.
- **When the GPU engine opens, under prebuilt delivery.** Certified
  prebuilt delivery -- the default path on a supported GPU -- runs
  requests through the native single-call runtime, and that runtime
  opens the GPU engine while it is being constructed: on the tokenizer's
  first request, whatever that request's size is. So
  `explain()["gpu_backend"]["loaded"]` can read `true` after a short
  first request. This is the native path's callback-free design rather
  than a change in this release, and it does not affect which backend
  executes an input: the 64 KiB crossover still decides that per
  request, and IDs are unchanged either way. JIT delivery and the
  experimental `repair_backend="fastokens"` adapter keep the Python
  host, whose GPU backend still opens lazily at the first input that
  routes to the GPU. README.md and `docs/gpu-jit.md` state both halves.
  Opening the engine lazily on the Rust side as well is recorded as a
  candidate for a later release; it touches a certified hot path, so it
  is not being done on the release itself.

## Install

```bash
pip install --upgrade toktier==0.2.0
pip install --upgrade "toktier[gpu]==0.2.0"
cargo add toktier@0.2.0
```

As with 0.1.x, the Python release artifact is one ABI3 Linux x86-64
wheel. No sdist is published because rebuilding the certified vendored
CPU binary during install would produce a different artifact. The Rust
crates ship as ordinary source packages on crates.io; their published
build carries no compile-time CUDA dependency, so a consumer without a
CUDA toolchain can still build the default features.
