# TokTier 0.2.1

TokTier 0.2.1 is a maintenance release on the 0.2.0 line. Existing 0.2.0
Python facade calls remain source-compatible; served ids, the store format,
the shipped fatbin and kernel ABI are unchanged.

Version axes moved by this release (see `docs/contracts/versioning.md`): the
package version (axis 1) moves to 0.2.1, and the six published crates carry it
together. The public API version, registry schema version, store format
version, kernel ABI version, and certification suite version do not move --
every `explain()`, `doctor`, and reason-code change below is additive. Two
supporting-crate signatures did change; they carry no independent stability
promise and are listed under "Rust crate API" below.

Evidence: the certification statements this release serves are the shipped
`tables/support_registry.json` and the `evidence/` manifests, which the
repository self-checks in README.md re-verify from the tree. The bounded
evidence carry-over channel introduced here holds no records for 0.2.1
(`python tools/verify_carryover.py --check` reports 0 records), so no
certification claim in this release rests on a carried-over judgement.

## Contract corrections

- **Experimental session persistence is now documented as
  fingerprint-isolated, not in-memory-only.** This is a contract-text
  correction: the previous "in-memory only" sentence was never enforced by
  any released implementation. Experimental sessions may persist under their
  implementation fingerprint without making a certification claim; that
  fingerprint isolates them from certified configurations and other engine
  meanings while allowing replay by the same experimental configuration. A
  facade hard-gate test now enforces the isolation.
- **The CLI JSON error envelope is now scoped to the commands that offer
  `--json`.** `docs/contracts/errors.md` Section 4 described the envelope as
  if every command accepted `--json`; `--json` is in fact a per-command option
  carried by `doctor`, `inspect`, and `gpu compile`, and the artifact commands
  reject it as a usage error (exit `64`). This is a contract-text correction:
  no command changed, and the envelope shape itself remains frozen. The
  section now lists the commands, records that the command set is append-only,
  and names a shared root-level `--json` as a 0.3 candidate.

## Rust crate API

- **The Rust crate posture is now explicit.** The six crates published on
  crates.io carry the workspace package version together, while axis 2's
  frozen, stability-promised surface is the Python facade in
  `docs/contracts/api.md`. The `toktier` crate remains the documented Rust API
  preview and the supported Rust package surface. The five supporting crates
  published for Cargo dependency resolution, and the unpublished `toktier-py`
  wheel binding, are internal implementation details with no independent API
  stability promise; their Rust APIs may change in any release.
- **Two supporting-crate changes require source updates for direct
  consumers.** `toktier-routing-core::NativeRouter::new` now takes
  `Option<NativeGpuSource>` instead of
  `Option<Arc<dyn NativeGpuEngine>>`; existing callers with an open engine use
  `NativeGpuSource::Open`, while `NativeGpuSource::Deferred` carries a
  one-shot opener. `toktier-store-sqlite::DbError` adds the
  `Io(std::io::Error)` variant and implements `From<std::io::Error>`, so an
  exhaustive downstream match must add an `Io` arm.
- **The remaining supporting-crate additions expose the deferred-open and
  diagnostic surfaces.** `toktier-routing-core` now exports
  `NativeGpuOpener`, `NativeGpuSource::{Open, Deferred}`, and
  `R_INPUT_POSTPROCESS_ROUTED`; adds
  `NativeRouter::gpu_engine_opened`, `NativeRouter::gpu_engine_open_error`,
  and `NativePrebuiltGpu::preflight`; and re-exports the new runtime items from
  its crate root. This batch has no other public Rust declaration changes.

## Behavior changes (GPU engine lifecycle)

- **The prebuilt GPU engine now opens on the first request routed to
  the GPU, under the native request path.** This lifts the 0.2.0 Known
  behavior entry "When the GPU engine opens, under prebuilt delivery":
  the native single-call runtime previously opened the engine while it
  was being constructed, on the tokenizer's first request of any size,
  so `explain()["gpu_backend"]["loaded"]` could read `true` after a
  short first request. The runtime now carries a deferred opener below
  PyO3 and runs it, GIL released, on the first request at or above the
  `gpu_min_bytes` crossover (or the first stateful seed that routes
  there); requests below the crossover leave the device untouched.
  Which backend executes an input is decided by the crossover exactly
  as before, and ids are unchanged either way. Concurrent first
  requests share one open. A failed open follows the existing
  per-request fallback semantics (`R_EXEC_FAULT` toward the next
  backend in the frozen chain, with `stage: "engine_open"` in the
  event detail); the outcome is latched, so later GPU-routed requests
  fall back without retrying the device, and the latched message is
  reported as `gpu_backend.load_error`. JIT delivery and the
  experimental `repair_backend="fastokens"` adapter keep the Python
  host, whose GPU backend already opened lazily. README.md (three
  language variants) and `docs/gpu-jit.md` state the new timing.
- **The process-wide delivery fact stays honest across the new
  window.** Constructing the native request path now *reserves* the
  prebuilt delivery for the Rust host: a divergent legacy or JIT load
  is refused from that moment on, exactly as it was refused after the
  eager open, while `KernelLoader.is_loaded()` / `delivery()` and the
  `kernel_deliveries.*.loaded` report keep answering with what has
  actually been loaded. The loaded fact is published when the facade
  observes that the open happened (at the end of the request that
  opened the engine, or on `explain()`). `explain()` keys are only
  added: `gpu_backend.load_error` now also carries a latched native
  open failure, and a `gpu_backend.publication_guard` entry appears in
  the exceptional case where the loader refuses the loaded-fact
  publication after the fact.

## Behavior changes (execution diagnostics)

- **A successful native session append that executes an encoder now
  replaces the seed record in the executor ledger.** This lifts the 0.2.0
  Known behavior entry "Session-append headline staleness on the native
  lane" across native configurations. A corrected-Gigatoken append names
  `executed_backend="fast_cpu"`, `source="gigatoken"`, and
  `path="gigatoken_repair"`, with `input_bytes` measured from the bounded
  repair window. A native reference full re-encode names
  `executed_backend="hf"` and `path="native_hf_full_reencode"`, with
  `input_bytes` measured from the full tail-plus-delta transcript; like a
  routed HF full encode, it adds no `source` field. The existing
  `backend_basis: "last_execution"` mechanism therefore updates the headline
  `backend` to the backend that ran. Corrected-Gigatoken accounting is
  consistent on its Rust-native and Python-adapter paths. The separate,
  family-agnostic Python-host window-repair lane is unchanged from 0.2.0:
  `session_repair.last` continues to report that repair rather than writing
  the executor ledger. An exact store hit or empty append still leaves the
  ledger unchanged because it runs no encoder.
- **Lazy native state seeds now name their checkpointed representation
  accurately.** Successful closure-verified seeds that retain sparse span
  checkpoints report the new informational `state_encode` path
  `accelerated_with_lazy_span_checkpoints`. The published
  `accelerated_with_reconstructed_spans` value remains in use for materialized
  payloads that reconstruct the complete span row; no existing diagnostic
  value was removed.

## Behavior changes (native request initialization)

- **Concurrent first requests now wait for one native runtime decision.**
  Runtime construction is guarded per tokenizer and the initialized state is
  published only after construction has produced either a runtime or the
  configured Python-host fallback. This removes a 0.2.0 race in which another
  first caller could observe an incomplete native runtime, use the Python
  adapter for that request, and make the legacy GPU loader latch a spurious
  native-host ownership error. Served ids and the intentional adapter fallback
  configurations are unchanged.

## Behavior changes (reason-code diagnostics)

- **Postprocessing capability routes now have their own reason code.** A request
  that asks for postprocessing which a core-stream-only accelerated backend
  cannot perform is now counted under `R_INPUT_POSTPROCESS_ROUTED` on both the
  native and Python-host request paths. In 0.2.0 the same pre-execution bypass
  was counted under `R_EXEC_FAULT` even though no backend fault occurred.
  Downstream counter aggregations should therefore expect those events to
  migrate one-for-one from `R_EXEC_FAULT` to
  `R_INPUT_POSTPROCESS_ROUTED`; `R_EXEC_FAULT` now reports genuine engine
  open or execution failures only. No existing reason-code identifier was
  removed or reused.
- **Guard-routing events now always identify their stage.** Every
  `R_INPUT_GUARD_ROUTED` detail mapping carries `stage` while preserving its
  existing keys: `engine_guard` identifies a fast-CPU engine guard,
  `span_bridge` identifies the native accelerated state-seed bridge, and
  `state_encode` identifies a facade-owned state-encoding guard.

## Behavior changes (session-store permissions)

- **Fresh Rust SQLite session stores now use owner-only permissions.** Store
  directories created by the Rust session path are explicitly mode 0700, and
  newly materialized SQLite database files and initialization-time WAL/SHM
  sidecars are mode 0600 on Unix, instead of inheriting the process umask.
  This tightens multi-process and container setups that relied on group-shared
  store directories, matching the Python facade's long-standing behavior.
  Pre-existing user directories retain their modes; the 0700 store directory
  is the primary guarantee throughout SQLite's sidecar lifecycle.

## Behavior changes (diagnostics)

- **`toktier doctor` now reports the probed CUDA machine and the selected
  delivery's architecture status.** Additive human and JSON fields list each
  device's index, name, and architecture, report the observed driver version,
  and map the machine's architectures to the certification status of
  `automatic_gpu_delivery`. `cuda_available` is unchanged and continues to
  mean that TokTier's CUDA runtime binding is installed;
  `cuda_hardware_present` separately reports whether the shared device probe
  found a usable CUDA device. The command remains probe-only and never loads a
  kernel.
- **`toktier doctor` now answers whether the automatic GPU route is actually
  eligible, not only whether it is a candidate.** Five additive fields appear
  in both the human and JSON reports: `jit_toolchain_satisfied` (the shared
  judgement of the observed compiler/runtime triple; `null` under the prebuilt
  delivery, which has no such premise, matching
  `GpuEngine.certification_report()`), `jit_toolchain_observed` and
  `jit_toolchain_constraint` (the triple this machine presents and the judged
  set), `automatic_gpu_eligible` (candidacy, an observed device whose
  architecture the selected delivery judges, that delivery's materials, and
  the toolchain premise together), and `automatic_effective_backend` (`gpu`,
  `fast_cpu`, or `hf`). A `toktier[gpu-jit]` install on an unjudged compiler
  previously showed `automatic_gpu_candidate: true` with nothing to say that
  large requests would run on the CPU. `automatic_gpu_candidate` keeps its
  meaning exactly -- torch importable and the GPU not disabled -- and is now
  documented as the installation-level fact it always was. The command is
  still probe-only: it consults the installed torch's two version attributes
  and `nvcc --version`, constructs no tokenizer, and compiles nothing.
- **`explain()` now separates registry status from the effective in-process
  certification verdict.** The additive
  `certification.effective_verdict` field reports `experimental` when an
  eligible route uses an explicit waiver, `certified` when all process
  premises attach, `reference` when the pinned reference oracle served the
  request, and `unverified` when no certificate attaches;
  `certification.state` remains unchanged.
- **A reference-route execution now reports
  `certification.effective_verdict = "reference"` instead of `unverified`.**
  This is a new value in an additive field introduced by this release, so no
  published value changed meaning. `unverified` read as a doubt about the ids
  where none exists: under the reference route the served ids are the pinned
  Hugging Face `tokenizers` oracle's own output -- the implementation that
  defines the exact-ID contract every accelerated route is judged against --
  and the only thing being said is that no *acceleration* certificate
  attaches. `unverified` is now reserved for the cases where nothing is known:
  no registry record for the artifact, or an installed oracle outside the
  certified set (`certification.state = "reference_only"`), where the
  reference that runs is not the pinned one. `docs/contracts/facade.md`
  tabulates the four values.
- **`explain(summary=True)` adds a concise diagnostic view.** The new flat
  mapping reports the family, actual and planned backend headlines, kernel
  delivery, registry certification state, effective in-process verdict, and
  whether any runtime fallback has occurred. The no-argument `explain()`
  mapping is unchanged and remains the full machine-readable report.
- **`explain(summary=True)` now names the time scope of each fact.** The
  summary mixed last-request, plan, process, and lifetime facts, so answering
  "what just happened?" meant opening the full report. Seven additive keys
  make each scope explicit: `last_execution_backend`, `last_execution_path`,
  and `last_execution_source` mirror `runtime_policy.last_execution`;
  `last_execution_fallback` is true exactly when that request finished on a
  backend other than the one selected for it (a mid-request fault or guard
  route -- not the GPU crossover, which decides before selection, and not a
  bounded session repair); `fallback_ever_occurred` states the lifetime
  meaning that `fallback_occurred` has always had; and
  `selected_kernel_delivery` / `loaded_kernel_delivery` separate the delivery
  chosen for a lazy load from the one this process has loaded. Every existing
  key keeps its meaning and value, including the sticky, crossover-inclusive
  `fallback_occurred`, which `docs/contracts/facade.md` now spells out.
- **Unknown tokenizer-family errors in the Python facade now suggest up to
  three close valid family IDs.** Suggestions are computed locally from the
  active artifact manifest, included in the human message when any match, and
  exposed additively as `ArtifactNotFound.details["suggestions"]`; unrelated
  names carry an empty list. The Rust API returns the same
  `ARTIFACT_NOT_FOUND` code without suggestions in 0.2.1.

## Documentation accuracy

- **Comments and rustdoc now match their implementations.** Corrected the tail
  span-storage layout, `TokenBuffer` shared-allocation ownership, the
  `commit_hash` link/payload distinction, and the public `EncodeOptions`,
  `RuntimeBuilder::home`, and `RaggedEncoding::into_rows` contracts.
- **The Rust crate's directory contract is now documented separately from the
  Python one.** `TOKTIER_HOME` and the XDG variables configure the Python
  product; the crate resolves its artifact cache from `TOKTIER_ARTIFACT_CACHE`
  (default `$HOME/.cache/toktier/artifacts`), its optional direct-JIT cache
  from `TOKTIER_JIT_CACHE`, and its session state from
  `RuntimeBuilder::home()`. README.md, `docs/rust-api.md`,
  `docs/rust-lifecycle.md`, and `docs/contracts/config.md` state this, so the
  shipped Rust examples can be run against a chosen directory rather than the
  user's default cache. No Rust behaviour changed in this release; aligning
  the crate with the Python `TOKTIER_HOME`/XDG contract is intended for 0.3.

## Packaging and licensing hygiene

- **All Apache-2.0 crates now ship their license text.** The `toktier-store-core`, `toktier-cuda-driver`, `toktier-routing-core`, and `toktier-store-sqlite` package archives include the same `LICENSE` distributed with `toktier`.

## Tooling and infrastructure

- **Sentinel builds support whole-artifact equivalence judging.** Maintainers
  can explicitly pin every embedded source-identity digest to one fixed,
  equal-length value while comparing native artifacts. The release-artifact
  verifier rejects any wheel containing the sentinel in either byte or
  hex-string form.
- **Version-normalized source identities support version-only carry-over.** A
  reviewable identity-v2 tool hashes the existing three coverage sets while
  normalizing only the enumerated workspace-version fields, with golden
  vectors for both the accepted and refused directions. Future binding and
  registry generation records v1 and v2 together, and a local/CI scanner
  refuses covered code that reads package versions outside known build-fact
  reporting sites.
- **Certification evidence now has a bounded, machine-checked carry-over
  channel.** A same-host sentinel judge compares the complete native extension
  and Rust rlib only after ordered source/lock/byte-shipped applicability
  checks. Add-only records retain the full replay recipe and original evidence
  pointers; the release gate enforces a maximum of three consecutive
  carry-overs and at least one real campaign per minor version. Full
  recertification remains the default.
