# TokTier 0.2.4

TokTier 0.2.4 is a feature and correctness-reporting release on the 0.2 line,
and the first release since 0.2.1. Existing 0.2.x Python facade calls remain
source-compatible; served ids, the store format, the shipped fatbin and the
kernel ABI are unchanged. The two intervening patch numbers were never
published; the work that would have carried them ships here.

Version axes moved by this release (see `docs/contracts/versioning.md`): the
package version (axis 1) moves to 0.2.4, and the six published crates carry
it together. The public API version, registry schema version, store format
version, kernel ABI version, and certification suite version do not move.
One Rust struct grew a public field, one Rust error code moved, and the Rust
build-flag key changed shape; all three are listed under "Rust crate API"
below.

Evidence: the certification statements this release serves are the shipped
`tables/support_registry.json` and the `evidence/` manifests. Every reading
in this release was re-taken against this release's build identities; none is
carried from 0.2.1. The bounded evidence carry-over channel holds no records
for the 0.2 line (`python tools/verify_carryover.py --check` reports 0
records), so no certification claim here rests on a carried-over judgement.

## The Han family joins the certified roster

`kimi_k3` was packaged in 0.2.1 as a locally derived conversion with a
reference-only GPU row. It now has the same shape as the other fourteen
artifacts:

- The product's own GPU engine encodes it end to end. The shipped fatbin
  already carried every device symbol the Han band needs, so no kernel was
  rebuilt; what was missing was the host wiring, which is now in place and
  verified bit-identical against the campaign's oracle container over
  120,000 documents.
- Its registry row reads `certified` for the prebuilt GPU delivery on
  `sm_89` and `sm_120`, with its own evidence manifest
  (`evidence/evidence_manifest_kimi_band.json`) recording the whole-corpus
  campaign: 3,800,016,491 documents, zero mismatches.
- Its CPU lane stays the reference engine by design, as for the other
  families without a certified corrected-CPU row.
- Its conversion is reproducible on your machine:
  `toktier artifacts check-conversion kimi_k3` converts the pinned upstream
  bytes twice and checks that both runs agree, that the result is the digest
  the manifest pins, and that the added-token block is contiguous and fully
  described.

The campaign totals in the README move with it: fifteen artifacts,
57,000,247,365 checks, zero divergence.

## Certification protocol: `gpu-cert-sm120-primary-v1`

From this release, the full per-family GPU campaign runs on `sm_120`
(fifteen families, 1,102,675 documents each, 16,540,125 in total) and `sm_89`
is maintained by a bounded spot check on the same protocol and roster
(100,000 documents per family, 1,500,000 in total). Both report zero
mismatches; both bind the same host build identity, because the `sm_89` host
rebuilds the extension from the same sources and reports the same digest.

The spot check rests on an accumulated cross-architecture record rather than
on assumption: 2,481 of 2,481 whole-corpus verdict groups concordant across
the two architectures, per-family parity of 16.5M documents taken on each of
them in an earlier wave with identical fallback distributions, and 169 GPU
digest vectors equal on both sides. `sm_89` remains a certified row; what
changed is the scale at which each wave re-takes it, and the readings record
their own scale.

## Certification now judges the dependency graph

Through 0.2.1, a build of the Rust crate from the registry replayed the
source digests recorded at publication and answered `certified: true` --
while Cargo had resolved the transitive versions around those sources from
the consumer's own lockfile. The sources were judged; the graph compiled with
them was not.

An accelerated Rust route now asks for both. The crate archive carries the
judged `Cargo.lock` and the judged compiled closure, and the build script
compares them against the lockfile governing this build: the first
`Cargo.lock` above `OUT_DIR`, above the manifest directory when building from
the workspace, or the one named by `TOKTIER_CARGO_LOCK`. Anything but a match
-- a drifted version, no locatable lockfile, an unreadable record -- is not
certified, and `doctor` names which. The next section says exactly what "a
match" covers.

What this changes in practice, said plainly: a consumer who adds the crate
today and lets Cargo resolve the graph will usually see `mismatched`, because
the transitive versions underneath third-party dependencies keep moving while
TokTier's own edges stay pinned. That build falls to the frozen Hugging Face
reference route under `Policy::Certified` instead of claiming a judgement
that was never taken -- the ids are still exactly right; the acceleration is
what is withheld. To get it back, `doctor` prints a
`cargo update --precise <judged version> <package>` command for every package
that differs, ordered so they can be run one after another in the workspace
that owns the governing lockfile; rebuilding then reads `verified`. The
shipped wheel is unaffected by all of this -- it is always built inside the
source workspace with `--locked`.

The mechanism addresses accidental drift. A host that can edit its own
sources can make any self-report say anything, and `docs/rust-api.md` says so
rather than implying otherwise.

## What the judged side of that comparison is

**The set of packages Cargo compiled for the certified build**, taken from
Cargo's own account of that build at release time and shipped with the crate
as `data/build/judged_compiled_closure.json`. For each of those packages,
this build's resolved graph must hold the same version, with the same content
hash for a registry package, and no semver-compatible sibling Cargo would
have unified onto instead.

The obvious alternative -- judging every package reachable in the judged
`Cargo.lock` -- reads more thorough and is not. A lockfile's dependency
lists are the union over every feature and every target, so that set is a
superset of what is linked, and it would refuse a Linux consumer over a
WebAssembly binding, a Windows shim, or an optional dependency no feature
enabled. On this workspace the compiled set is 165 packages where the
reachable set is 227, and a fresh consumer resolution taken on the release
date diverges in six of them where the reachable rule would have named
fourteen. All six really are compiled, so every alignment command `doctor`
prints changes the bytes that run.

The line is *does Cargo compile it*, which one command answers and anyone
can re-run, rather than *is the compiled code ever called*, which would need
a cross-language call graph and could not be re-checked in a gate. Build
dependencies are inside the judgement, because what `cc` produces is linked;
so is `find-msvc-tools`, which `cc` declares unconditionally and Cargo
therefore compiles on Linux as well.

Three things this judgement does not do, stated here because they are easier
to find than to rediscover:

- It does not make a fresh resolution certified. Exact versions age, and six
  transitive packages under third-party dependencies had moved by the time
  this release was measured. `Policy::Certified` routes such a build to the
  reference engine, which returns the same ids.
- It does not judge packages this build compiles that the certified build
  did not -- for instance, one a consumer's own feature unification pulls
  into a judged dependency. That boundary is structural rather than pending:
  a consumer's build script cannot compute its own feature resolution, since
  that would mean running Cargo inside a Cargo build against a workspace an
  unpacked registry copy cannot see. This crate's own features *are* judged,
  in the `features` build flag; the features of transitive packages are not
  observable from where the question is asked.
- `cargo install --locked toktier` answers `unlocated`: the install builds
  in a temporary directory with no lockfile above it, and a registry build
  deliberately does not read the copy beside its own manifest, since
  comparing a packaged file against itself answers nothing. Handing that
  copy over by name, with `TOKTIER_CARGO_LOCK`, is refused for the same
  reason. The installed binary is fully usable and runs the reference
  engine.

`docs/rust-api.md` carries the whole statement, including what each of the
three answers is worth.

## Build flags claim only what a build script can observe

The `build_flags` key of a `runtime_builds` entry records `profile`,
`opt-level`, `target`, `debug`, `target-features`, `rustflags`, and this
crate's own `features`. Every one of those is read from the environment
Cargo gives a build script.

Three keys that earlier releases carried -- `lto`, `codegen-units` and
`panic` -- are not claimed, because Cargo exposes none of them to a build
script. They were inferred from the profile name, which meant a build with
`lto = false` reported `lto=fat` and matched the judged key on it: a
fail-open path present since 0.2.0. Reading `CARGO_CFG_PANIC` is not a fix
either, since it reports the panic strategy of the build script -- which
Cargo always compiles for the host with unwinding -- and still reads
`unwind` under a `panic = "abort"` profile. Not claiming them is the honest
form of not knowing them.

`rustflags` (`CARGO_ENCODED_RUSTFLAGS`) is claimed instead: it can be
observed, and it is where a `-C` codegen switch appears when a caller sets
one. A build that sets RUSTFLAGS is therefore not the judged build.
`Policy::Experimental` remains the way to take the accelerated route
knowingly anyway, and `doctor` names the key that differs and both ways
forward.

## Roots that cannot hold private state answer inside the contract

Three ways a resolved directory root could leave the error contract, all now
closed:

- `TOKTIER_HOME` pointing at a regular file ended the command with a
  `NotADirectoryError` traceback, no code and no envelope.
- An empty `HOME` with no XDG override expanded `~` to nothing, reported
  `/.cache/toktier` as this machine's layout, and met a bare
  `PermissionError` further in. Such an environment is now refused with a
  remedy while naming one still helps, rather than guessed at.
- Directories created on the way to a leaf arrived at the process umask, so
  a fresh cache root came out `0775/0775/0700` where
  `docs/contracts/config.md` section 5 offers 0700 for every directory the
  layer creates.

Both faces now create every directory they make owner-only, the intermediate
ones included and independently of the umask, and leave directories that
were already there exactly as their operator has them. A location that
cannot become a private directory answers `CONFIG_INVALID`, carrying the
operating system's own exception in `cause`.

`toktier doctor` answers the same question rather than printing paths
beneath an unusable root: `directory_roots_usable` and
`directory_roots_problem` report whether the three resolved roots can hold
what they are for, and name what stands in the way when they cannot. The
probe stays read-only -- creating the roots to find out whether they can be
created would make it an operation.

## Every command answers the way the contract says

`artifacts check-conversion` refused a family that is downloaded whole
rather than converted with one line of prose: the right exit code, but no
`error <CODE>:` prefix without `--json` and no envelope with it, in either
flag position. It now raises `UNSUPPORTED_CONFIG` carrying the command that
does answer for that family, and a failed conversion gate raises
`ARTIFACT_HASH_MISMATCH` carrying both digests and which claims did not
hold.

`artifacts import` given a file that is not a bundle wrote five lines: the
`BUNDLE_INVALID` headline followed by the tar reader's account of each
compression method it tried. Section 4 of `errors.md` freezes that report
as one line. The reader's account now travels in `details["cause"]`, which
`--json` delivers whole, the way a hub client's message travels.

## The last execution is the one that ran

A short session's repair window covers the whole text, so there is no safe
cut to find and the grown text is re-encoded on the reference engine. Only
the successful bounded window recorded an execution, so
`runtime_policy.last_execution` went on reporting the seed encode, and a
session whose latest answer came from the reference path headlined the
accelerated one. The ids were never affected. The reference re-run now
records its execution; an empty delta still records nothing, because nothing
ran. A repair falling back to the exact engine remains a repair-layer
decision with its own counters, not a routing fallback.

## The Rust crate says what a derived family is

`kimi_k3`'s certified artifact is converted on the installing machine from
the `tiktoken.model` its upstream repository carries. The Rust crate did not
know that: it asked the hub for the file the manifest names and reported the
404 as `NETWORK_ERROR`, which a Python-free consumer could neither act on
nor tell apart from an outage. The crate now reads the same shipped
conversion table the Python package does, and refuses before any request
with `ARTIFACT_NOT_FOUND` naming the conversion, its pinned upstream inputs,
and the two ways the bytes arrive. It answers that way offline too: being
air-gapped is not what stands between a derived family and its artifact,
and an air-gapped reader is the one who most needs the two routes named,
so the question is asked before the offline gate rather than after it.
Everything after acquisition is unchanged: an artifact cache holding those
bytes is used as it stands, `import_bundle` installs one, and
`Runtime::load_local` opens an explicit directory.

## The source archive is coherent with its own README

Four links in the README that travels inside the Rust source archive did not
resolve from there: the Simplified-Chinese translation and the three
evidence manifests it names as the records behind its claims. The archive
now carries `evidence/`, `data/`, and the translation, which turns five of
the seven self-check commands into commands a reader can run from the
delivery; the remaining two say why they need a repository checkout.

## Rust facade improvements

- **`TOKTIER_HOME` and the XDG variables now place the crate's
  directories.** The artifact and JIT caches keep their own most-specific
  variables and otherwise fall back to `$TOKTIER_HOME/cache`,
  `$XDG_CACHE_HOME/toktier`, and `$HOME/.cache/toktier`, in that order, with
  an empty value counting as unset. Persistent sessions with no explicit
  `home()` resolve `$TOKTIER_HOME/state`, `$XDG_STATE_HOME/toktier`, or
  `$HOME/.local/state/toktier`, and are refused when none of the three is
  set: session state is not rebuildable and is not placed by guesswork.
- **A mistyped family gets the closest ids.** The Rust facade computes the
  same ranking the Python facade does -- difflib's `get_close_matches`,
  cutoff 0.6, at most three -- so the same typo gets the same answer on
  either surface.
- **`ErrorCode` has a published meaning table.** `docs/rust-api.md` carries
  a row per variant, marking the three that are deliberately wider than
  their Python namesakes.

## Python facade improvements

- **`session()` ships.** The context manager of `docs/contracts/api.md`
  Section 5 is available on the facade and yields the `SessionUpdate` the
  contract describes, with `replace_from` reporting the longest surviving
  prefix. Two deviations are recorded in `docs/contracts/facade.md`
  Section 7: `store=` may be omitted or repeat the directory given to
  `load(store=...)` and a different one is refused rather than ignored, and
  `session()` accepts `text=`, the transcript already exchanged, which is how
  a stored conversation is resumed.
- **`--json` is accepted by every command, before or after it.**
  `toktier --json artifacts verify FAMILY` and
  `toktier artifacts verify --json FAMILY` are one request. `fetch`,
  `verify`, `export`, `import`, and `version` gain machine-readable success
  payloads carrying exactly what their prose lines carried; without the flag
  every line is byte-for-byte what it was.
- **A download client's failure is a command failure.** When the hub client
  raises -- a repository that needs credentials is the ordinary case --
  `artifacts fetch` reports `ARTIFACT_NOT_FOUND` with the client's exception
  type in `details.cause` and a remedy beside it, exits `2`, and writes the
  `--json` envelope when asked, instead of letting that client's exception
  escape. The classification happens at the fetch boundary, so the facade and
  the library see the same code the command does.
- **`toktier doctor --family FAMILY`** adds a `family` section describing
  what this machine would do with one family: its certification identity and
  evidence id, its `fast_cpu` and GPU statuses, the selected delivery's
  status on each observed architecture, and two effective-backend answers,
  one at or above the GPU threshold and one below it. Without the option the
  section is `null` and every other field is unchanged.

## Rust crate API

- **`RuntimeBuildFacts` gains `dependency_closure`.** It reports how the
  resolved dependency graph of this build compares with the judged one:
  `verified`, or an `unlocated:` or `mismatched:` line that also says what
  would align the build. Code that constructs or exhaustively destructures
  this struct needs the new field; code that reads it does not.
  `toktier::DEPENDENCY_CLOSURE` is a new public constant carrying the same
  string.
- **Path-policy refusals report `CONFIG_INVALID`, not `IO_ERROR`.** A cache,
  bundle, or JIT root containing a parent-directory component, a
  symbolic-link component, or a non-directory component -- and a final path
  that is not a regular directory -- is a statement about a configured
  location, not a failure of an attempted operation. Reporting it as I/O
  invited a retry that could never succeed. Messages are unchanged; code
  matching on `ErrorCode::Io` for a refused root needs the one-line update.
- **A converted store error names its code once.** `StoreError`'s own
  `Display` writes a `[CODE]` prefix and so does the facade's `Error`; the
  conversion used to carry both, so a checksum rejection read
  `[STORE_CORRUPT] [STORE_CORRUPT] record checksum mismatch`.
  `StoreError::message()` is the new accessor for the body alone.
- `RuntimeBuildFacts` also grows `build_flag_divergence:
  Option<String>`: why the build flags of this build are not the judged
  ones, when a judged entry agrees with it on every other axis.
- `runtime_builds` entries carry seven build flags: `lto`, `codegen-units`
  and `panic` are absent, `rustflags` is present. Consumers that read the
  shipped registry rather than the crate see the same shape.
- `dependency_closure` is a `String` with a three-way shape: `verified`,
  `unlocated: …`, or `mismatched: …`. Its `mismatched:` text describes
  packages this build compiles, and carries the command that aligns each.

## Python API

No public Python signature changed. `CONFIG_INVALID` and
`UNSUPPORTED_CONFIG` answer for conditions that previously escaped the
contract, and `ARTIFACT_HASH_MISMATCH` answers for the conversion gate; all
three are documented additions to existing codes rather than new codes.

## Upgrading

`pip install --upgrade toktier`. No stored session needs migration and no
cached artifact needs re-fetching. Rust callers should read the API notes
above: each is a one-line adjustment and none affects served ids. Consumers
who set RUSTFLAGS should expect an explicit statement that they do, where
earlier releases quietly accepted such a build as the judged one.
