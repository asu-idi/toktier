# TokTier 0.2.5

TokTier 0.2.5 is a dependency-footprint and diagnostics release on the
0.2 line. Served ids, the store format, the shipped fatbin, and the
kernel ABI are unchanged, and existing Python facade calls remain
source-compatible.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.5, and the six published
crates carry it together. The public API version, registry schema
version, store format version, kernel ABI version, and certification
suite version do not move.

## Default features: `network` is now opt-in

The `toktier` crate's default feature set is `sqlite`, `prebuilt-gpu`,
and `serving`. `network` remains available and unchanged; it is simply
no longer enabled unless a consumer asks for it.

Enabling it explicitly restores exactly the previous behaviour:

```toml
toktier = { version = "0.2.5", features = ["network"] }
```

What this changes and what it does not:

- Without the feature, uncached remote acquisition answers
  `NETWORK_DISABLED` instead of reaching the network. Verified caches,
  `ArtifactSource::LocalDirectory`, `verify`, `inspect`, bundle
  `import`/`export` over cached bytes, `Runtime::load_local`, and the
  air-gap workflows are all unaffected.
- Consumers that already set `default-features = false`, or that
  already list `network` explicitly, or that build with
  `--all-features`, see no change at all.
- The Python wheel is unaffected in every respect. Its native module is
  built from `crates/toktier-py`, which does not depend on the
  `toktier` crate, and Python-side artifact retrieval goes through
  `huggingface-hub`. The wheel's compiled closure never contained
  `ureq` or a TLS stack.
- The `toktier-rust` CLI ships with the crate, so
  `cargo install --locked toktier` now installs a binary that cannot
  fetch. Use `cargo install --locked --features network toktier` for a
  CLI that acquires artifacts over the network.

Why: the network feature pulls sixteen packages into the compiled
closure, including the whole TLS stack. The default build of this
release compiles 149 packages and a build with `network` compiles 165,
so those sixteen are a tenth of what a default build would otherwise
have to carry. Ten of the sixteen published at least one new version in
a recent ninety-day window, so they are also the fastest-moving part of
the graph. Builds that never fetch should not carry, audit, or track
them.

Certification note: the judged build recipe records this crate's
feature list, so the certified default build for 0.2.5 is the one
without `network`. A build that enables `network` differs from the
judged recipe on that key; `Runtime::doctor()` names the divergence.
See `docs/rust-api.md`.

## Diagnostics

- `ExecutionFacts` grows a `reason` field: the machine-readable
  `ReasonCode` for the route that actually ran, drawn from the same
  vocabulary `RoutePlan::reasons` uses. It is `None` when the admitted
  route ran with nothing to explain.
- `DoctorFacts` grows `network_compiled: bool`, so a control plane can
  see whether this binary can acquire artifacts at all.
- The public diagnostic records (`RoutePlan`, `ExecutionFacts`,
  `DoctorFacts`, `RuntimeBuildFacts`, `CudaFacts`, `StoreStats`) are
  now `#[non_exhaustive]`. They are produced by this crate and read by
  callers, so this documents the direction they were always growing in.
  Code that constructs them with a struct literal, or matches them
  exhaustively, needs the usual `..` adjustment.

## Performance

`Session.append` reports `replace_from` by finding the first index the
old and new streams disagree on, over the whole accumulated stream. That
search was an element-by-element Python loop, and it was the whole of
the gap an evaluation measured between `Session.append` and the
pre-existing `encode(..., session=)` path: about 20 ns per token of
session length, which is 3.9 ms on a session of a quarter of a million
tokens. It now compares blocks in C and walks only the block that
differs -- the same index, from the same definition, 5.3x faster
(9.5 ms to 1.8 ms at half a million tokens). The rest of the append is
the encode both paths share.

## Records and checks

A documentation review left a batch of small items open at 0.2.3. They
close here:

- The dependency-closure reader names the Cargo lockfile formats it can
  read and refuses one it cannot, rather than parsing it into a closure
  with no edges and answering about that. A governing lockfile whose
  `toktier` entry lists no dependencies is refused for the same reason.
- GPU parity readings carry `scale`, `full` or `spot`, and the registry
  check requires it. Both scales are certified and both report zero
  mismatches; what separated them until now was an unlabelled document
  count.
- `docs/rust-api.md` names the shared `CARGO_TARGET_DIR` case that
  answers `unlocated`, and how `TOKTIER_CARGO_LOCK` resolves it.
- `docs/rust-lifecycle.md` says that the crate's own tests locate
  artifacts through `TOKTIER_TEST_ARTIFACTS`, not through the directory
  table, so `TOKTIER_HOME` does not move that fixture path.
- `docs/support-matrix.md` reconciles the three sibling counts that have
  to be read together: the shipped `counts` object counts rows, the
  basis table counts siblings, and the per-artifact table folds the
  source-file rows into its `identical` column.
- Two accuracy fixes in existing records: the 0.2.4 note said three
  pinned actions moved to "their current major versions" when one was a
  patch within v2, and one action pin was annotated with a branch name
  where every other pin names a version.

## Sparse GPU fallback: a failed batch is halved, not redone

When one document in a GPU batch trips a guard, the batch fails as a
whole and the backend has to work out which document it was. It used
to redo every row of that batch on its own, so one failing document in
a batch of 128 cost 128 separate device passes and the rows that were
never in question paid for the one that was. A measurement campaign
over a 1.1-million-document corpus found this shape dominating the
aggregate wall clock at a fallback rate near one document in a
thousand.

The backend now halves the batch instead: a half that succeeds is
adopted whole, and only a half that still fails is divided again. A
half of one document is that row on its own, which is the call it used
to receive, so the answer any row gets is the answer it got before.

- **Ids are unchanged.** The search relies on a document's ids not
  depending on which other documents share its batch -- the property
  the batch surface already promises (`docs/contracts/api.md` Section
  4) -- and that condition is now pinned by tests across every batch
  shape a halving search produces.
- **Counting is unchanged.** A document that ends on the reference
  path still counts exactly one fallback, and n such documents in one
  batch count n. Sub-batch attempts are internal probes and record
  nothing; `docs/contracts/facade.md` Section 5 states this.
- **The clean path is untouched.** A batch that succeeds takes the
  same code it always did; nothing about halving is on that path.

On the campaign's own fault corpus and packing, halving issues 4,118
device passes where redoing every row issues 35,456 -- 8.6x fewer, and
at most 26 for any one batch instead of 128.

The end-to-end reading was taken for this release. Both versions were
resident in one run on one host and asked in turn, over the campaign's
controlled slice: 220,535 documents, 897,520,054 bytes, five aligned
groups, seven repetitions, no clock throttling recorded, and the two
versions' complete id streams identical. Packed at up to 512 documents
or 4 MB, this release finishes the slice in 0.37 of the time 0.2.4
takes, or 2.7x; packed at up to 128 documents, in 0.57 of it, or 1.8x.
The same slice with the fallback documents removed takes the same time
on both, within 1.6%, which is what leaving the clean path alone looks
like. What moves is the share of the slice the fallback documents carry:
72.9% of the wall clock at the larger packing becomes 26.8%, and 59.9%
at the smaller becomes 29.8%. These are ratios and shares from one host
in one sitting; absolute milliseconds do not travel between machines or
days. The measurement campaign's own model, which predicted this change
would close 88.5% of the distance to a perfect-foreknowledge bound, is a
separate figure and is not restated by this reading.

## Rust crate API

- `ExecutionFacts::reason: Option<ReasonCode>` is a new public field.
- `DoctorFacts::network_compiled: bool` is a new public field.
- `ReasonCode` gains `InputPostprocessRouted` and `SessionNoSafeCut`. The
  enum was already `#[non_exhaustive]`, so a `match` over it already
  carried the arm that receives them.
- Ten public records became `#[non_exhaustive]`: `RoutePlan`,
  `ExecutionFacts`, `DoctorFacts`, `RuntimeBuildFacts`, `CudaFacts`,
  `StoreStats`, `ArtifactInspection`, `BundleInspection`,
  `BundleFileInspection`, and `ServingTimings`. `ServingLimits` is not
  among them: callers construct it, so it is an input rather than a
  record this crate produces.
- In the sibling crate `toktier-routing-core`, `RoutedIds` gains
  `reason: Option<&'static str>`, the `R_*` code its ledger recorded for
  that input. This is what the facade's `ExecutionFacts::reason` reads,
  and it is why that field is a quotation rather than an inference.
- `toktier-routing-core`'s prebuilt GPU engine resolves a failed batch
  by halving it rather than redoing every row. No signature changed;
  the behaviour is described under "Sparse GPU fallback" above.
- The same crate's entry store gains
  `session_revision(&self, session_id) -> Option<u64>`, which reads the
  revision out of a record when the entry is not resident. The Python
  extension exposes it as `NativeRuntime.session_revision`. Neither
  opens, writes, or makes a session resident.

## Python API

No public Python signature changed. One documented value begins to
mean what it said, and that is visible:

- **`Session.revision` is durable.** A conversation resumed in a later
  process now reports the revision its record carries and continues
  from there, where it used to restart at `0` and report `1` after its
  next append. Nothing about the stored format changed to make this
  true -- the record has carried `session_revision` at offset 56 since
  format v1, and the Rust `Session::revision()` already reported it
  across a restart. No stored session is affected and no format
  version moves.
- **The number can be lower than it was, once.** It is the store's own
  revision rather than a count of appends made through one object, and
  the store's genesis write is revision `0`, so a session written with
  three turns reads `2` where it used to read `3`. Callers comparing a
  revision recorded under an earlier release should re-read it rather
  than expect it to have only grown.
- **`Tokenizer.store_session_revision()` returns a number where it
  returned `None`.** The certified configurations serve sessions from
  the native request runtime, which that lookup did not consult, so it
  answered `None` for every session the product actually stores. A
  tokenizer bound to a store directory now opens that store to answer;
  one without a store directory is unchanged in every respect.
- An in-memory session still counts the writes made through the object.
  That is not a store fact, is not durable, and is unchanged.

## Upgrading

`pip install --upgrade toktier` for the Python package; nothing to do.

Rust callers who rely on uncached remote acquisition should add
`features = ["network"]`, as shown above. Callers who construct the
diagnostic records themselves need the `..` adjustment described under
"Diagnostics".
