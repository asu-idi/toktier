# TokTier 0.2.6

**Status: in preparation.** This document is written as the 0.2.6 work
lands and is not a published release note yet. Numbers, evidence
references, and the release date below are filled in at the release cut.

TokTier 0.2.6 is a certification-scope release on the 0.2 line. Served
ids, the store format, the shipped fatbin, and the kernel ABI are
unchanged, and existing Python facade calls remain source-compatible.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.6, and the six published
crates carry it together. The public API version, registry schema
version, store format version, kernel ABI version, and certification
suite version do not move.

## What `certified` says from 0.2.6

Through 0.2.5 a Rust build was certified only when every package it
compiled -- 149 in the default build -- was the one the certification
campaign compiled. That rule refused a build over packages that never
touch tokenization: an error-handling crate, a build-script helper, a
container. It also asked consumers to align packages their application
graph resolves for them, which in practice is not available.

From 0.2.6 the certificate names its subject: the **certified core** --
TokTier's own crates, the packages they call directly, and the
text-semantics libraries beneath them (regex engines, Unicode property,
normalization and segmentation data and algorithms, SentencePiece
normalization). Every one of those still has to be, byte for byte, the
one the campaign compiled, together with the source identities,
toolchain and build flags of a judged entry. A build whose core differs
is not certified; it routes to the reference engine and its ids stay
exactly right, as before.

Packages outside the core are still compared. When they differ,
`doctor` says so in a new `runtime_build.dependency_advisory` line next
to `certified`, names each package, and prints the `cargo update
--precise` commands that align them. That advisory does not change
`certified` and does not move any request off the accelerated route.
The whole-closure reading keeps its name, type and three-way shape as
`runtime_build.dependency_closure`; consumers who want the 0.2.4/0.2.5
rule can require it to read `verified` themselves.

This narrows what the certificate claims. It does not claim that
packages outside the core cannot influence behaviour; it says which
packages the certificate covers and reports the rest.

Lineage, stated plainly: 0.2.1 certified a registry build without
looking at the resolved graph at all; 0.2.4 and 0.2.5 refused a build
over any package in the compiled closure; 0.2.6 refuses over the core
and reports the rest. The change is a re-drawing of the certificate's
subject, made because a tokenizer library lives inside application
graphs it does not control, and because a certificate should say what
was tested.

### How the line is drawn

Three mechanical rules, re-derivable from this repository and recorded
with the answer in `data/build/judged_compiled_closure.json`:

- **R0**, the six crates this repository publishes.
- **R1**, their non-development direct dependencies that an encode-path
  source file names. Every one is pinned exactly by at least one of our
  own edges, which a generation gate requires, so an R1 package cannot
  drift by version. `fs2` and `tar` are direct dependencies that only
  the artifact cache and bundle import name, so they are outside.
- **R2**, the text-semantics libraries an engine crate reaches:
  `regex`, `regex-automata`, `regex-syntax`, `onig`, `onig_sys`,
  `unicode-segmentation`, `unicode_categories`, `icu_properties_data`.

Whether a package belongs to R2 is data, and its completeness is a
gate: any package in the closure whose name matches the text-semantics
name net must be classified by hand, on one side or the other, with a
reason, or the record cannot be generated.

### Text semantics are compared by behaviour version

An R2 package is compared by the version of the tables it carries
rather than by its own version. `regex 1.13.1 -> 1.14.0` with the same
Unicode tables is a package move, and the certificate holds; tables
that read another Unicode version are a change of behaviour, and the
certificate does not hold. `Runtime::doctor()` reports each unit in
`runtime_build.behavior_versions`, beside the judged value and with the
source it was read from: the newest `\p{Age=...}` the regex engine
accepts, `onig::version()`, and `unicode_segmentation::UNICODE_VERSION`.
A unit whose version cannot be read falls back to comparing package
versions exactly, which is the strict direction, and so does a core
package that resolves from somewhere other than the judged one.

What this leaves open, stated as plainly as the rest: an R2 upstream
that publishes new tables between our release-day re-judgement and the
next one puts fresh consumers back on the reference engine until they
align their lockfile. That is the cost of keeping the libraries that
decide where text is cut inside the certificate's subject.

### One premise that was never written down

Certification compares TokTier's ids with the ids the frozen Hugging
Face reference engine produces. That engine cuts text on Unicode
character classes it reads from Oniguruma; the fast CPU pre-tokenizer
reads the same classes from ICU property data. Nothing said the two had
to carry the same Unicode version, and in August 2026 they stopped
doing so: ICU4X 2.1 moved to Unicode 17.0 while Oniguruma stayed on
16.0. Measured exhaustively, 4,804 code points answered differently --
4,803 assigned in 17.0, including the whole of CJK Extension J, and one
older code point, U+0295, whose category changed. No corpus in the
certification campaigns is new enough to contain them, which is why
every parity reading stayed at zero mismatches while this was true.

This release pins the property data to the Unicode version the judge
carries, which takes the default compiled closure from 149 packages to
148, and ships the comparison as a gate: every scalar value, every class
the shipped patterns name, run by `tools/check_class_parity.py` and by
CI. The certification criteria in `docs/rust-api.md` and
`docs/contracts/registry.md` now state the premise.

## Where the code runs: a device nobody judged

The section above is about which code a build compiles. This one is
about where it runs, and it is the second half of the same idea.

A certification campaign measures a kernel on the devices and with the
compilers it actually had. A device it never ran on is not a device it
found wrong -- nobody looked. Through 0.2.5 both were refused with one
word: an sm_100 card and a build whose host digest did not verify both
read "uncertified" and both routed to the reference engine.

### What you see

`Policy::Supported` (`"supported"` in Python) is the new default. Under
it a device architecture or a JIT compiler triple no campaign judged
runs, provided the shipped kernel loads there and every constraint the
registry does bind still verifies, and the route is labelled:

- `supported_untested` -- the engines and digests are the judged ones,
  and this combination is not one a campaign measured.
- `locally_verified` -- the same, and a check on this machine compared
  the route with the reference engine and they agreed.

`Policy::Certified` keeps its frozen meaning exactly and is the strict
switch: under it an unlisted architecture and an unjudged compiler
triple route to the reference engine, as they always have. Nothing else
was relaxed. A source, host or flags mismatch still refuses; a
world-writable compiler component still refuses unless the caller
accepts it explicitly; a certified core that does not verify still
routes to the reference engine.

Driver and CUDA runtime versions are reported as environment facts and
are not certificate premises. A registry row that binds `driver_min`
still checks it, as a precondition for the image loading at all.

### Measuring it yourself

```text
toktier-rust verify-local --engine both --family qwen3_8b --input my-text.txt
toktier verify-local --family qwen3_8b --input my-text.txt
```

Both encode your documents on the accelerated route and on the reference
engine and compare every id. `--synthetic N` builds documents from rules
instead, so a check needs no corpus and no network -- no text of anyone
else's ships with either package.

What they write is a record, not a certificate. It is filed under the
device, delivery, image digest, compiler triple, driver, source
identities and family artifact it was taken under, so it stops applying
the moment any of those moves; `--forget` removes it. A check that
disagreed is kept and reported, and the route keeps the label it would
have had if nobody had run one: running the tool never makes a
configuration more restricted than not running it, and nothing is
changed on your behalf. Nothing runs a check automatically.

### Two more devices on the certified list

`sm_80` (A100) and `sm_90` (measured on an H200; the H100 shares that
architecture, but no reading in this wave was taken on one) are certified
rows in 0.2.6. Both were measured on NCSA Delta -- an `A100-SXM4-40GB` and
an `H200`, both on driver 595.71.05 -- against the architecture images the
shipped fatbin already carried, on the same bounded spot check the `sm_89`
row is held by: fifteen families, 100,000 documents each, 6,104,728,470
characters, zero mismatches, one native host identity shared with the rows
already on file.

The honest limitation belongs next to the claim. `sm_89`'s spot check
rests on a full per-family campaign taken earlier on the same fatbin
lineage; `sm_80` and `sm_90` have the spot check and nothing behind it
yet. If your work turns on one of these two, `verify-local` above is
still the instrument that answers for your text on your machine.

## The experimental Fastokens adapter: what was measured

Nothing about this adapter changes in 0.2.6. It stays an explicit,
opt-in experimental session adapter, it still reports
`exact_id_guarantee: false`, and the certified policy still never
selects it. What is new is that there are measurements behind that
position now instead of only a disclaimer.

Over the course of our certification campaign for this adapter --
differential runs at increasing scale, up to 998,857,881 documents per
artifact against Hugging Face `tokenizers==0.22.2`, comparing the full
token-id list per document -- we observed five defects in the upstream
0.3.1 code relative to that reference. One raises an error on a rare
character. Four are silent id divergences: nothing is raised and no
diagnostic is emitted, so a caller cannot tell from the return value
that anything differed. Each of the five has a standalone reproduction
that fails on a build made from unmodified upstream sources. Reports
have been prepared for the upstream project. With five patches of our
own applied to those sources, the final differential -- 998,857,881
documents against each of 15 tokenizer artifacts, 14,982,868,215
document-artifact comparisons -- recorded zero id divergences, under a
guard of 108 codepoints that routed 505 documents per artifact to the
reference path instead of the adapter.

The honest limitation belongs next to the claim, and here it is about
naming the thing measured. The subject of those readings is a source
revision -- upstream 0.3.1 plus our five patches -- but the identifier
the adapter can actually show you is the `engine_digest` in `explain()`,
and that digest covers every file the distribution installs, including
the compiled extension that is nearly all of its bytes. So the digest
names a wheel, not a source revision, and a wheel built from the same
sources on another machine reports a different one. Version separates
none of it either: every build reports `0.3.1`, because patching sources
does not change distribution metadata. The three builds behind the
numbers above are:

| build | `engine_digest` |
|---|---|
| patched sources, the wheel the 998,857,881-per-artifact run used | `4c7e9c9f03313cc0c262eb781e9cf3389cc802ea5bd0eee9db367b326d0c17d9` |
| patched sources, the wheel the session, topology and splice checks used | `24e3cccaef6d97f43d016a2483d1b423a0e40e4717b756ce7f47da1894f14aa2` |
| unmodified upstream sources, the comparison build | `8600f509c10dc03c98013bb9b7be214e0fae4bcb3f3618b937cd5f92ccc9120a` |

If your installation reports some other digest, these numbers are not
about it -- not necessarily worse, just unmeasured.

What backs these readings -- the differential run records, the five
standalone reproductions, the patches, and the three wheels whose digests
are listed -- lives in the audit records behind this document and does not
ship inside the package, on the same footing as the upstream audit records
`docs/support-matrix.md` describes. What ships is the summary in this
section.

A pinned distribution of the patched build is being prepared for a
subsequent release, which is what would let a digest be quoted and
checked rather than only described.

## Rust crate API

- `RuntimeBuildFacts` grows three public fields next to `certified`:
  `core_closure: String`, `dependency_advisory: Option<String>`, and
  `behavior_versions: Vec<BehaviorVersion>`. The struct is
  `#[non_exhaustive]`, as it has been since 0.2.5.
- `BehaviorVersion` is a new public record: `unit`, `observed`,
  `judged`, `source`.
- `toktier::DEPENDENCY_CLOSURE` keeps its name, type and three-way
  shape. What changed is what it is used for: it is reported, and
  `core_closure` gates.
- The shipped record `data/build/judged_compiled_closure.json` moves to
  schema `toktier.rust_compiled_closure.v2`, carrying a `tier`, a
  `criterion` and the rule text. A build that reads a record of another
  schema, or an entry with no tier it knows, fails closed.
- `Policy` gains `Supported`, which is its `Default`. `Certification`
  gains `Supported` and `LocallyVerified`. Both enums are
  `#[non_exhaustive]`, so this is an addition; a match that listed the
  old variants and a wildcard keeps compiling, and one that gated on
  `Certification::Certified` still admits exactly what it used to.
- JIT products carry an `assurance` and the binding manifest moves to
  `toktier.rust_jit_binding.v3`. A product built under an unjudged
  triple is cached and reused like any other, which is a change from the
  0.2.5 behaviour where the only way to build one was `Experimental` and
  its products were deliberately not persisted.

## Python API

No public Python signature changed. The tier split is a Rust-crate
certificate; the wheel's certification comes from the shipped registry
and its own probes, and that is unchanged.

What did change is the default policy and what the report says about it:

- `RoutingPolicy.SUPPORTED` is added and is the default of
  `Config.routing_policy`. Worth saying plainly, because the word invites
  the opposite reading: **`"auto"` is not the default policy.** It has
  always been an alias for `CERTIFIED` and it still is, so a caller who
  wrote `policy="auto"` selects the strict setting -- judged devices and
  judged compilers only -- while a caller who passed nothing gets
  `SUPPORTED`. Neither meaning changed; they simply stopped being the
  same thing. The keyword is `policy=`; `toktier.load` has no `tier=`
  argument to pass the alias through.
- `explain()` grows `supported_untested`: the coverage reasons the
  policy admitted, in the same shape as `plan_reasons`, empty on a
  judged combination. `certification.state` gains `supported_untested`
  and `locally_verified`; `certification.effective_verdict` gains
  `supported`. A reader that gated on `"certified"` gets exactly the
  configurations it used to.
- `REQUIRE_ACCELERATED` follows the default rather than `CERTIFIED`: it
  asks that some accelerated path be eligible, and on a device outside
  the judged list the honest answer to that question is now yes.
- `Tokenizer.verification_key(engine)` is added, and
  `toktier verify-local --family <family>` takes and records the
  measurement. It is a top-level command on both faces and takes the
  same options on each.
- `toktier gpu compile` asks for the policy this machine resolves rather
  than pinning `certified`; `--accept-uncertified-jit` keeps its narrow
  job under the stricter policies.

## Upgrading

`pip install --upgrade toktier` for the Python package; nothing to do.

Rust callers who want the previous rule can gate on
`runtime_build.dependency_closure == "verified"` themselves. Callers who
match `RuntimeBuildFacts` exhaustively need the usual `..` adjustment,
as the struct grew three fields.

Callers who want the previous admission rule -- judged devices and
judged compilers only -- select `Policy::Certified` in Rust or
`policy="certified"` (or `policy="auto"`) in Python. That is the one
change in this release that a configuration file can make for a whole
machine: `routing_policy = "certified"` under `TOKTIER_HOME`.
