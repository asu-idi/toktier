# TokTier 0.2.6

**Status: in preparation.** This document is written as the 0.2.6 work
lands and is not a published release note yet. Numbers, evidence
references, and the release date below are filled in at the release cut.

TokTier 0.2.6 is a certification-scope release on the 0.2 line. Served
ids, the store format, the shipped fatbin, and the kernel ABI are
unchanged, and existing Python facade calls remain source-compatible.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.6, and the six published
crates carry it together. The public API version, registry schema
version, store format version, kernel ABI version, and certification
suite version do not move.

## What `certified` says from 0.2.6

Through 0.2.5 a Rust build was certified only when every package it
compiled -- 149 in the default build -- was the one the certification
campaign compiled. That rule refused a build over packages that never
touch tokenization: an error-handling crate, a build-script helper, a
container. It also asked consumers to align packages their application
graph resolves for them, which in practice is not available.

From 0.2.6 the certificate names its subject: the **certified core** --
TokTier's own crates, the packages they call directly, and the
text-semantics libraries beneath them (regex engines, Unicode property,
normalization and segmentation data and algorithms, SentencePiece
normalization). Every one of those still has to be, byte for byte, the
one the campaign compiled, together with the source identities,
toolchain and build flags of a judged entry. A build whose core differs
is not certified; it routes to the reference engine and its ids stay
exactly right, as before.

Packages outside the core are still compared. When they differ,
`doctor` says so in a new `runtime_build.dependency_advisory` line next
to `certified`, names each package, and prints the `cargo update
--precise` commands that align them. That advisory does not change
`certified` and does not move any request off the accelerated route.
The whole-closure reading keeps its name, type and three-way shape as
`runtime_build.dependency_closure`; consumers who want the 0.2.4/0.2.5
rule can require it to read `verified` themselves.

This narrows what the certificate claims. It does not claim that
packages outside the core cannot influence behaviour; it says which
packages the certificate covers and reports the rest.

Lineage, stated plainly: 0.2.1 certified a registry build without
looking at the resolved graph at all; 0.2.4 and 0.2.5 refused a build
over any package in the compiled closure; 0.2.6 refuses over the core
and reports the rest. The change is a re-drawing of the certificate's
subject, made because a tokenizer library lives inside application
graphs it does not control, and because a certificate should say what
was tested.

### How the line is drawn

Three mechanical rules, re-derivable from this repository and recorded
with the answer in `data/build/judged_compiled_closure.json`:

- **R0**, the six crates this repository publishes.
- **R1**, their non-development direct dependencies that an encode-path
  source file names. Every one is pinned exactly by at least one of our
  own edges, which a generation gate requires, so an R1 package cannot
  drift by version. `fs2` and `tar` are direct dependencies that only
  the artifact cache and bundle import name, so they are outside.
- **R2**, the text-semantics libraries an engine crate reaches:
  `regex`, `regex-automata`, `regex-syntax`, `onig`, `onig_sys`,
  `unicode-segmentation`, `unicode_categories`, `icu_properties_data`.

Whether a package belongs to R2 is data, and its completeness is a
gate: any package in the closure whose name matches the text-semantics
name net must be classified by hand, on one side or the other, with a
reason, or the record cannot be generated.

### Text semantics are compared by behaviour version

An R2 package is compared by the version of the tables it carries
rather than by its own version. `regex 1.13.1 -> 1.14.0` with the same
Unicode tables is a package move, and the certificate holds; tables
that read another Unicode version are a change of behaviour, and the
certificate does not hold. `Runtime::doctor()` reports each unit in
`runtime_build.behavior_versions`, beside the judged value and with the
source it was read from: the newest `\p{Age=...}` the regex engine
accepts, `onig::version()`, and `unicode_segmentation::UNICODE_VERSION`.
A unit whose version cannot be read falls back to comparing package
versions exactly, which is the strict direction, and so does a core
package that resolves from somewhere other than the judged one.

What this leaves open, stated as plainly as the rest: an R2 upstream
that publishes new tables between our release-day re-judgement and the
next one puts fresh consumers back on the reference engine until they
align their lockfile. That is the cost of keeping the libraries that
decide where text is cut inside the certificate's subject.

### One premise that was never written down

Certification compares TokTier's ids with the ids the frozen Hugging
Face reference engine produces. That engine cuts text on Unicode
character classes it reads from Oniguruma; the fast CPU pre-tokenizer
reads the same classes from ICU property data. Nothing said the two had
to carry the same Unicode version, and in August 2026 they stopped
doing so: ICU4X 2.1 moved to Unicode 17.0 while Oniguruma stayed on
16.0. Measured exhaustively, 4,804 code points answered differently --
4,803 assigned in 17.0, including the whole of CJK Extension J, and one
older code point, U+0295, whose category changed. No corpus in the
certification campaigns is new enough to contain them, which is why
every parity reading stayed at zero mismatches while this was true.

This release pins the property data to the Unicode version the judge
carries, which takes the default compiled closure from 149 packages to
148, and ships the comparison as a gate: every scalar value, every class
the shipped patterns name, run by `tools/check_class_parity.py` and by
CI. The certification criteria in `docs/rust-api.md` and
`docs/contracts/registry.md` now state the premise.

## Rust crate API

- `RuntimeBuildFacts` grows three public fields next to `certified`:
  `core_closure: String`, `dependency_advisory: Option<String>`, and
  `behavior_versions: Vec<BehaviorVersion>`. The struct is
  `#[non_exhaustive]`, as it has been since 0.2.5.
- `BehaviorVersion` is a new public record: `unit`, `observed`,
  `judged`, `source`.
- `toktier::DEPENDENCY_CLOSURE` keeps its name, type and three-way
  shape. What changed is what it is used for: it is reported, and
  `core_closure` gates.
- The shipped record `data/build/judged_compiled_closure.json` moves to
  schema `toktier.rust_compiled_closure.v2`, carrying a `tier`, a
  `criterion` and the rule text. A build that reads a record of another
  schema, or an entry with no tier it knows, fails closed.

## Python API

No public Python signature changed, and no Python behaviour changed.
The tier split is a Rust-crate certificate; the wheel's certification
comes from the shipped registry and its own probes.

## Upgrading

`pip install --upgrade toktier` for the Python package; nothing to do.

Rust callers who want the previous rule can gate on
`runtime_build.dependency_closure == "verified"` themselves. Callers who
match `RuntimeBuildFacts` exhaustively need the usual `..` adjustment,
as the struct grew three fields.

## Release-cut checklist

Items that are deliberately not final in this tree:

- `CITATION.cff`'s `date-released` and `RELEASE_DATE` in
  `tools/verify_release_identity.py` still carry the 0.2.5 date. They
  move together on the day of the cut.
- The README News entries carry `2026.08.TBD` until that day.
- The whole release certification battery runs on the cut tree. The
  0.2.5 evidence bindings in this tree are stale by construction: the
  version bump, the property-data pin, and the new direct edges each
  move recorded build identities.
