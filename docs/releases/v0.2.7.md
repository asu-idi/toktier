# TokTier 0.2.7

**Status: in preparation.** This document is written as the 0.2.7 work
lands and is not a published release note yet. The release date and the
evidence bindings of the cut tree are filled in at the release cut.

TokTier 0.2.7 is a distribution and certification-scope release on the
0.2 line. Served ids, the store format, the shipped fatbin, and the kernel
ABI are unchanged, and existing Python facade calls remain
source-compatible.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.7, and the six published crates
carry it together. The public API version, registry schema version, store
format version, kernel ABI version, and certification suite version do
not move; the registry gains one optional top-level node under schema
version 1.

## A pinned Fastokens distribution

From 0.2.7, `pip install "toktier[fastokens]"` installs `toktier-fastokens`,
a build of fastokens 0.3.1 that carries five patches from this project. We
publish it because the readings we took on that build -- 15 families,
998,857,881 documents each, zero guarded mismatches -- are readings about
specific bytes, and only wheels we publish have digests we can name.
Nothing about admission changed: the adapter is selected only explicitly
under `policy="experimental"`, is never an automatic route, and
`certification` still reads `experimental`. What is new is a second,
separate answer, `engine_assurance`: when the installed engine is the wheel
we published, it reads `certified_pinned` and `exact_id_guarantee` is
`true` in the guarded sense (ids equal the pinned reference, or the request
is routed to it by a Unicode guard covering 154 combining marks). What is
compared is the engine digest rather than who built the wheel: the
upstream wheel reads `upstream_build`, and a build whose digest is not
among the published ones -- one made from the sdist on another host or
toolchain usually is not -- reads `unrecognized_build`; both read
`false`, and a build whose digest is identical reads as the published one
does. The pinned distribution keeps the import
name `fastokens`; installing it beside the upstream distribution overwrites
shared files, and `toktier doctor` reports which one is present. The
seam-related patches were exercised at eight visible CPUs in the large run
and across six topologies in the topology gate; the evidence, the wheel
digests, and the guard are recorded in the shipped registry. Reports about
the id divergences the patch set addresses have been submitted to the
upstream project.

### What the adapter does now

The adapter used to look the engine up by the distribution name
`fastokens`, which the pinned distribution does not carry, and it hashed
the files a RECORD named rather than the files the import system would
load. It now locates the import package, hashes what is there, and
attributes those bytes to the installed distribution whose RECORD matches
them. Two cases that were invisible before are refused with the reason: a
copy of the package earlier on `sys.path` than the recorded one, whose
bytes no metadata describes (`engine_assurance: unverifiable`), and
metadata whose files were removed by uninstalling the other distribution
that shared them (a reinstall hint is printed). Two distributions
installed side by side are not refused: the bytes on disk belong to one of
them, the report says which, and an `advisory` carries the reinstall
command.

The Unicode guard the differential run applied on the judge's side is now
part of the adapter. The frozen reference (`tokenizers 0.22.2`) does not
canonically reorder 154 combining marks that the engine reorders, so a
document containing one of them would compare unequal for a reason that is
the reference's Unicode vintage rather than the engine. The adapter
compiles the set from the shipped registry, checks it against the digest
the registry records for it, and answers such a request from the pinned
reference on its own path, `hf_full_fastokens_unicode_skew_guard`. The set
is a strict superset of the 108 code points the run used, re-derived on the
published wheel over the whole code space; a wider guard routes more
documents to the reference and cannot turn an equal result into an unequal
one. There is no switch to turn the guard off: it is part of what
`certified_pinned` means. Because the adapter's behaviour changed, its
configuration id moved to `toktier-fastokens-full-experimental-v2`. That
id is part of the session fingerprint, so in-process state from the
earlier meaning misses and is re-encoded -- and a persistent store, which
is written as a whole under one fingerprint, is refused with
`SESSION_STATE_MISMATCH` when it is opened under the new one rather than
re-encoded record by record. See Upgrading.

### Where it is recorded

The shipped support registry gains a top-level `engine_distributions`
node. Its `fastokens` entry records the published wheel by file name,
sha256 and engine digest, the sdist beside it, the upstream revision and
patch series, the oracle and the fifteen families the evidence covers, the
guard set with its digest, and the readings of the four gates with the
evidence id `ev-fastokens-pinned-v1`, which resolves to a shipped evidence
manifest. The node is not a backend status and admits no route.
`tools/fastokens_binding.json` is the hand-written source,
`tools/update_fastokens_registry.py` carries it into the registry after
checking every number against the shipped readings, and the release check
refuses a placeholder wheel digest. The adapter source is bound to the node
it reads.

`packaging/fastokens-pinned/` holds everything the distribution carries
besides the upstream code: the upstream license and notices verbatim, the
NOTICE with the Apache-2.0 section 4(b) statement of modification, the five
code patches and a sixth that adds a notice line to each modified source
file, the change log, the distribution README, the build recipe with digest
and tree-hash checks, the SBOM the published wheel embeds, and the license
bundle of the compiled dependency closure. The 0.3.1.1 artifacts were built
from the five-patch tree before the notice patch existed; the recipe
applies the full series by default and can stop after the five code patches
to reproduce the published tree, and the packaging README says why the two
trees do not compile to the same bytes. A release-asset workflow
(`publish-fastokens.yml`) uploads a future pinned build to PyPI after
checking the assets against the recorded digests; it does not rebuild.

## Coverage added in 0.2.7

### Repositories admitted after the audit snapshot

Two model repositories published after the 2026-08-04 audit snapshot join
the shipped sibling registry. Both ship a `tokenizer.json` byte-identical
to the anchor of a family that is already certified, so each is admitted
on the `identical` basis and no campaign was run for either:

| Repository | Revision | `tokenizer.json` sha256 | Family |
|---|---|---|---|
| `deepseek-ai/DeepSeek-V4-Pro-0813` | `72e1d3230f6c` | `8f9f37ca37fd` | `deepseek_v4_flash` |
| `zai-org/GLM-5.3-Flash` | `3f1971b7b5f7` | `19e773648cb4` | `glm_5_2` |

`from_pretrained()` already resolved both by content before this release,
because the sibling table is keyed on the file digest. What the new rows
add is the audited bookkeeping: a pinned revision to resolve by default,
a countable entry in the support matrix, and the comparison date on
record. The DeepSeek-V4 collection and the GLM lineage now hold seven
listed sub-versions each.

Nothing else moves for these two. The certified artifacts, the three
source identities, the kernel families and the repair tables are all
unchanged, and the accelerated route each repository reaches is the one
its anchor was certified on.

### Examined and not certified: the Qwen3.8 tokenizer

`Qwen/Qwen3.8-27B` and `Qwen/Qwen3.8-Flash-Next` ship one shared tokenizer,
`tokenizer.json` sha256 `0997f410c57a`. It was examined on 2026-08-27 and is
recorded in the support matrix under "Examined and not certified" rather than
counted as coverage.

Its pipeline sections are equal to the certified `qwen3_5_08b` artifact -- the
two share the capability `pipeline.bc687a3b57eba58b`, and their `vocab.json`
and `merges.txt` are byte-identical. What differs is the added-token table: 33
entries against 26, the extra seven being audio and text-to-speech specials.
That is a different artifact under the rule this project applies, its
added-token capability `added-frontend.6f80a43b9fe6a15f` has no campaign
reading behind it, and so both repositories route to the reference engine and
report `R_UNCERTIFIED_ARTIFACT`. Ids stay exactly right; only acceleration is
withheld.

Recording it is the point. A reader who looks for these repositories finds
what was compared and what was concluded, instead of finding nothing.

## Python API

No public Python signature changed.

- `explain()["session_repair"]` for the Fastokens adapter grows
  `engine_distribution`, `engine_assurance`, `assurance_reason`,
  `guarantee_basis`, `known_wheel`, `unicode_guard` and `advisory`;
  `exact_id_guarantee` is `true` only under `certified_pinned` and
  `certification` keeps reading `experimental`. The path name
  `hf_full_fastokens_unicode_skew_guard` is new in `path_counts`.
- `toktier doctor` grows `fastokens_distribution`,
  `fastokens_known_wheel`, `fastokens_engine_assurance`,
  `fastokens_coinstalled`, `fastokens_orphaned` and `fastokens_advisory`
  beside the existing five `fastokens_*` keys;
  `fastokens_exact_id_guarantee` says what `true` means in the same line
  when it holds. With `--family` the family premise is applied as well,
  in the half a reader can act on: `fastokens_family_admitted` says
  whether the adapter has a repair-table entry for that family and
  artifact at all, `fastokens_family_admission_reason` says what a
  session would be refused with when it has none, and
  `fastokens_exact_id_guarantee` reads `false` for such a family.
  `fastokens_engine_assurance` keeps stating the engine-level fact, which
  is a different question.
- `toktier doctor --family <family>` reports `family.plan_reasons`: the
  reason codes the planner recorded for that family with their detail,
  including the axis and the expected and observed values of an engine
  binding that did not verify. `verify-local` points here when the plan
  admitted no accelerated route, so the answer is now where the sentence
  says it is.
- `docs/contracts/facade.md` gains Section 5.2, which states the two
  answers and the guarded meaning of `true`; the three sentences that said
  the adapter carries no guarantee now say "unless Section 5.2 applies".

## Rust API

No public Rust signature changed. `ReasonCode` gains one variant, which
`#[non_exhaustive]` has always asked consumers to expect.

- `ReasonCode::InvalidPriorState` names the outcome a session reports
  when a stored tail did not describe itself consistently and the
  accumulated text was re-encoded from the reference. It used to travel
  as `ReasonCode::Other("invalid_prior_state")`, a string that appeared
  in neither face's vocabulary; `R_INVALID_PRIOR_STATE` is now in
  `docs/contracts/routing.md` Section 5.2 and in the Python
  `ReasonCode`, so both faces name it from one list.
- `toktier-rust doctor --json` prints the typed facts as JSON under the
  same field names. The flag used to be accepted and ignored; an option
  the command does not implement is now refused rather than ignored.
- `ARTIFACT_NOT_FOUND` from the Rust artifact manager says which family
  was asked for, which directory was searched, whether acquisition is
  offline and by which condition, and the two commands that place the
  bytes there. It used to print the raw `os error 2`. The Python package
  answered the same four things from 0.2.6; this is the other half of
  that change.

## Carried over from 0.2.6

- `verify-local` on both faces: when a route served none of the
  documents, the note now distinguishes a route the plan did not admit
  from a route the plan admitted and every document left again for a
  per-input reason. Each face points at its own facilities. The Python
  note names `toktier doctor --family <family>` and `explain()`; the
  Rust note carries the plan's own reason codes and names
  `Tokenizer::plan().reasons`, `ExecutionFacts::reason` and
  `toktier-rust doctor`, because this crate has no `explain()`. Both
  notes are wrapped for a terminal and end in a full stop.
- The Rust build's core-drift hint no longer prints a template command;
  it points at the `dependency_closure` line of the same `doctor` report,
  which carries the runnable `cargo update --precise` commands.
- The dependency advisory names `toktier-rust verify-local` for a host
  that has the CLI and `toktier verify-local` for the Python package, and
  says where the CLI comes from for a crate consumer that has neither.
- A JIT verification record is filed under the compiler triple that built
  the product; before, the Rust face wrote `toolchain: null` for JIT
  records, so a product built by another compiler could read the same
  record. A record filed under the earlier key is ignored rather than
  re-taken: run `verify-local` again to file one under the new key.

## Upgrading

`pip install --upgrade "toktier[fastokens]"` for the Python package with
the adapter. If the upstream `fastokens` distribution is installed in the
same environment, reinstall rather than uninstall one of the two, because
uninstalling either removes the files they share:

```bash
pip uninstall -y fastokens toktier-fastokens && pip install "toktier[fastokens]"
```

A persistent session store written by 0.2.6 with `repair_backend=
"fastokens"` cannot be opened by 0.2.7: the adapter's configuration id is
part of the store's semantic fingerprint, and a store whose fingerprint
does not match is refused with `SESSION_STATE_MISMATCH` rather than
re-encoded. Point `store=` at a new directory; a session is rebuilt by
replaying its text into the new store, which is what a session store
holds a transcript for. Nothing is lost silently: the refusal names both
fingerprints, and the earlier directory is left as it is. Stores written
without the Fastokens adapter are unaffected.

If other code needs the upstream distribution, use a separate environment;
the two cannot coexist under one import name. Rust callers who hold JIT
verification records will find them ignored, because the key they are
filed under gained the compiler triple; running `verify-local` again
files a record under the new key.
