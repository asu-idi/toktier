# TokTier 0.2.8

TokTier 0.2.8 settles a definition 0.2.7 left open: which face of a
tokenizer artifact the reference is. The store format, the shipped
fatbin, and the kernel ABI are unchanged, and existing Python facade
calls remain source-compatible. Served ids change on exactly one class
of input over one packaged artifact, described below; on everything the
certification campaigns judged, nothing moves.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.8. The public API version,
registry schema version, store format version, kernel ABI version, and
certification suite version do not move; artifact records gain two
optional members under schema version 1 (`config_added_tokens`,
`carryover`).

## The reference is the loader face

An artifact's identity key remains its `tokenizer.json`. The certified
subject now explicitly covers that file plus the added tokens its
`tokenizer_config.json` declares beyond it -- the object the pinned
loader (`transformers.AutoTokenizer`) materializes, which is what
loader-based serving stacks such as SGLang compare against. 0.2.7
recorded the boundary honestly but did not settle it: the reference
route executed the artifact file alone, the certified CPU fast path was
built through the loader, and an input holding a configuration-only
added-token literal could receive different ids from the two certified
routes depending on `policy`.

From 0.2.8 every face reads one subject. The reference backend
materializes the loader face when the configuration contributes added
tokens (and executes the verified artifact bytes directly when it does
not, which is every other packaged artifact); the decode oracle is
built from the same document; the added-token router scans the loader
face's literal table, so the routing answer and the execution ledger
agree about the same input; and the session seal guard reads the same
table. The one packaged artifact where this is observable is
`qwen3_5_08b`, whose configuration declares seven literals at ids
248070-248076: those inputs now encode to the declared single ids on
every policy, equal to `AutoTokenizer.encode`, where 0.2.7's
`policy="reference"` spelled them out as plain text.

On an artifact whose configuration names no loader class the pinned
`transformers` can resolve, the loader face is materialized file-only --
taken only when the configuration declares no added token beyond the
artifact file, which is exactly the condition under which the file-only
face and the loader face are provably the same function. When that
premise fails, the loading error propagates instead of a fallback
silently dropping a token.

## The declared subset is verified, fail-closed

A certified artifact whose loader face carries added tokens beyond the
artifact file now declares that subset in the registry record
(`config_added_tokens`: a canonical digest over the id-ascending rows
with their matching-semantics flags, and the count). The loading paths
of both the reference and the fast CPU backend recompute the subset
from the files they are about to execute and refuse a mismatch
(`ARTIFACT_HASH_MISMATCH`, reason `config_added_tokens_mismatch`): a
sidecar that has grown, lost, or changed declared added tokens is not
executed under a certificate that describes a different subject. A
record without the claim asserts the subset is empty, so the other
fourteen packaged BPE artifacts carry a live, machine-checked statement
that their two faces coincide.

## Corpus-equivalence carry-over

Redefining the reference re-poses a question every certification
reading already answered: do the recorded readings still describe the
judge we now compare against? For `qwen3_5_08b` the answer is yes, and
0.2.8 makes the reasoning a machine-verified object rather than a
remark. The two faces differ only on inputs holding one of the seven
literals; a dedicated scan of the full certification corpus
(3,800,016,491 documents, 12.3 trillion characters -- a superset of the
2,293,999,686 documents the record's readings were taken on) found zero
occurrences of all seven, with same-shaped positive controls hitting
thousands of times in the same pass. The scan ships as
`readings/corpus_absence_qwen3_5_08b.json`; the record's readings are
annotated with a `carryover` node naming the mechanism, the divergence
set, and the certificate by path and digest; and the release check
re-verifies the certificate byte for byte. The mechanism is specified
in `docs/contracts/evidence-carryover.md` Section 3, and its generation
channel refuses any record that would change a reading: carry-over
restates which judge the readings hold under, never the numbers.

## Re-importing a bundle answers the same way on both faces

`docs/rust-lifecycle.md` has always said that re-importing an air-gap
bundle is idempotent while the visible tree still authenticates exactly.
The Python `import_bundle` did not follow that rule: it refused every
alias its cache already held, whatever was in it, so running the
documented air-gap recipe twice against one cache produced a refusal
about a bundle that had just verified. From 0.2.8 both faces apply the
Rust condition. The installed tree is re-read against the manifest --
every declared path, byte count and SHA-256, and no undeclared file --
and a tree that still authenticates ends the import successfully with
the directory that is already there, its bytes untouched. A tree that
holds the alias and something else is reported rather than overwritten,
naming the first path that does not match.

That refusal has a code of its own from this release. `ALIAS_CONFLICT`
(class `AliasConflict`) says the tree the cache holds is not this bundle,
which is what the Python facade used to report as `ARTIFACT_NOT_FOUND`
about a bundle that had been found, and what the Rust face used to spread
over `BUNDLE_INVALID`, `ARTIFACT_NOT_FOUND` and `ARTIFACT_HASH_MISMATCH`
depending on which part of the tree disagreed. Both faces now use the one
code, `details.path` names the first file that does not match, and
`details.failure` says how. Decision 0004 item 5 records the reasoning;
code matching on the older answers for a re-import needs a one-line
update, as the 0.2.4 path-policy move did.

## Four diagnostics say one more thing than they did

None of these change a route; each closes a place where a report stopped
one sentence before the reader needed it to.

`toktier doctor` applies the `REFERENCE` policy the way the plan applies
it. Check 1 of the plan refuses every accelerated backend under that
policy, unwaivably, and the report used to read past it and print an
eligible GPU or a certified CPU lane on an installation whose next
request goes straight to the reference engine. Both the installation
answers and the `--family` section now read `false` and `hf` there. A new
`automatic_routing_policy` field names the policy the answers were
computed under, since the same machine answers differently under three of
the five and a report that does not say which one it applied cannot be
compared with another machine's.

`explain()["session_repair"]["guarantee_basis"]` gains `family_ids`
beside the `families` count it has always carried, so the coverage
boundary can be drawn from the object itself. The count is unchanged.

The two refusals that report an unverifiable Fastokens engine now end
with something to do. A shadowing copy on `sys.path` names the relation
to change and stops there, leaving which copy to keep to the reader; a
package no installed distribution records names the published
distribution in the same replacement form the unrecognized-build state
already prints, taken from the registry rather than written out here.

`docs/contracts/facade.md` also records which combinations of the two
family premises the shipped tables can actually produce: every family the
certified repair table reaches is inside the evidence, so
`engine_assurance: family_outside_evidence` is not reachable by opening
the adapter on a shipped build, while four covered families have no
repair entry and are refused by the other half. A registry test pins the
containment.

## The Rust face documents what it had only been doing

`toktier-rust verify-local --json` gains `route_admitted` and
`unserved_paths`, the two facts its report already carried inside the
prose note and the Python face has carried as fields since it grew the
flag, and `docs/rust-api.md` now states the whole `--json` key set rather
than leaving it to be read off a struct. The plan-time `ReasonCode`
variants -- `ReferenceRequested`, `RuntimeBuildUncertified`,
`GpuUnavailable`, `GpuUncertified`, `CpuUncertified`, which
`verify-local` prints by name when no route was admitted -- get a
vocabulary table of their own in `docs/contracts/routing.md` Section 5.6,
with the two that have no Python counterpart said to be so. The Rust
guide also separates the three closure readings that look interchangeable
on an all-green report, says which one gates `certified`, and tells a
Rust reader outright that Fastokens is a Python-side facility carried in
the registry data and reachable from no Rust route. The crate README
declares the `network` feature before the example that needs it, rather
than after.

## Documentation says what was measured

A round of corrections, none of which changes a route.

The F2 path counts in `docs/benchmarks.md` read `1800 / 0` instead of
`4001 / 1999`. The published split could not be re-derived from anything
shipped -- the sample manifest and seed behind it were not archived with
the figure -- and the one replay on record, at 60 of the 200 sessions,
took every turn in every tier lane through the healed path and none
through the window-all path. The table now says which caliber the counts
come from and what the old number was.

The F4 table gains the sentence its two headline cells needed: the
`repair (HF tokenizers win.)` column is not a lane the shipped facade
takes by default. Both repair columns measure the same certified session
path with two window engines, and the default is the other one. The F4
figures themselves are unchanged.

The two direct-JIT protocol facts that had lived only in campaign
scripts are in `docs/rust-lifecycle.md`: `TOKTIER_CAMPAIGN_DEVICE` is a
bare ordinal for the JIT matrix and the routing spelling for the API
matrix, and the final JIT round needs an empty cache directory or its
miss-then-hit judgement fails on a cache state.

The Fastokens co-installation sentence in the three READMEs, the 0.2.7
notes and the packaging README said the two distributions "cannot
coexist". They can: they share one import name, so only one of them owns
the bytes that run, and `doctor` reports the other as co-installed. The
sentence now says that.

`verify-local`'s uncovered notes on the Python face are wrapped and end
in a full stop, which the Rust face has pinned with a test since it grew
them; the same test is now on both sides. The Rust source archive carries
`README.pypi.md`, which `pyproject.toml` names from inside the archive.
Command lines in `docs/` say `python3`, as the READMEs already did.

The Qwen3.8 entry in `docs/support-matrix.md` no longer asserts
unconditionally that both repositories report `R_UNCERTIFIED_ARTIFACT`:
on a machine with no accelerated backend installed the first premise to
fail is `R_BACKEND_UNAVAILABLE`, and the artifact is never reached. The
entry is now qualified the way the Hy4-preview entry beside it is.
`ROADMAP.md` lists Hy4-preview among the families under evaluation.

`data/sibling_aliases.v1.json` says in its own `provenance.selection`
what that block is: a snapshot of the 2026-08-04 admission audit,
deliberately not refreshed against the current tree. Its
`support_matrix_sha256` is the digest `docs/support-matrix.md` carried at
the admission commit, nothing checks it because there is nothing for it
to agree with, and rewriting it to today's digest would make the record
describe an audit that did not happen. The values are unchanged.

## Two tools stop being sharper than they look

`tools/refresh_dependency_judgement.py` updates the lockfile offline and
workspace-scoped by default. Its write mode used to begin with an
unrestricted `cargo update`, which reaches the network and moves every
transitive third-party version published since the lockfile was written;
a 0.2.7 wave met that as twelve unrelated packages lifted, a seven-line
lock diff turned into thirty-seven, and the version-normalised source
identities moving with them. The wide update is still there under
`--allow-network-update`, the docstring says what it does, and the flag
semantics have tests.

The release-artifact gate is tested against a real wheel's `METADATA`.
Its fastokens check previously had a test that read the tool's own source
and the `pyproject` table -- both of which said the right thing while the
matching logic read a correct wheel as one that had lost the pinned
extra, because the builder writes markers with single quotes. The check
is now a function that takes `METADATA` bytes, and the suite feeds it the
text a real `maturin build --release` wrote, plus four edits of that text
for the four ways it should refuse.

## Scope

The Rust serving crate continues to execute the artifact file on every
route: it has no `transformers`, so it cannot materialize the loader
face. `docs/rust-api.md` states the resulting boundary explicitly; it
is observable on the same seven literals of the same one artifact, and
the same absence certificate covers it.

A standing alignment gate, `tools/check_loader_face_alignment.py`,
compares the default and reference policies with `AutoTokenizer.encode`
id for id on the recorded probe set over the real artifact, and pins
the file-only degradation on a frozen loader-less artifact directory
when one is supplied.
