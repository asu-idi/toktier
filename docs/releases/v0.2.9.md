# TokTier 0.2.9

TokTier 0.2.9 aligns the capability identities with the certification
subject. 0.2.8 settled that the reference is the loader face; the two
capability fingerprints were still computed from the artifact file, so
the id and the subject could describe different documents. They no
longer can: both fingerprints are now computed on the loader-face
document. Tokenization is unaffected -- no served id changes on any
input over any packaged artifact -- and the store format, the shipped
fatbin, and the kernel ABI are unchanged.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.2.9. The public API version,
registry schema version, store format version, kernel ABI version, and
certification suite version do not move. Axis 3 stays at 1, but two
JSON shapes do change under it: both sibling-alias schemas gain a fifth
`basis` value, `equivalent_loader_face`, with the counts key that goes
with it, and the support-registry schema drops two optional carry-over
fields no registry ever carried (below). A validator pinned to the
earlier schema file does not recognise the new `basis` value. What the
frozen contract *texts* gain is `Since 0.2.9` clauses, the same form
0.2.8 used.

## Capability ids are computed on the loader face

An artifact's identity key remains its `tokenizer.json`, and the
certified subject remains that file plus the added tokens its
`tokenizer_config.json` declares beyond it. What changes is the document
the two capability fingerprints read. Since 0.2.9 they read the
loader-face document -- the tokenizer JSON the pinned loader serializes
after materializing the verified artifact directory -- so a capability
id names the object the certification readings were taken against.

The preimage encodings and the domain tags are untouched
(`docs/contracts/fingerprint.md` is unchanged word for word): the
pipeline fingerprint still covers the decoder, model, normalizer and
pre-tokenizer sections, and the added-frontend fingerprint still encodes
the seven attributes of every added-token row in order. Only the
document they are read from moved. An artifact whose loader class the
pinned `transformers` cannot resolve degrades to the file-only face, and
the same rule reads that face; there is no special case for it.

## What moved and what did not

Six fingerprint cells of the shipped registry moved. Five of them are
`pipeline_id` cells, where the pinned loader writes the same pipeline in
the current serialisation form that the frozen artifact file predates
(the `merges` array notation, and an explicit default the file leaves
out):

| Family | Pipeline id | Added-frontend id |
|---|---|---|
| `deepseek_v3` | `pipeline.59b9c3a611148dad` to `pipeline.9f6d5117c3680d0e` | unchanged |
| `deepseek_v4_flash` | `pipeline.59b9c3a611148dad` to `pipeline.9f6d5117c3680d0e` (still shared with `deepseek_v3`) | unchanged |
| `llama_3_1_8b` | `pipeline.ff6dd044a1cb9ba5` to `pipeline.a4722932ce483dfa` | unchanged |
| `minimax_m3` | `pipeline.eb3b41ea275dabaa` to `pipeline.70d78ff23f735b25` | unchanged |
| `qwen3_5_08b` | `pipeline.bc687a3b57eba58b` to `pipeline.244da91e0b85bac5` | `added-frontend.2ad65676cbf6bb4d` to `added-frontend.6f80a43b9fe6a15f` |

The ten remaining families keep both ids to the byte. The one
added-frontend id that moved is the one that had to: `qwen3_5_08b`
declares seven added tokens in its configuration sidecar, so its
materialized table holds 33 rows where its artifact file holds 26, and
the fingerprint now covers all 33 -- which is exactly the subject the
registry already declared under `config_added_tokens`.

What did not move: every reading, every evidence id, every carry-over
annotation, and the block shapes (14 pipeline identities, 15
added-frontend identities, 15 artifact records, 15 compositions).
Families that shared a pipeline still share one -- `deepseek_v3` and
`deepseek_v4_flash` hold the same pipeline id by design, which is why
fifteen records carry fourteen pipeline identities. What no id does is
collide: two families sharing one means they share a loader face, never
that two different faces hashed alike. Nothing about how any artifact
tokenizes changed -- these fingerprints are certification identities,
not tokenizer behaviour.

The backend entries did move, for a reason unrelated to this release's
subject. Every release recertifies the roster against its own build
identities, so each entry now records 0.2.9's engine and host digests
instead of 0.2.8's; that rebinding reaches the source-binding digests of
all fifteen artifact rows and both runtime-build rows. It is what the
version bump does, and it is independent of where a capability
fingerprint is computed.

The fingerprint move itself was applied under a gate that required the
regenerated registry to differ, from the registry as it stood
immediately before the migration, in exactly the enumerated cells and in
nothing else, with an independent second computation over all fifteen
families agreeing value for value. That gate scopes the migration step;
the recertification above is a separate, later change. The generator now
also refuses to write the registry when the installed
`transformers`/`tokenizers` pair is not the locked one, since the
loader-face serialization is a function of that pair.

## Nothing at runtime recomputes a capability fingerprint

Worth stating because the change would otherwise look larger than it is:
the capability fingerprints are generation-time values. The Python
runtime consults certification records by `artifact_sha256`; the Rust
runtime does not even deserialize the capability fields, and binds the
registry by whole-file digest. No path in either language recomputes a
capability fingerprint from an artifact, so the values moving is a
statement about what the registry records, not about what any loaded
tokenizer does.

## The Qwen3.8 tokenizer is admitted as the object it is

`Qwen/Qwen3.8-27B` and `Qwen/Qwen3.8-Flash-Next` ship one and the same
tokenizer, which materializes a loader face byte-identical to the
certified `qwen3_5_08b` anchor's: the seven added tokens the anchor
declares in its configuration sidecar are the seven the Qwen3.8 file
writes into `tokenizer.json` directly, field for field. With the
capability ids computed on that shared face, the two files hold the same
ids, and a fifth sibling basis, `equivalent_loader_face`, records the
relationship in the shipped table.

`from_pretrained()` on either repository resolves by content to the
`qwen3_5_08b` anchor, executes its bytes, and is covered by its
certificates. Admission remains by digest, so a later Qwen3.8 revision
with different bytes matches no row and stays on the reference route.
There is no new family id: the registry keeps fifteen artifact rows, and
`load("qwen3_8_27b")` reports `ARTIFACT_NOT_FOUND`, because a family id
names a certified family and these repositories reach one through
content resolution. The sibling table therefore holds 215 rows (214
siblings plus one canonical self-row); `docs/support-matrix.md` carries
the audit accounting.

The audit step behind such a row materializes both loader faces from the
frozen directories and compares the serializations byte for byte before
the row may be written.

## Two unused registry fields are removed

`carryover.from_artifact_sha256` and `carryover.supporting_readings`
were added in 0.2.8 as a reservation: a cross-artifact carry-over would
have needed them to name the artifact whose readings were being carried
and the readings the equivalence rested on. This release makes that
shape unnecessary rather than filling it in. Two artifacts that
materialize the same loader face have an empty divergence set, so they
hold the same capability ids and need no carry-over record at all; two
that do not are handled by the mechanism as it already stands. No
document ever carried either field, and nothing read them, so their
removal is compatible with every registry written to date. If a future
release needs them, they come back as optional members, which is an
additive change.

## An artifact's fetch list names every file the certified face reads

Materializing the loader face reads more than `tokenizer.json`: a
`tokenizer_config.json` for the added tokens the artifact declares
beyond the file, a `config.json` for the loader class, and a
`chat_template.jinja` wherever the pinned loader reads one. The shipped
artifact manifest named only `tokenizer.json` -- one line per family,
fifteen lines in all. A cache built from nothing by `artifacts fetch`
therefore held one file per family, and the added-token check then
looked for the seven tokens whose only source was the sidecar that was
never fetched. For `qwen3_5_08b` a cold cache failed to load, and the
remedy the failure printed was a fetch that produced the same cache
again.

**0.2.8 ships this defect.** It is not a regression introduced here:
the published 0.2.8 wheel behaves the same way, and 0.2.9 is the first
release to carry the fix. A warm cache built before the defect mattered
is why it went unnoticed.

The manifest now pins the input closure of the certified face: 46 file
lines over the same fifteen families, each line with its size and
SHA-256. The groups are measured rather than assumed. The generator
materializes each face from the frozen directory under the pinned
loader, records which files that actually opens, and then proves the
closure by rematerializing from the recorded group alone and requiring
the serialized face to be byte-identical to the first. Fourteen
families now name more than one file. `kimi_k3`, whose certified
artifact is derived on your machine from pinned upstream bytes, stays a
single file, and the generator proves that its conversion output alone
materializes the same face. `toktier inspect <family>` lists the group
a family now needs.

A gate, `tools/check_cold_cache_closure.py`, builds a cache from the
manifest with no network at all, loads through it, and requires each of
the seven declared added tokens to come back as one id -- and requires
a cache built in the 0.2.8 shape to keep failing closed rather than
quietly serving a face that is missing them.

Two smaller things move with this. The remedy printed on a
`config_added_tokens_mismatch` now names a fetch that brings the sidecar
back, so following it terminates. And a directory that holds neither
`config.json` nor `tokenizer_config.json` is materialized file-only and
directly, rather than being handed to `AutoTokenizer`, which resolves a
loader class partly from substrings of the directory path: a cache
under a path containing `opt` or `bert` could otherwise materialize a
different face from the same bytes. The affected families were
recomputed on neutral, `opt`- and `bert`-containing paths and reached
their registry values on all three. No fingerprint value moved.

## A bundle re-import no longer stops at the marker's own leftover

The artifact cache writes its `.toktier-verified.json` marker through a
temporary and renames it into place. A process that stopped in between
left that temporary at the top of the alias, and the next import of the
same bundle answered `ALIAS_CONFLICT` over it -- a file nothing reads,
whose only remedy was to delete it by hand. An import now clears it
first, on both faces, and both faces recognise both temporary shapes
because both write the same marker. Nothing else is removed: a file of
the marker's name deeper in the tree, and every other undeclared file,
are refused exactly as before. `docs/contracts/facade.md` gains
Section 1.1, which states the whole of the Python-face bundle behaviour
in one place rather than leaving it spread across the error rows and the
Rust lifecycle document.

## Three records are now recomputed rather than kept by hand

The crate pins the digest of each embedded data payload in a constant no
generator writes, so a data file that moved without its constant was a
load-time refusal only `cargo test` reported; 0.2.8 shipped one such
mismatch past three green Python gates. `tools/sync_rust_package_data.py`
now reads those constants back out of the source and hashes what each one
pins. The pinned Fastokens recipe's `SHA256SUMS` is recomputed for every
line naming a file kept in the repository, which the publishing workflow
never covered. And the `Config` field table's comparison against a
resolved configuration now declares which rows are allowed to state their
default in prose, so a row rewritten into prose cannot leave the
comparison quietly.

Beside those, the `upstream_build` assurance sentence now ends with the
same reinstall command the advisory prints, and says why the plain
install is not the one to run: the pinned and the upstream distribution
share an import name, so whichever was installed last owns the bytes.

One lockfile entry moved: `chacha20` is at 0.10.2 rather than 0.10.1,
which crates.io has yanked. It reaches the lockfile through an optional
dependency no feature enables, so it compiles into nothing and is not in
the judged compiled closure, which stays at 148 packages with 34 in the
certified core. None of the eight R2 text-semantics packages moved --
those are the ones whose version can change ids by design -- and the
licence list gains no SPDX expression it did not already carry.

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]"` for the Python package with the adapter.

Served ids are unchanged on every input over every packaged artifact,
and `artifact_sha256`, the identity that keys a certification lookup, is
unchanged, so code that consults certification by artifact digest needs
no change. Three things do want a look before you upgrade.

**A capability id you recorded may now read differently.** Five pipeline
ids and one added-frontend id move; the table above maps old to new.
Where such an id can be read is worth stating exactly, since a recorded
one came from somewhere: from the registry file the wheel ships, at
`toktier/routing/tables/support_registry.v1.json`, or from these notes.
Neither runtime surface reports one. They are not in `explain()`, not in
`toktier inspect --json`, not in `toktier doctor --json`, and the Rust
crate neither exposes them nor deserializes the fields at all. So the
registry file is both where a recorded id came from and where to map it.

**An offline deployment wants the widened artifact set staged before it
upgrades.** The fetch list described above grows from fifteen file lines
to 46; `qwen3_8b`, for one, goes from a single file to three. A
connected host repairs itself and needs nothing from you: the first
`load()` after the upgrade fetches and verifies the added files, then
serves. An offline host does not. Its warm cache holds the old file set,
`load()` raises `ARTIFACT_NOT_FOUND` naming what is missing, and the
remedy a connected host would use, `toktier artifacts fetch <family>
--force`, needs the network.

The offline route is an air-gap bundle. On a host that has the new set,
`toktier artifacts export <family> --out <family>.tar`; on the offline
host, `toktier artifacts import <family>.tar` followed by `toktier
artifacts verify <family>`. One step between those is easy to miss: the
offline host's cache already holds that alias, filled with the old and
smaller file set, so an import over it answers `ALIAS_CONFLICT` --
correctly, because the tree it holds is not this bundle. Move the
existing alias directory aside first, or import under a fresh cache root
by pointing `TOKTIER_HOME` at one. With that done the import, its
verification, and the `load()` after them complete with no network at
any point.

**A persistent session store written by 0.2.8 is not opened by 0.2.9.**
This is the rule 0.2.8 stated for its own upgrade, holding again for the
same reason: the source identities a release rebinds are components of
the store's semantic fingerprint, a persistent store carries one
fingerprint for the whole directory, and a store whose fingerprint does
not match is refused at open with `SESSION_STATE_MISMATCH` rather than
re-encoded record by record. The refusal leaves the store's bytes as
they are. The migration is the same as it was: point `store=` at a
directory 0.2.8 never wrote, and replay each session's text into it.
In-process session state is unaffected -- a record written under another
fingerprint misses and is re-encoded.

## Scope

The claims in this release are the claims of the certification registry
it ships: what was judged, on which artifacts, against which oracle
version, with which readings. This release moves how two of the three
identity kinds are computed; it does not widen what has been certified.
