# TokTier 0.3.0

TokTier 0.3.0 lets one long request use more than one core without
leaving the exact-ID contract, and it brings an SGLang adapter into the
package. Four things are new: chunk-parallel encode on the CPU route
(`toktier.chunked`), which runs either as a Python helper over the batch
path or inside a native chunk encoder, and which the Rust `toktier` crate
reaches through `Tokenizer::chunked()`; a patch-only session append; the
SGLang adapter; and a pool of tokenizer worker processes the adapter can
schedule requests on. Every one of them is opt-in. A program that does
not call them behaves as it did under 0.2.9, and no served id changes on
any input over any packaged artifact. The store format, the shipped
fatbin and the kernel ABI are unchanged, and no third-party Rust
dependency changed in this release.

The native chunk encoder is compiled into the corrected CPU engine, so
its source belongs to that engine's certified identity. All three source
identities (fast_cpu, native_host, rust_api) therefore move, in their
exact and their version-normalized forms alike, and this release
recertifies the roster against them. The visible consequence is that a
persistent session store written by 0.2.9 is not opened by 0.3.0; the
Upgrading section says what to do.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.3.0. The public API version,
registry schema version, store format version, kernel ABI version and
certification suite version do not move. `Session.append_patch` and
`SessionPatch` are an addition on the frozen track. The other new Python
surfaces, `toktier.chunked`, the `parallel` keyword of `Tokenizer.encode`
and the two SGLang adapter modules (`toktier.integrations.sglang` and
`toktier.integrations.sglang_sched`), are provisional
(`docs/contracts/facade.md` Section 7), which means they may
still change within 0.x without moving the API version. The append-only
`R_*` reason namespace gains four codes, an addition the contract
allows: three run-time codes for the chunked path and one plan-time
code, `R_LOADER_FACE_MISMATCH` (Installing beside SGLang, below); a
consumer that switches on known codes passes them through. The
package also gains one data table, the chunked admission table described
below, and the repository gains two schemas,
`schemas/chunked_admission.schema.json` for that table and
`schemas/chunked_readings.schema.json` for the chunked-path readings.
Neither is a frozen schema. The support-registry schema gains one
optional artifact-record member, `loader_face_sha256`, additive under
schema version 1 like the identity columns before it, and every shipped
record carries it; the frozen schemas are otherwise unchanged, and the
chunked-path evidence manifest uses the existing evidence-manifest schema
as it stands.

## Chunk-parallel encode on the CPU route (`toktier.chunked`)

A single encode runs on one core, and for an input of several hundred
thousand characters that is tens of milliseconds even on the certified
CPU engine. `toktier.chunked.encode(tokenizer, text)` cuts the input at
certified stable boundaries, encodes the chunks in parallel, and
concatenates the id rows. The result is the serial encoding by
construction. A cut is placed only where the pre-tokenizer of the
certified byte-level BPE families cannot carry a pre-token across it.
That is the synchronizing-transition rule the session-repair witness
already uses (eight class pairs over the frozen O/S/L/N/M table, minus a
line break after punctuation and an apostrophe after letters), together
with a guard that keeps every cut outside any added-token literal of the
loaded artifact. There is no seam to repair and nothing to retry. A
position where no certified cut can be found is not cut. The rule, its
proof obligations and the measurements behind this path are described in
the Delta Tokenizer paper (arXiv:2610.19801), which is the paper to cite
for the chunk-parallel path and the serving adapter.

Two paths make the same plan. The Python path cuts in Python and runs
the chunks as one batch through the tokenizer's own batch path. The
native path makes the same cuts, position for position, inside the
native runtime, encodes the chunks on its own worker pool and
concatenates them before the ids reach Python (next section). By default
`encode` chooses between them on its own: for an admitted tokenizer the
native path runs whenever it can run here, which is when the loaded
runtime carries it and the route carries the corrected CPU engine; the
Python path runs otherwise. `native=False` asks for the Python path.
`native=True` asks for the native path and raises `RuntimeError` when
the runtime does not carry it or the tokenizer is not admitted, naming
which one; on a route without the corrected CPU engine it encodes
serially under `R_CHUNK_ROUTE_NOT_FAST_CPU`. The native path's own
evidence level is shown as a label, not used as a condition
(Certification of the chunked path, below).
`Tokenizer.encode(text, parallel="auto")`, or `parallel=` a chunk count,
is a shortcut to the same call for a stateless core-stream request.

The Python path is a helper over the public batch path. The chunks go
through the same plan, the same per-input guards and the same fallback
ledger as any document, so a chunk that trips a guard is routed to the
reference on its own, and that cost stays with one chunk instead of the
whole document. Its parallelism is the native batch worker pool, sized
by `RAYON_NUM_THREADS` at first use, with at most one worker per 64 KiB
of payload.

Admission and fallbacks. A tokenizer may be chunked when three things
hold. Its family and artifact digest have an entry in the certified
repair roster, the eleven byte-level BPE artifacts the sync profile was
certified on. Its loader face carries no normalizer, the empty
normalizer sequence, or NFC with every added token matched on the input
text, and none of its added tokens sets `lstrip`, `rstrip` or
`single_word`: the reference matches such a literal together with its
neighbourhood, which the cut rule does not reason about, so such a face
is refused as `added_token_strip_or_single_word` (no packaged artifact
sets these flags). And the chunked admission table has a certified row
for its artifact, one that holds both levels of chunked-path evidence
(Certification of the chunked path, below), for the installed oracle and
the loaded face. Any other tokenizer is encoded serially under
`R_CHUNK_FAMILY_UNSUPPORTED`, and `explain()["chunked"]["refusal"]`
names the reason. For the table step that is
`artifact_without_chunked_evidence` when the artifact has no row,
`chunked_evidence_incomplete:<status>` when its row holds one level of
evidence only, `oracle_differs_from_chunked_evidence:<version>` when the
facade's probe finds the installed oracle outside the set the artifact's
record was judged with (the plan then reports `R_ORACLE_MISMATCH`), and
`loader_face_differs_from_chunked_evidence:<digest>` when the loaded face
is not the one the row's evidence was taken on. A
document with no certified cut is encoded serially under
`R_CHUNK_NO_CUT`. The native path adds `R_CHUNK_ROUTE_NOT_FAST_CPU` for
an input whose route does not start at the corrected CPU engine. All three are run-time reason codes
(`docs/contracts/routing.md` Section 5.2). They are counted in the
`chunked` block of `explain()` and not in the routing ledger's top-level
`fallback_counts`, because the serial route is the same certified backend
the chunks would have used.

Normalizing families. The cut rule speaks about the text the
pre-tokenizer sees, which for an NFC family (qwen3_8b, qwen3_5_08b and
minimax_m3 on the roster) is the normalized text. A cut certified on
input characters alone can change ids there. U+0958 before a slash is
the example: as written it is a letter followed by punctuation, and once
normalized it is a mark that shares the slash's pre-token. For such a
family a candidate cut is accepted only when it is also a certified cut
of the normalized text. That means a stable split point on both sides (a
character NFC cannot change from either neighbor, decided with the
artifact's own normalizer), no added-token literal in the anchored
window, the normalizer mapping the window to the concatenation of its
halves, and the rule holding on the two normalized characters at the
cut. Three stable characters around a cut need no window at all, so
prose, code and CJK text keep their cuts. `docs/serving.md` Section 3
states the condition, and `norm_rejects` counts the candidates it
declined. The shipped test judges this on a generated corpus of
decomposing characters, combining sequences, jamo, kana voicing marks
and literals beside marks. The battery for this release ran that
corpus over all eleven roster families, 460,000 strings in all (100,000
on each of the three NFC families), and found no id difference against
the from-scratch reference on either chunked path (Certification of the
chunked path, below). When the rule was designed, a variant that looked
at input characters only differed on about two percent of the qwen3_8b
strings. The quick part of the cut search is bounded by `scan_budget`,
and `min_chunk` binds the last chunk as well as the others.

The chunk table. With `k=None` the chunk count follows a staircase: one
chunk below 256 K characters, 4 up to 1 M, 16 up to 4 M and 32 above,
capped by one chunk per 64 KiB. It is the argmin of the measured
batch-path latency on three certified families (qwen3_8b, llama_3_1_8b,
gpt_oss_120b) over four corpus types (prose, code, chat transcripts and a
multilingual mix) at 64 K to 4 M characters on one 16-core NUMA node.
Representative readings of the Python path at 1 M characters of English
prose with 16 workers are 26.5 ms serial against 8.6 ms chunked on
qwen3_8b (3.1x), and 9.8 ms against 6.9 ms on llama_3_1_8b (1.4x), where
the Python boundary, each chunk's ids handed over and concatenated, is
most of what remains. Every chunked encode in that measurement (33,518
of them, up to 10 M characters) returned the ids of the from-scratch
reference. The shipped test `tests/test_chunked.py` repeats the identity
check on every admitted family whose artifact it finds locally, over
three corpus types and three lengths, against the oracle package.

Guidance and limits are in `docs/serving.md` Section 3. Two of them bear
repeating. Below 256 K characters a single encode is already as fast.
And a process started with `RAYON_NUM_THREADS=1` gets the chunks one
after another, on either path: exact, not faster.

## Native chunk encoder

The native chunk encoder is the same plan implemented inside the native
runtime, with the literal guard and the normalization-stability
condition included. It plans the cuts in Rust, encodes the chunks on a
persistent pool of corrected-Gigatoken workers and concatenates the ids
before they cross into Python, so the per-chunk Python boundary that
limits the Python path goes away. Each chunk passes the engine's own
guarded full-encode gate, so a chunk that holds an added-token literal or
trips a guard is encoded by the reference on its own, as on the Python
path.

The pool is separate from the batch path's workers. A worker is checked
out for one chunk and returned, so concurrent callers do not share a
prefix of the pool, and the pool size does not depend on the chunk
count. It is forked on first use. `toktier.chunked.warm(tokenizer,
workers=None, text=None)` forks it ahead of the first request, to the
Rayon thread count when `workers` is omitted, and with a sample `text` it
also runs each new worker once so its caches are warm. The chunks run on
the process's Rayon threads, so with `RAYON_NUM_THREADS=1` they run one
after another and stay exact. That is the case inside the SGLang pool's
worker processes, which start with one thread each by default.

Three places report what happened. `ChunkedEncoding.native_facts` carries
the per-call facts of the native path: how many rows each implementation
produced (the corrected engine, or the reference for an added token or a
guard), the plan, encode and concatenation times, and the workers forked
during the call. It is `None` on the Python path. `explain()["chunked"]`
counts native calls in `native_calls` and marks the last call with
`last["native"]`. `toktier.chunked.admission(tokenizer)` reports the
decision for both paths in one dict: `admitted` and `refusal`; the
`family`, `normalizer` and `literals` (the added-token count the guard
holds) behind it; the admission-table row (`evidence_id`,
`evidence_status`, `evidence_paths`, `loader_face_sha256`), the label of
what that row records for the native path (`native_evidence_label`) and
`admission_gate`; whether the native encoder can run for the tokenizer
(`native_available`: the loaded runtime carries it and the route carries
the corrected CPU engine) and whether `native=None` would choose it
(`native_by_default`: the tokenizer is admitted and `native_available`
is true); and
under `native` the native planner's own facts, or `None` with
`native_unavailable_reason` saying why.

Chunking is a CPU-route feature. When the native path is selected for an
input whose route does not start at the corrected CPU engine, the input
is encoded serially through the normal route and the result says
`R_CHUNK_ROUTE_NOT_FAST_CPU`. That is a plan with a GPU at its head, for
an input at or above the GPU crossover, and a route without the
corrected CPU engine when `native=True` asks for the native path there;
`native=None` takes the Python path on such a route.

## Certification of the chunked path

The chunked path returns the serial encoding by construction. This
release also binds evidence to it, artifact by artifact, and three kinds
of evidence are worth keeping apart because they say different things.

- The engine differential. The corrected CPU engine's whole-document
  campaign, 41,800,181,401 checks over 11 artifacts and 3,800,016,491
  documents with zero divergence, is evidence about the engine that
  encodes each chunk. It never cut a document, so it says nothing about
  the cuts.
- The adversarial battery. Strings built to stress the cut rule
  (decomposing characters, combining sequences, jamo, kana voicing
  marks, literals beside marks) are encoded on both chunked paths,
  serially and by the reference, and compared id for id. The battery
  for this release, run on 2026-10-14 with
  `tools/run_chunked_cut_campaign.py adversarial`, covered all eleven
  roster artifacts: 100,000 strings each for qwen3_8b, qwen3_5_08b and
  minimax_m3 and 20,000 for each of the other eight, 460,000 in all, on
  both the Python and the native path. None of the four comparisons
  (each chunked path against the reference, the two chunked paths
  against each other, the serial encode against the reference) found a
  difference, and the native plan equaled the Python plan on every
  string. Four strings found no admissible cut and were encoded serially,
  on both paths alike. The four comparisons are recorded per artifact in
  `readings/chunked_cuts_campaign.json`; the plan comparison is a reading
  of the same run that the shipped file does not carry.
- The corpus cut comparison. Web documents of 512 to 400,000 characters
  are encoded with forced cuts on both chunked paths and compared id for
  id with the serial encode and the reference.

Only the second and the third are evidence about the chunked path.

Which artifacts may be chunked is read from a table that ships with the
package, `toktier/routing/tables/chunked_admission.v1.json`. It is
generated from the evidence records
(`evidence/evidence_manifest_chunked_cuts.json` and
`readings/chunked_cuts_campaign.json`), and a standing check keeps it
equal to them. Each row names the artifact, its normalizer shape, the
evidence behind it, its status and the paths that evidence covers
(`python`, `native`). A row is `certified` only when it holds both
levels of chunked-path evidence, the adversarial battery and the corpus
cut comparison; a row with one level reads `adversarial_only` or
`corpus_only`, and its artifact is refused at run time like one without
a row. Rows are bound to the code they were measured on. The Python
path is bound to `chunked_identity`, a digest of `toktier/chunked.py`
and the two repair tables it reads. The native path is bound to the
corrected CPU engine's version-normalized source digest. A change to
either code takes its rows out of the evidence until it is measured
again.

## Patch-only session append (`Session.append_patch`)

`Session.append(text)` returns a `SessionUpdate` that carries the whole
stream. A serving process usually holds that stream itself and only
needs the splice. `Session.append_patch(text)` returns a `SessionPatch`
with `replace_from` and `replacement_ids` and nothing else, from the same
append and with the same values `append` would report. `append` and
`SessionUpdate` are unchanged (`docs/contracts/facade.md` Section 7).

What it saves today is modest. On the native request path the engine
hands over the whole stream as one Python list on every append (7.2 ms
of the 7.6 ms an append over 220 K tokens costs), so `append_patch`
removes the update object and its copies and is not yet proportional to
the appended text. The Python surface is the one that will not change
when a patch-shaped native return lands (registered below).

## Stateless calls: say so

`encode(text)` with `lookup` omitted asks the content index to digest
the input so a later request can find it. On a request that is never
extended that work is pure overhead, 55-79 % of the encode itself at
1 M characters, and a serving path that knows a request is single-shot
should pass `lookup="off"`. The default is not changing, because the
facade cannot tell a single-shot request from the first turn of a
conversation. The serving layer can, and `docs/serving.md` Section 1
lays out the four request shapes and the call for each. The SGLang
adapter's stateless mode already does this.

## SGLang adapter (`toktier.integrations.sglang`)

The adapter wraps the Hugging Face tokenizer SGLang loads. Its encode
calls run on toktier's certified CPU route, and everything else
(`decode`, chat templates, special-token attributes, vocabulary) is
delegated to the wrapped object. There are two ways to install it. A
small patch adds `--tokenizer-backend toktier`; it comes in two files,
`patches/sglang-0.5.19-toktier-backend.patch` for SGLang 0.5.19 and
`patches/sglang-0.5.21-toktier-backend.patch` for 0.5.20 and 0.5.21.
Without patching anything,
`attach_to_tokenizer_manager(TokenizerManager)` installs the same wrapper
from a `sitecustomize`. A third way needs no adapter at all: compute the
ids with toktier and send `input_ids`. `docs/integration/sglang.md`
describes all three.

Session state can be keyed by the request's `session_id` (else its
`cache_salt`), left to content lookup (`auto`, the default, which needs
no protocol change), or turned off (`off`, stateless encode). Long
stateless requests can be handed to `toktier.chunked.encode` above a
threshold (`TOKTIER_SGLANG_CHUNKED_MIN_CHARS`, off by default). A shadow
mode re-encodes requests with the wrapped tokenizer and compares id by
id.

The wrapper accelerates nothing until it has established that the
object it was handed is the tokenizer toktier loaded. A family or
repository name alone cannot establish this. It serializes the supplied
object's fast backend, tokens added after loading included, and compares
it with toktier's loader face on the sections that decide the core id
stream: model, normalizer, pre-tokenizer, post-processor, added tokens,
truncation and padding. The supplied object's `split_special_tokens`
setting, which the serialization does not carry, must be off. The
`trim_offsets` flag of a byte-level pre-tokenizer or post-processor is
left out on both sides, because it decides character offsets and not ids
(`transformers` 5.12.1 sets it on the live objects of the two Qwen
families, qwen3_8b and qwen3_5_08b, where their artifact files do not).
The check is repeated after construction: before every accelerated
encode a cheap fingerprint of the supplied object's mutable surface is
compared with the one taken at admission, and a difference that turns
out to matter switches the wrapper to delegation for good. Whenever the
two sides are not equivalent, every call goes to the supplied tokenizer
and `stats()["identity"]` records why. The check is always on:
`TOKTIER_SGLANG_IDENTITY` accepts only `require`, and any other value is
refused.

The adapter was checked against SGLang 0.5.19, 0.5.20 and 0.5.21 on
2026-10-13, on the CPU side: the `TokenizerManager` shape, the attach to
the real class, the backend patch applied to each release's published
wheel, and token ids on a real Qwen3-8B tokenizer through both forms,
the worker pool included. The two methods it wraps have the same
signatures in all three. On another version, `attach_to_tokenizer_manager`
first checks that `_tokenize_one_request` and `_tokenize_texts` have the
shape it wraps; if they do not, it leaves SGLang unchanged, returns
`False`, and records `sglang_shape_unverified` with the reason and the
SGLang version. The backend patch is written per release line, as named
above. Both forms wrap the tokenizer of SGLang's `TokenizerManager` and
no other: the backend patch does it in `init_tokenizer_and_processor`
and leaves `get_tokenizer` unchanged, so the scheduler, TP worker and
detokenizer processes keep the plain Hugging Face tokenizer they load
(`docs/integration/sglang.md`).

## Scheduled encodes behind the SGLang adapter (`toktier.integrations.sglang_sched`)

SGLang encodes every request on the thread of its event loop, so the
tokenizer is a serial stage of the request path and a long request
occupies one core however many the host has. The certified CPU engine is
serialized inside one process, so parallel encodes need one process
each. The adapter can now run a pool of worker processes, each with its
own loaded tokenizer, and a policy over it. Keyed requests are served on
the session path by a home worker chosen from the key, which keeps the
store's single-writer rule. Stateless ones come from a shared
shortest-first queue with aging. Long stateless ones become certified
chunk tasks that any worker may take, using the cuts of
`toktier.chunked`, so the concatenation is the serial encoding.
`attach_to_tokenizer_manager` also patches `_tokenize_texts`, and the
backend patch adds the same hook
(`toktier.integrations.sglang.tokenize_texts_with_pool`). With the pool
on, a request is then awaited rather than encoded on the loop's thread,
and several requests are in flight at once; without a pool the original
method runs.

The pool is off by default (`TOKTIER_SGLANG_SCHED_WORKERS=0`). A good
starting point is one worker per physical core you can reserve for
tokenization; our own SGLang measurements used four on a 16-core NUMA
node. A request the pool cannot answer is encoded in-process on its
usual route and counted, so ids never depend on the pool. Scheduler
settings are read once through the adapter's own configuration. The
three on/off settings, `TOKTIER_SGLANG_PER_PROCESS_STORE`,
`TOKTIER_SGLANG_SCHED_AFFINITY` and `TOKTIER_SGLANG_SCHED_CALIBRATE`,
accept `1`, `true` or `yes` and `0`, `false` or `no`, in any letter
case, and any other value is refused rather than read as on.
`TOKTIER_SGLANG_SCHED_WORKERS` takes a non-negative integer, and a
numeric setting that does not parse is refused with a message that
starts with the variable's name, as for the on/off settings. The
loader of the pool's workers is a construction argument and no longer
has an environment variable. `docs/integration/sglang.md` describes the
settings and the cost, which is that the text and the ids cross a
process boundary on every request. With either form the pool runs in the
`TokenizerManager` process only, one pool per tokenizer process (with
`--tokenizer-worker-num N`, one in each of the N workers).

## Installing beside SGLang

toktier's package metadata admits `tokenizers>=0.22.2,<0.24` and
`transformers>=4.57.6,<6` in place of the two exact pins earlier releases
carried, so it installs beside SGLang with its dependencies resolved the
ordinary way:

```
pip install "sglang==<version>"
pip install toktier==0.3.0
pip check
```

SGLang 0.5.19, 0.5.20 and 0.5.21 pin `transformers==5.12.1`,
`tokenizers==0.22.2` and `torch==2.13.0`, and SGLang's main branch has
moved to `transformers==5.19.0` and `tokenizers==0.23.2`; both pairs are
inside the ranges. Older toktier releases pinned `transformers==4.57.6`
and had to be installed with `--no-deps` beside SGLang; that is no longer
needed. The range is what installs, not what is certified. The reference
engine compiled into toktier is the `tokenizers` crate at the version
`Cargo.lock` resolves, 0.22.2 in every build we ship (a Rust host that
resolves another runs labelled `uncertified_reference` under the crate's
own certified reference versions, next section), and the exact Python `tokenizers`
releases the certificates speak for are the certified reference versions
the shipped registry's oracle record lists; a later release joins that list only on parity readings taken under
it (`docs/contracts/registry.md` Section 2, `tools/update_oracle_certified_versions.py`).
This release ships `tokenizers` 0.22.2, 0.23.2 and 0.23.3 as certified
reference versions, which covers SGLang 0.5.19 to 0.5.21 (0.22.2) and
SGLang's main branch (0.23.2). The two 0.23 releases were certified on
fast CPU, sm_120 and sm_89 parity readings and on the chunk-parallel
adversarial battery, each taken with the release installed beside
`transformers` 5.19.0, none with a mismatch. With toktier 0.3.0, `pip
check` reported "No broken requirements found." on 2026-10-14 in a new
environment holding SGLang 0.5.21's pins and in one holding SGLang main's
pins (`docs/integration/sglang.md` gives these readings and the 3.10 one).
Routing does not consult the `transformers` version, so beside a certified
`tokenizers` release the certified routes are the same as in a
toktier-only environment. One artifact is the
exception to "nothing else changes": `qwen3_5_08b` declares added tokens
in its configuration, so its loader face is materialized by the
installed `transformers`, and under 5.12.1 that face differs from the
one its readings were taken with. Beside `transformers` 5.x its ids
follow the installed Hugging Face object, the one SGLang itself uses,
and they are outside what the certification covers
(`docs/integration/sglang.md` gives the reading). toktier now says so
at load: every certification record carries the digest of the loader
face its readings were taken on (`loader_face_sha256`,
`docs/contracts/registry.md` Section 1, written by
`tools/update_loader_face_registry.py` under the pinned loader), and a
face the installed loader materializes differently closes the
accelerated routes with `R_LOADER_FACE_MISMATCH`
(`docs/contracts/routing.md` Section 5.1). Beside `transformers` 5.12.1
`explain()` for `qwen3_5_08b` reports `certification.state`
`reference_only`, `effective_verdict` `unverified` and that reason with
both digests; the other ten roster families materialize the same face
under both versions and report as they do in a toktier-only
environment. A record that matches the materialized face plans exactly
as a record without the digest did.
`toktier doctor` reads differently there, and
`docs/integration/sglang.md` explains how to read it. The combinations we
have checked, and the risks, are listed on the same page.

## Rust crate: caret edges, certified reference versions, admission on other compilers, chunk-parallel encode

Three things about the `toktier` crate's certificate changed shape in this
release, all in the direction of letting a Rust host take the crate on its
own terms and still reach the fast CPU route.

- **Dependency edges.** Every third-party dependency of the workspace is
  taken on a caret edge; earlier releases pinned all of them exactly (`=`),
  which moved a host's lockfile onto our versions and made sharing a
  `tokenizers` build with the host impossible. `Cargo.lock` records the
  versions every judged build resolved (unchanged by this release), and
  the shipped judged-closure record says what each package can do to the
  certificate: the six workspace crates and the reference libraries are the
  certified core; the implementation libraries (`serde`, `serde_json`,
  `sonic-rs`, `rayon`, `aho-corasick`, `memchr`, `rustc-hash`, `itertools`,
  `base64`, `sha2`, `blake2b_simd`, `eyre`, `winnow`, `libc`, `flate2`,
  `rusqlite`) are compared and reported in `dependency_advisory` and no
  longer withhold the route; the periphery is reported as before. A
  generation gate now refuses an exact edge of ours on a third-party crate.
- **Certified reference versions on the Rust side.** The embedded reference
  engine (`tokenizers`), the Unicode property data (`icu_properties`,
  `icu_properties_data`), the normalization tables
  (`unicode-normalization-alignments`), the SentencePiece normalizer
  (`spm_precompiled`) and `unicode_categories` are compared by crate version
  against a per-package list of certified reference versions; in this
  release each list holds the judged version alone. A build that resolves
  another version, or whose tables read another Unicode version, runs the
  accelerated engines labelled `supported_untested` rather than
  `certified`, and `Runtime::doctor()` reports
  `reference_certification_reason: "uncertified_reference"` beside each
  package's resolved, judged and certified versions (`reference_versions`),
  with the alignment command in `dependency_advisory`; nothing is refused
  and nothing is moved to the reference engine. The case this is written
  for is `icu_properties` 2.3.0, which a dependency on `icu_normalizer
  ~2.3` elsewhere in a consumer's graph forces and `cargo update --precise`
  cannot move: it carries Unicode 17.0 property data where the judged 2.0.2
  carries 16.0, and the exhaustive class-parity reading between that data
  and the reference engine's Oniguruma tables (`tools/check_class_parity.py`)
  was taken on 16.0. The label says so; the engines run (`docs/rust-api.md`,
  "Unicode tables"). The same words name the same mechanism in the Python
  facade's `doctor`.
- **`core_closure` names this project's own crates alone.** What decides
  admission by closure is that `toktier` and its sibling crates are the
  judged copies. A crate an optional feature brings in --
  `toktier-store-sqlite` under `sqlite` -- carries an `optional` mark in
  the judged-closure record and is compared only when the feature is on,
  so `default-features = false, features = ["serving"]` is no longer a
  `mismatched` core for want of a package it does not compile; the advisory
  names such packages as absent. The reference libraries moved to the
  label above; the implementation libraries and the periphery were already
  advisories. A build on which no accelerated engine is admitted -- today,
  one whose source identity the shipped register does not carry -- repairs
  nothing incrementally: with no fast CPU engine there is no sealed prefix,
  the whole transcript is re-encoded on the reference engine each turn, and
  the session path is exact but not faster than encoding from scratch. The
  startup facts (`toktier-rust doctor`) say which premise is missing.
- **Admission without the exact compiler.** The fast CPU engine is admitted
  by its source identity. A build from the judged sources on a rustc or
  feature recipe no campaign used -- rustc 1.89 to 1.92, or
  `default-features = false, features = ["serving"]` on a CPU-only host --
  is admitted under every policy but `Policy::Reference` and labelled
  `Certification::Supported` (`supported_untested`), or `LocallyVerified`
  once `toktier-rust verify-local --engine cpu` has compared it with this
  binary's reference engine; the reference route is only for a build whose
  sources do not verify. `runtime_build.certified` keeps its meaning (the
  judged recipe: judged sources, judged rustc, judged flags); two new facts,
  `source_identity_judged` and `recipe_judged`, say which half holds, and
  `toolchain_divergence` names both compilers when they differ. The GPU
  route keeps the judged-recipe requirement. Through 0.2.x the fast CPU
  route was admitted only on a build whose rustc was exactly the judged one.
- **The same rule on the Python side.** The planner's engine-binding check
  (`R_ENGINE_BINDING_MISMATCH`) compares the extension's source identity,
  engine version, delivery, module and repair configuration; the build
  flags and the Rust toolchain it reports are recorded and reported, never
  a reason to fall back. A `toktier._native` built from the bound sources
  with another rustc -- a source install, say -- runs the fast CPU engine
  under every policy but `REFERENCE`, and `explain()["supported_untested"]`
  carries the axis with `cause: recipe_unjudged`; `toktier doctor` reports
  `gigatoken_recipe_judged` and, per family, `fast_cpu_recipe_divergences`.
  Earlier releases closed the route on any of those axes.
- **MSRV.** `rust-version` is 1.89, measured on this release with rustc
  1.89.0 and 1.92.0 on the default feature set, on
  `--no-default-features --features serving` and on the crate's test suites,
  and checked in CI; `rust-toolchain.toml` still names 1.93.1, the toolchain
  the judged builds are made with. Earlier releases declared 1.93.1, which a
  host on rustc 1.92 could not compile at all.
- **`Runtime::family_for_sha256(sha256_hex)`** answers which shipped
  canonical family a `tokenizer.json` digest belongs to, without touching a
  file, so a host that already holds the file can ask before calling
  `load_local`; `None` means the file is outside the shipped families.
- **Chunk-parallel encode on the crate.** `Tokenizer::chunked()` is the
  Rust face of `toktier.chunked`, over the same native chunk encoder:
  `admission()`, `plan()`, `encode()`, `warm()` and `stats()` under
  `toktier::chunked`, with `ChunkOptions` carrying the Python call's `k`,
  `min_chunk` and `scan_budget`. The ids equal the serial encode of the
  route. Admission is the roster, the encoder's structural rule and the
  chunked admission table, which the crate now ships beside the registry
  and reads by the row's status, the one the Python face admits by, so
  the two faces admit the same artifacts and refuse the rest with the
  same strings; the three `R_CHUNK_*` codes are named `ReasonCode`
  variants. The evidence the row records for the native chunk encoder is
  a label, not a condition: `evidence_label` on the admission, the
  counters and every result that was cut. Under the default policy the
  four roster artifacts with certified rows (qwen3_8b, llama_3_1_8b,
  deepseek_v3, gpt_oss_120b) are admitted and labelled
  `native_evidence:adversarial_only`, since the native path holds the
  adversarial battery and not yet the corpus cut comparison, and the other
  seven answer `chunked_evidence_incomplete:adversarial_only`; a route
  without the corrected CPU engine encodes serially under
  `ChunkRouteNotFastCpu`. A table that records the corpus level for the
  native path removes the label without a code change, and
  `Policy::Experimental` lifts the table step. The
  chunks run on the process-wide Rayon pool; a host with a pool of its own
  runs the call inside that pool's `install`. `docs/rust-api.md` has the
  surface, and `cargo run --release -p toktier --example chunked` runs it.
- **`Policy::Experimental` and the engine binding.** The engine's source
  binding in the registry is no longer a condition of the fast CPU route's
  admission under `Policy::Experimental`, the way the Python facade's
  experimental policy waives `R_ENGINE_BINDING_MISMATCH`: a build whose
  engine sources the registry does not record can run the engine, labelled
  experimental. The artifact's row and its status are not waived, and no
  other policy changes.

`docs/rust-api.md` has the tier rules, the label table and what a fresh
resolution reads; `docs/rust-lifecycle.md` the distribution contract.

## Registered for a later release

- Certified reference versions beyond the judged ones on the Rust side -- a
  `tokenizers` crate release other than 0.22.2 as the embedded reference,
  or the Unicode 17.0 property data -- each of which needs the cargo gates
  and the Rust API matrix taken with a lockfile that resolves it; and a
  wider `tokenizers` edge than `^0.22.2` once that evidence exists for a
  0.23.x release, so that a host on `tokenizers` 0.23.x can share one build
  of it with this crate.
- A patch-shaped native return for session appends, behind the
  `append_patch` surface shipped here.
- A pool entry point outside SGLang. In this release the worker pool is
  reachable only through the SGLang adapter.
- Corpus-level chunked-path evidence for the native path, which
  `native=True` on the Python facade waits for and which removes the
  `native_evidence:adversarial_only` label on the Rust crate's chunked
  results.
- Recording the loader faces under a second `transformers` release, so
  that an artifact whose face the installed loader materializes
  (`qwen3_5_08b`) can read as certified beside a loader other than
  4.57.6. The loader is admitted as a range in this release; the recorded
  faces are still those of one release.
- A second cut mode at the edges of special-token strings, for
  tokenizers whose special tokens neither strip surrounding whitespace
  nor depend on word boundaries.
- A bytes entry point for encode, with UTF-8 validation outside the GIL.
- A Unicode quick-check in front of the corrected CPU engine's
  normalization guard, so non-ASCII text that is already in NFC skips
  the full normalization.
- Per-chunk guard judgement inside a plain `encode`, so an unchunked
  request pays reference speed only for the passage that tripped a
  guard; and, for the batch path's own workers, forking and warming at
  construction, checkout of disjoint idle workers for concurrent
  callers, and the 64 KiB-per-worker floor as a parameter. The native
  chunk encoder's pool already works this way.
- Certification of the DeepSeek-V4.1-Flash tokenizer, which
  `docs/support-matrix.md` records as examined and not certified.

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]"` for the Python package with the pinned Fastokens
adapter. Beside SGLang, the ordinary install applies (Installing beside
SGLang, above); the `--no-deps` form earlier releases needed is not.

Served ids are unchanged on every input over every packaged artifact,
and every new surface is opt-in, so code that does not call
`toktier.chunked`, `Session.append_patch`, `Tokenizer.encode(...,
parallel=...)` or the SGLang adapter needs no change. One thing does
want a look before you upgrade.

**A persistent session store written by 0.2.9 is not opened by 0.3.0.**
This is the rule 0.2.8 and 0.2.9 stated for their own upgrades, holding
again for the same reason. The source identities a release rebinds are
components of a store's semantic fingerprint, and the fast CPU identity
moves in this release, the native chunk encoder having joined that
engine's source. A persistent store carries one fingerprint for the
whole directory, and a store whose fingerprint does not match is refused
at open with `SESSION_STATE_MISMATCH` rather than re-encoded record by
record. The refusal names both fingerprints in its `details`
(`expected_fingerprint` and `stored_fingerprint`, which a store opened
through the native extension left out through 0.2.9) and leaves the
store's bytes as they are. It also works in the other direction, so
0.2.9 refuses a store that 0.3.0 wrote. The migration is the same as
before. Point `store=` at a directory 0.2.9 never wrote, and replay
each session's text into it. In-process session state is unaffected.

Smaller things a consumer may notice. `explain()` carries a `chunked`
block once `toktier.chunked` has served the tokenizer, and the routing
contract gains three `R_CHUNK_*` codes and the plan-time
`R_LOADER_FACE_MISMATCH`; both are additions the contracts already
require readers to tolerate. On the Rust face the three chunked codes
arrive as named `ReasonCode` variants rather than as `Other`. `explain()["probe"]` also names the digest
of the loader face the facade materialized (`loader_face_sha256`).
`toktier doctor` no longer names the GPU as the effective backend while
its own plan reasons refuse the GPU: `automatic_gpu_eligible` now also
requires the driver floor and, for a prebuilt certificate, the Rust
request host binding to verify, read from the same list the plan refuses
from. The package metadata admits `tokenizers>=0.22.2,<0.24` and
`transformers>=4.57.6,<6` in place of two exact pins, and `doctor` gains
two keys that say what that leaves open: `certified_reference_versions`,
the exact `tokenizers` releases the shipped registry certifies, and
`reference_certification_reason`, `null` when the installed release is one
of them and `uncertified_reference` when it is not.
`certified_cpu_profile_ready` requires membership in that set and no
longer requires one `transformers` release; the loader is judged per
artifact by the recorded loader-face digest at load. These are the only
`doctor` keys added, and no key changes meaning otherwise.

The prebuilt GPU delivery is certified on `sm_80`, `sm_89` and `sm_120`.
`sm_90` is not certified in this release; the 0.2.9 reading is not carried
over because the host build changed. The fatbin still carries the `sm_90`
image, and the registry lists it with the other experimental architectures.

## Scope

The claims in this release are the claims of the certification registry
and the chunked admission table it ships: what was judged, on which
artifacts, against which oracle version, with which readings. The
chunked path is claimed exact for the artifacts and paths its table
lists, and the rest of the roster is served serially. Nothing here widens
what the whole-document routes were certified for.
