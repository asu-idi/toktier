# TokTier 0.3.0

TokTier 0.3.0 lets one long request use more than one core without
leaving the exact-ID contract, and it brings an SGLang adapter into the
package. Four things are new: chunk-parallel encode on the CPU route
(`toktier.chunked`), which runs either as a Python helper over the batch
path or inside a native chunk encoder; a patch-only session append; the
SGLang adapter; and a pool of tokenizer worker processes the adapter can
schedule requests on. Every one of them is opt-in. A program that does
not call them behaves as it did under 0.2.9, and no served id changes on
any input over any packaged artifact. The store format, the shipped
fatbin and the kernel ABI are unchanged.

The native chunk encoder is compiled into the corrected CPU engine, so
its source belongs to that engine's certified identity. All three source
identities (fast_cpu, native_host, rust_api) therefore move, in their
exact and their version-normalized forms alike, and this release
recertifies the roster against them. The visible consequence is that a
persistent session store written by 0.2.9 is not opened by 0.3.0; the
Upgrading section says what to do.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.3.0. The public API version,
registry schema version, store format version, kernel ABI version and
certification suite version do not move. The new Python surfaces are
provisional (`docs/contracts/facade.md` Section 7), which means they may
still change within 0.x without moving the API version. The append-only
`R_*` reason namespace gains three codes, an addition the contract
allows; a consumer that switches on known codes passes them through. The
package also gains one data table, the chunked admission table described
below, and the repository gains two schemas,
`schemas/chunked_admission.schema.json` for that table and
`schemas/chunked_readings.schema.json` for the chunked-path readings.
Neither is a frozen schema. The frozen schemas are unchanged, and the
chunked-path evidence manifest uses the existing evidence-manifest schema
as it stands.

## Chunk-parallel encode on the CPU route (`toktier.chunked`)

A single encode runs on one core, and for an input of several hundred
thousand characters that is tens of milliseconds even on the certified
CPU engine. `toktier.chunked.encode(tokenizer, text)` cuts the input at
certified stable boundaries, encodes the chunks in parallel, and
concatenates the id rows. The result is the serial encoding by
construction. A cut is placed only where the pre-tokenizer of the
certified byte-level BPE families cannot carry a pre-token across it.
That is the synchronizing-transition rule the session-repair witness
already uses (eight class pairs over the frozen O/S/L/N/M table, minus a
line break after punctuation and an apostrophe after letters), together
with a guard that keeps every cut outside any added-token literal of the
loaded artifact. There is no seam to repair and nothing to retry. A
position where no certified cut can be found is not cut.

Two paths make the same plan. The Python path cuts in Python and runs
the chunks as one batch through the tokenizer's own batch path. The
native path makes the same cuts, position for position, inside the
native runtime, encodes the chunks on its own worker pool and
concatenates them before the ids reach Python (next section). By default
`encode` chooses between them on its own: the native path runs when the
loaded runtime carries it and the admission table lists the native path
for the artifact, and the Python path runs otherwise. `native=False`
asks for the Python path. `native=True` asks for the native path and
raises `RuntimeError` when either condition is missing, naming which one.
`Tokenizer.encode(text, parallel="auto")`, or `parallel=` a chunk count,
is a shortcut to the same call for a stateless core-stream request.

The Python path is a helper over the public batch path. The chunks go
through the same plan, the same per-input guards and the same fallback
ledger as any document, so a chunk that trips a guard is routed to the
reference on its own, and that cost stays with one chunk instead of the
whole document. Its parallelism is the native batch worker pool, sized
by `RAYON_NUM_THREADS` at first use, with at most one worker per 64 KiB
of payload.

Admission and fallbacks. A tokenizer may be chunked when three things
hold. Its family and artifact digest have an entry in the certified
repair roster, the eleven byte-level BPE artifacts the sync profile was
certified on. Its loader face carries no normalizer, the empty
normalizer sequence, or NFC with every added token matched on the input
text. And the chunked admission table has a certified row for its
artifact, one that holds both levels of chunked-path evidence
(Certification of the chunked path, below). Any other tokenizer is
encoded serially under `R_CHUNK_FAMILY_UNSUPPORTED`, and
`explain()["chunked"]["refusal"]` names the reason. For the table step
that is `artifact_without_chunked_evidence` when the artifact has no row,
`chunked_evidence_incomplete:<status>` when its row holds one level of
evidence only, and `loader_face_differs_from_chunked_evidence:<digest>`
when the loaded face is not the one the row's evidence was taken on. A
document with no certified cut is encoded serially under
`R_CHUNK_NO_CUT`. The native path adds `R_CHUNK_ROUTE_NOT_FAST_CPU` for
an input whose route does not start at the corrected CPU engine. All three are run-time reason codes
(`docs/contracts/routing.md` Section 5.2). They are counted in the
`chunked` block of `explain()` and not in the routing ledger's top-level
`fallback_counts`, because the serial route is the same certified backend
the chunks would have used.

Normalizing families. The cut rule speaks about the text the
pre-tokenizer sees, which for an NFC family (qwen3_8b, qwen3_5_08b and
minimax_m3 on the roster) is the normalized text. A cut certified on
input characters alone can change ids there. U+0958 before a slash is
the example: as written it is a letter followed by punctuation, and once
normalized it is a mark that shares the slash's pre-token. For such a
family a candidate cut is accepted only when it is also a certified cut
of the normalized text. That means a stable split point on both sides (a
character NFC cannot change from either neighbor, decided with the
artifact's own normalizer), no added-token literal in the anchored
window, the normalizer mapping the window to the concatenation of its
halves, and the rule holding on the two normalized characters at the
cut. Three stable characters around a cut need no window at all, so
prose, code and CJK text keep their cuts. `docs/serving.md` Section 3
states the condition, and `norm_rejects` counts the candidates it
declined. The shipped test judges this on a generated corpus of
decomposing characters, combining sequences, jamo, kana voicing marks
and literals beside marks. A 220,000-string run of that corpus over six
roster families (100,000 on qwen3_8b) found no id difference against the
from-scratch reference, where a rule that looked at input characters
only differed on about two percent of the qwen3_8b strings. The quick
part of the cut search is bounded by `scan_budget`, and `min_chunk`
binds the last chunk as well as the others.

The chunk table. With `k=None` the chunk count follows a staircase: one
chunk below 256 K characters, 4 up to 1 M, 16 up to 4 M and 32 above,
capped by one chunk per 64 KiB. It is the argmin of the measured
batch-path latency on three certified families (qwen3_8b, llama_3_1_8b,
gpt_oss_120b) over four corpus types (prose, code, chat transcripts and a
multilingual mix) at 64 K to 4 M characters on one 16-core NUMA node.
Representative readings of the Python path at 1 M characters of English
prose with 16 workers are 26.5 ms serial against 8.6 ms chunked on
qwen3_8b (3.1x), and 9.8 ms against 6.9 ms on llama_3_1_8b (1.4x), where
the Python boundary, each chunk's ids handed over and concatenated, is
most of what remains. Every chunked encode in that measurement (33,518
of them, up to 10 M characters) returned the ids of the from-scratch
reference. The shipped test `tests/test_chunked.py` repeats the identity
check on every admitted family whose artifact it finds locally, over
three corpus types and three lengths, against the oracle package.

Guidance and limits are in `docs/serving.md` Section 3. Two of them bear
repeating. Below 256 K characters a single encode is already as fast.
And a process started with `RAYON_NUM_THREADS=1` gets the chunks one
after another, on either path: exact, not faster.

## Native chunk encoder

The native chunk encoder is the same plan implemented inside the native
runtime, with the literal guard and the normalization-stability
condition included. It plans the cuts in Rust, encodes the chunks on a
persistent pool of corrected-Gigatoken workers and concatenates the ids
before they cross into Python, so the per-chunk Python boundary that
limits the Python path goes away. Each chunk passes the engine's own
guarded full-encode gate, so a chunk that holds an added-token literal or
trips a guard is encoded by the reference on its own, as on the Python
path.

The pool is separate from the batch path's workers. A worker is checked
out for one chunk and returned, so concurrent callers do not share a
prefix of the pool, and the pool size does not depend on the chunk
count. It is forked on first use. `toktier.chunked.warm(tokenizer,
workers=None, text=None)` forks it ahead of the first request, to the
Rayon thread count when `workers` is omitted, and with a sample `text` it
also runs each new worker once so its caches are warm. The chunks run on
the process's Rayon threads, so with `RAYON_NUM_THREADS=1` they run one
after another and stay exact. That is the case inside the SGLang pool's
worker processes, which start with one thread each by default.

Three places report what happened. `ChunkedEncoding.native_facts` carries
the per-call facts of the native path: how many rows each implementation
produced (the corrected engine, or the reference for an added token or a
guard), the plan, encode and concatenation times, and the workers forked
during the call. It is `None` on the Python path. `explain()["chunked"]`
counts native calls in `native_calls` and marks the last call with
`last["native"]`. `toktier.chunked.admission(tokenizer)` reports the
decision for both paths in one dict: `admitted` and `refusal`; the
`family`, `normalizer` and `literals` (the added-token count the guard
holds) behind it; the admission-table row (`evidence_id`,
`evidence_status`, `evidence_paths`, `loader_face_sha256`) and
`admission_gate`; whether the native encoder is reachable
(`native_available`) and whether `native=None` would choose it
(`native_by_default`); and under `native` the native planner's own
facts, or `None` with `native_unavailable_reason` saying why.

Chunking is a CPU-route feature. When the native path is selected for an
input whose route does not start at the corrected CPU engine, which is a
plan with a GPU at its head for an input at or above the GPU crossover,
or a route without the corrected CPU engine, the input is encoded
serially through the normal route and the result says
`R_CHUNK_ROUTE_NOT_FAST_CPU`.

## Certification of the chunked path

The chunked path returns the serial encoding by construction. This
release also binds evidence to it, artifact by artifact, and three kinds
of evidence are worth keeping apart because they say different things.

- The engine differential. The corrected CPU engine's whole-document
  campaign, 41,800,181,401 checks over 11 artifacts and 3,800,016,491
  documents with zero divergence, is evidence about the engine that
  encodes each chunk. It never cut a document, so it says nothing about
  the cuts.
- The adversarial battery. Strings built to stress the cut rule
  (decomposing characters, combining sequences, jamo, kana voicing
  marks, literals beside marks) are encoded on both chunked paths,
  serially and by the reference, and compared id for id.

Which artifacts may be chunked is read from a table that ships with the
package, `toktier/routing/tables/chunked_admission.v1.json`. It is
generated from the evidence records
(`evidence/evidence_manifest_chunked_cuts.json` and

(`python`, `native`). A row is `certified` only when it holds both

a row. Rows are bound to the code they were measured on. The Python
path is bound to `chunked_identity`, a digest of `toktier/chunked.py`
and the two repair tables it reads. The native path is bound to the
corrected CPU engine's version-normalized source digest. A change to
either code takes its rows out of the evidence until it is measured
again.

## Patch-only session append (`Session.append_patch`)

`Session.append(text)` returns a `SessionUpdate` that carries the whole
stream. A serving process usually holds that stream itself and only
needs the splice. `Session.append_patch(text)` returns a `SessionPatch`
with `replace_from` and `replacement_ids` and nothing else, from the same
append and with the same values `append` would report. `append` and
`SessionUpdate` are unchanged (`docs/contracts/facade.md` Section 7).

What it saves today is modest. On the native request path the engine
hands over the whole stream as one Python list on every append (7.2 ms
of the 7.6 ms an append over 220 K tokens costs), so `append_patch`
removes the update object and its copies and is not yet proportional to
the appended text. The Python surface is the one that will not change
when a patch-shaped native return lands (registered below).

## Stateless calls: say so

`encode(text)` with `lookup` omitted asks the content index to digest
the input so a later request can find it. On a request that is never
extended that work is pure overhead, 55-79 % of the encode itself at
1 M characters, and a serving path that knows a request is single-shot
should pass `lookup="off"`. The default is not changing, because the
facade cannot tell a single-shot request from the first turn of a
conversation. The serving layer can, and `docs/serving.md` Section 1
lays out the four request shapes and the call for each. The SGLang
adapter's stateless mode already does this.

## SGLang adapter (`toktier.integrations.sglang`)

The adapter wraps the Hugging Face tokenizer SGLang loads. Its encode
calls run on toktier's certified CPU route, and everything else
(`decode`, chat templates, special-token attributes, vocabulary) is
delegated to the wrapped object. There are two ways to install it. A
small patch adds `--tokenizer-backend toktier`; it comes in two files,
`patches/sglang-0.5.19-toktier-backend.patch` for SGLang 0.5.19 and
`patches/sglang-0.5.21-toktier-backend.patch` for 0.5.20 and 0.5.21.
Without patching anything,
`attach_to_tokenizer_manager(TokenizerManager)` installs the same wrapper
from a `sitecustomize`. A third way needs no adapter at all: compute the
ids with toktier and send `input_ids`. `docs/integration/sglang.md`
describes all three.

Session state can be keyed by the request's `session_id` (else its
`cache_salt`), left to content lookup (`auto`, the default, which needs
no protocol change), or turned off (`off`, stateless encode). Long
stateless requests can be handed to `toktier.chunked.encode` above a
threshold (`TOKTIER_SGLANG_CHUNKED_MIN_CHARS`, off by default). A shadow
mode re-encodes requests with the wrapped tokenizer and compares id by
id.

The wrapper accelerates nothing until it has established that the
object it was handed is the tokenizer toktier loaded. A family or
repository name alone cannot establish this. It serializes the supplied
object's fast backend, tokens added after loading included, and compares
it with toktier's loader face on the sections that decide the core id
stream: model, normalizer, pre-tokenizer, post-processor, added tokens,
truncation and padding. The supplied object's `split_special_tokens`
setting, which the serialization does not carry, must be off. The
`trim_offsets` flag of a byte-level pre-tokenizer or post-processor is
left out on both sides, because it decides character offsets and not ids
(`transformers` 5.12.1 sets it on the live objects of the two Qwen
families, qwen3_8b and qwen3_5_08b, where their artifact files do not).
The check is repeated after construction: before every accelerated
encode a cheap fingerprint of the supplied object's mutable surface is
compared with the one taken at admission, and a difference that turns
out to matter switches the wrapper to delegation for good. Whenever the
two sides are not equivalent, every call goes to the supplied tokenizer
and `stats()["identity"]` records why. The check is always on:
`TOKTIER_SGLANG_IDENTITY` accepts only `require`, and any other value is
refused.

The adapter was checked against SGLang 0.5.19, 0.5.20 and 0.5.21 on
2026-10-13, on the CPU side: the `TokenizerManager` shape, the attach to
the real class, the backend patch applied to each release's published
wheel, and token ids on a real Qwen3-8B tokenizer through both forms,
the worker pool included. The two methods it wraps have the same
signatures in all three. On another version, `attach_to_tokenizer_manager`
first checks that `_tokenize_one_request` and `_tokenize_texts` have the
shape it wraps; if they do not, it leaves SGLang unchanged, returns
`False`, and records `sglang_shape_unverified` with the reason and the
SGLang version. The backend patch is written per release line, as named
above. With the backend patch, the wrapper is installed in SGLang's
`get_tokenizer`, so every SGLang process that loads its tokenizer
through that function gets a wrapper of its own: the tokenizer manager,
and also the scheduler and detokenizer processes, where the attach form
leaves the tokenizer alone (`docs/integration/sglang.md`).

## Scheduled encodes behind the SGLang adapter (`toktier.integrations.sglang_sched`)

SGLang encodes every request on the thread of its event loop, so the
tokenizer is a serial stage of the request path and a long request
occupies one core however many the host has. The certified CPU engine is
serialized inside one process, so parallel encodes need one process
each. The adapter can now run a pool of worker processes, each with its
own loaded tokenizer, and a policy over it. Keyed requests are served on
the session path by a home worker chosen from the key, which keeps the
store's single-writer rule. Stateless ones come from a shared
shortest-first queue with aging. Long stateless ones become certified
chunk tasks that any worker may take, using the cuts of
`toktier.chunked`, so the concatenation is the serial encoding.
`attach_to_tokenizer_manager` also patches `_tokenize_texts`, and the
backend patch adds the same hook
(`toktier.integrations.sglang.tokenize_texts_with_pool`). With the pool
on, a request is then awaited rather than encoded on the loop's thread,
and several requests are in flight at once; without a pool the original
method runs.

The pool is off by default (`TOKTIER_SGLANG_SCHED_WORKERS=0`). A good
starting point is one worker per physical core you can reserve for
tokenization; our own SGLang measurements used four on a 16-core NUMA
node. A request the pool cannot answer is encoded in-process on its
usual route and counted, so ids never depend on the pool. Scheduler
settings are read once through the adapter's own configuration. The
loader of the pool's workers is a construction argument and no longer
has an environment variable. `docs/integration/sglang.md` describes the
settings and the cost, which is that the text and the ids cross a
process boundary on every request. With the backend patch, each SGLang
process that wraps its tokenizer (see the previous section) starts a pool
of its own when the pool is on.

## Installing beside SGLang

toktier pins `transformers==4.57.6`, the loader companion its loader-face
readings were taken with. SGLang 0.5.19, 0.5.20 and 0.5.21 all pin
`transformers==5.12.1`, `tokenizers==0.22.2` and `torch==2.13.0`.
The two cannot be satisfied in one environment by a resolver, so install
SGLang first and then toktier without its dependencies, together with
`platformdirs`:

```
pip install "sglang==<version>"
pip install --no-deps toktier==0.3.0 "platformdirs>=3.0"
pip check
```

`platformdirs` is the one dependency of toktier that SGLang's own
dependencies do not bring. Without it `pip check` also lists it as
missing; toktier still runs and falls back to the standard XDG
directories, which is where `platformdirs` points on Linux. With it,
`pip check` reports one line, toktier's `transformers` requirement
(checked on 2026-10-13 in a new environment with SGLang 0.5.21). The
`tokenizers` version is the one toktier certifies against, and routing
does not consult the `transformers` version, so the certified routes are
the same as in a toktier-only environment. One artifact is the
exception to "nothing else changes": `qwen3_5_08b` declares added tokens
in its configuration, so its loader face is materialized by the
installed `transformers`, and under 5.12.1 that face differs from the
one its readings were taken with. Beside `transformers` 5.x its ids
follow the installed Hugging Face object, the one SGLang itself uses,
and they are outside what the certification covers
(`docs/integration/sglang.md` gives the reading).

## Registered for a later release

- A patch-shaped native return for session appends, behind the
  `append_patch` surface shipped here.
- A pool entry point outside SGLang. In this release the worker pool is
  reachable only through the SGLang adapter.
- Chunk-parallel encode on the Rust `toktier` crate. This release
  reaches it from the Python facade only.
- Accepting a second `transformers` version as the loader companion, so
  that an environment beside SGLang can read as fully certified.
- A second cut mode at the edges of special-token strings, for
  tokenizers whose special tokens neither strip surrounding whitespace
  nor depend on word boundaries.
- A bytes entry point for encode, with UTF-8 validation outside the GIL.
- A Unicode quick-check in front of the corrected CPU engine's
  normalization guard, so non-ASCII text that is already in NFC skips
  the full normalization.
- Per-chunk guard judgement inside a plain `encode`, so an unchunked
  request pays reference speed only for the passage that tripped a
  guard; and, for the batch path's own workers, forking and warming at
  construction, checkout of disjoint idle workers for concurrent
  callers, and the 64 KiB-per-worker floor as a parameter. The native
  chunk encoder's pool already works this way.
- Certification of the DeepSeek-V4.1-Flash tokenizer, which
  `docs/support-matrix.md` records as examined and not certified.

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]"` for the Python package with the pinned Fastokens
adapter. Beside SGLang, use the `--no-deps` install described above.

Served ids are unchanged on every input over every packaged artifact,
and every new surface is opt-in, so code that does not call
`toktier.chunked`, `Session.append_patch`, `Tokenizer.encode(...,
parallel=...)` or the SGLang adapter needs no change. One thing does
want a look before you upgrade.

**A persistent session store written by 0.2.9 is not opened by 0.3.0.**
This is the rule 0.2.8 and 0.2.9 stated for their own upgrades, holding
again for the same reason. The source identities a release rebinds are
components of a store's semantic fingerprint, and the fast CPU identity
moves in this release, the native chunk encoder having joined that
engine's source. A persistent store carries one fingerprint for the
whole directory, and a store whose fingerprint does not match is refused
at open with `SESSION_STATE_MISMATCH` rather than re-encoded record by
record. The refusal leaves the store's bytes as they are. It also works
in the other direction, so 0.2.9 refuses a store that 0.3.0 wrote. The
migration is the same as before. Point `store=` at a directory 0.2.9
never wrote, and replay each session's text into it. In-process session
state is unaffected.

Smaller things a consumer may notice. `explain()` carries a `chunked`
block once `toktier.chunked` has served the tokenizer, and the routing
contract gains three `R_CHUNK_*` codes; both are additions the contracts
already require readers to tolerate.

## Scope

The claims in this release are the claims of the certification registry
and the chunked admission table it ships: what was judged, on which
artifacts, against which oracle version, with which readings. The
chunked path is claimed exact for the artifacts and paths its table
lists, and the rest of the roster is served serially. Nothing here widens
what the whole-document routes were certified for.
