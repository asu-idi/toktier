# TokTier 0.3.1

TokTier 0.3.1 is a registration and evidence release. It certifies six
more tokenizer artifacts, admits the repositories that ship their bytes,
and adds one way of certifying an artifact: the cross-artifact form of the
corpus-equivalence carry-over, under which an artifact holds the readings
of a certified anchor when the two faces differ only in added-token
literals that never occur in the judged corpus. Four artifacts were judged
directly on the full certification corpus (`hy4`, `step5_preview`,
`muse_spark` and `nemotron_super_vl`) and two are certified through the
carry-over (`deepseek_v4_1_flash` and `mimo_v2_6`). The package now ships
21 certified artifacts (21+3 model families) and no examined one, and the
chunked admission table now certifies all eleven roster artifacts, on both
chunked paths.

No engine changes in this release. The corrected CPU engine, the native
GPU request host and the chunked path have the same code as in 0.3.0: their
version-normalized source identities (`fast_cpu` v2, `native_host` v2 and
`chunked_identity`) are unchanged, and the shipped fatbin and the kernel
ABI are the same files. With the same `tokenizers` and `transformers`
releases installed, served ids are unchanged on every input over every
artifact 0.3.0 packaged. The exact source identities of the two engines
(`fast_cpu` and `native_host` v1) move with the package version, because
the workspace `Cargo.toml` and `Cargo.lock` are in their path sets, and
the Rust API identity moves because the embedded tables gained rows; this
release recertifies the roster against all three. The visible consequence
is that a persistent session store the Python facade wrote under 0.3.0 is
not opened by 0.3.1; the Upgrading section says why and what to do.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.3.1. The public API version,
registry schema version, store format version, kernel ABI version and
certification suite version do not move. The support-registry schema
gains four optional members under schema version 1, additive like the
identity columns before them: `carryover.from_family`,
`carryover.from_artifact_sha256` and `carryover.engine_parity` for the
cross-artifact form, and `backends.fast_cpu.repair` for repair parameters
held in a registry record. The evidence-carryover contract
(`docs/contracts/evidence-carryover.md` Section 3.1) and the registry
contract (`docs/contracts/registry.md` Section 3.0) describe them. The two
sibling-table schemas (`schemas/sibling_aliases.schema.json` and
`schemas/sibling_alias_source.schema.json`) pin the table's row counts, so
their counts move with the new rows (215 to 241). No other schema changes,
and no third-party Rust dependency changed.

## Three faces judged on the full corpus: `hy4`, `step5_preview` and `muse_spark`

`hy4`, `step5_preview` and `muse_spark` were each judged directly on the
full certification corpus: 3,800,016,491 documents and
12,328,592,579,973 characters per face, every document encoded by the
accelerated path and compared with the frozen reference digest, with zero
mismatches. The evidence is `evidence/evidence_manifest_roster_2026_10.json`
(`ev-roster-2026-10-v1`, suite `gpu-e2e-differential-v1`, reference
`tokenizers` 0.22.2); 14,197 documents were answered by the reference
frontend because they carry an added-token literal. The readings were taken
with `add_special_tokens=False` under the pinned loader pair,
`transformers` 4.57.6 and `tokenizers` 0.22.2.

The three run on the certified GPU route, on existing kernel bands: `hy4`
on the band of `hy3`, whose splitter sections it shares, and
`step5_preview` on the band of `deepseek_v3` and `deepseek_v4_flash`,
whose core pipeline it holds; `muse_spark` has the split pattern of
`gpt_oss_120b`. The certified repair roster has no row for any of them, so
the corrected CPU engine is not planned for them and the CPU path is the
reference engine (the fast CPU entry reads `unsupported`, for want of a
repair row rather than because the engine was found unable to load them).
`docs/support-matrix.md` has a note per face: `hy4` is a preview
publication pinned at the judged revision; the `step5_preview` face under
a `transformers` 5.x loader is a different object, which the facade
reports as `R_LOADER_FACE_MISMATCH`; and the `muse_spark` anchor is the
upstream repository, whose access is granted on request, while the
campaign read an openly published copy whose tokenizer files are
byte-identical and whose loader face is the same.

## Nemotron 3.5 Super VL (`nemotron_super_vl`)

`nemotron_super_vl` is the `nemotron_3_nano_4b` file with the twelve
special slots at ids 18 to 29 renamed, in the vocabulary and in the
added-token table alike, and nothing else changed. It runs on the anchor's
kernel band with the anchor's parameters. Because the vocabulary belongs to
the core pipeline, both capability ids move (`pipeline.dcfd047a66819db2`,
`added-frontend.e7a4b96faa37718a`), and the two artifacts give different
ids exactly on inputs that contain one of 24 literals. Those literals do
occur in the judged corpus (595,726 times, in 222,203 documents, all of
them the new names), so the carry-over below does not apply and the face
was judged directly: 3,800,016,491 documents encoded by the accelerated
path and compared with the frozen reference digest, with zero mismatches
(`evidence/evidence_manifest_super_vl_2026_11.json`,
`ev-super-vl-2026-11-v1`), under the same pinned loader pair and with
`add_special_tokens=False`. As for the three faces above, the certified
repair roster has no row for it, so the CPU path is the reference engine
and the GPU route is the certified one.

The new section "Renamed special slots inside the vocabulary" of
`docs/support-matrix.md` describes the rename, the document-by-document
comparison of the two artifacts' reference digests (they differ on 222,197
documents, all among those that contain a literal), the file-only loader
face, and why the configuration's `fix_mistral_regex: true` is a no-op for
this face. Four more repositories ship this `tokenizer.json` byte for byte
and are admitted as identical siblings.

Beside the certification campaign, the pinned Fastokens adapter was run
over the same corpus on this face as a research reading: its ids equal the
reference on all 3,800,016,491 documents, with zero mismatches. That
reading is not a certificate, the registry does not carry it, and the
adapter's assurance is unchanged (Pinned Fastokens distribution in
`docs/support-matrix.md`).

## Certified by cross-artifact carry-over: `deepseek_v4_1_flash` and `mimo_v2_6`

0.3.0 listed the DeepSeek-V4.1-Flash tokenizer as examined and not
certified. In this release it is a certified record, and so is the MiMo-V2.6
tokenizer, both through the cross-artifact form of the corpus-equivalence
carry-over (`docs/contracts/evidence-carryover.md` Section 3.1). Each
artifact's loader face equals its certified anchor's as a document outside
the added-token table, the tables differ only in the listed ids
(`deepseek_v4_1_flash` against `deepseek_v4_flash`: 9 ids, 18 literals;
`mimo_v2_6` against `qwen3_8b`: 6 ids, 6 literals), and none of the
differing literals occurs in the judged corpus. The record holds the
anchor's readings, evidence id and suite.

What a carried record ships, and what `tools/generate_registry.py --check`
re-reads:

- an absence certificate per artifact
  (`readings/corpus_absence_deepseek_v4_1_flash.json`,
  `readings/corpus_absence_mimo_v2_6.json`) that counts every differing
  literal, both sides', over the full certification corpus (3,800,016,491
  documents, 15,205 of 15,205 units, nonzero positive controls) and finds
  each zero times;
- a fast CPU engine-parity reading per artifact
  (`readings/fast_cpu_carryover_parity_deepseek_v4_1_flash.json`,
  `readings/fast_cpu_carryover_parity_mimo_v2_6.json`) that compares the
  engine, the public encode path and session appends with the reference
  over the artifact's own face, on 8,680 documents including 380 probes
  that hold the differing literals, with zero mismatches; the check
  requires it to have been taken on the fast CPU engine source identity
  the registry records, so it is taken again with each rebind;
- the anchor's GPU entry, with each family listed in its anchor's kernel
  band and class table (`deepseek_v1`, `cl100k_v3`), backed, as every
  certified prebuilt family is, by the hardware parity readings below.

`toktier.load("deepseek_v4_1_flash")` and `toktier.load("mimo_v2_6")`, and
`from_pretrained` on the pinned repositories, plan the corrected CPU engine
under the default policy and under `policy="certified"` and report
`certification.state: certified_source`; on the Rust face the judged
recipe reads `CertifiedSource` for them under `Policy::Certified`.
Neither family has a row in the chunked admission table, so
`toktier.chunked` encodes them serially; their cut readings are taken and
the row is registered for a later release.

## Chunked path: all eleven roster artifacts admitted

The corpus cut comparison now covers the eleven roster artifacts on both
chunked paths, with no difference from the serial encode or the reference
(102,400,000 web documents per artifact; `readings/chunked_cuts_campaign.json`).
The admission table that ships with the package is generated from it, and
all eleven rows are certified for the Python path and the native chunk
encoder. The seven artifacts that 0.3.0 encoded serially
(`chunked_evidence_incomplete:adversarial_only`) are now chunked, and
`native_evidence_label` reads `None` on every admitted artifact. The
chunked code is unchanged; only the table moved.

## Repair parameters inside registry records

The two carried artifacts are not in the fast CPU repair roster: the roster
keeps the eleven artifacts the CPU campaign judged, its digest and the fast
CPU engine's bound source set unchanged. Their repair parameters (margin,
effective maximum token length, normalizer flag) are the anchor's and are
recorded in the registry record itself, under `backends.fast_cpu.repair`
(`docs/contracts/registry.md` Section 3.0). Both faces read them there: the
Python facade resolves a family from the roster, then from the carried
records, then from the examined table, and refuses a registry in which two
sources give the same family or digest; the Rust runtime merges the carried
rows into its repair set and fails to load on the same collision.

## Sibling repositories

The sibling registry grows from 215 rows (214 siblings, 208 mapping to a
packaged artifact) to 241 rows (240 siblings, 234 packaged): repositories
that ship the bytes of the newly certified artifacts, and repositories of
already certified artifacts published after the 0.3.0 audit, each verified
at a pinned revision. `docs/support-matrix.md` lists them under "Repositories
admitted after the snapshot" and per artifact under "Verified model
repositories".

## The examined-artifact table

The examined-artifact table ships without rows: its one 0.3.0 row,
DeepSeek-V4.1-Flash, is a certified record now. The schema never required a
row, and the table, its digest and its loader stay in place for later use.

## Registered for a later release

- Certified reference versions beyond the judged ones on the Rust side -- a
  `tokenizers` crate release other than 0.22.2 as the embedded reference,
  or the Unicode 17.0 property data -- each of which needs the cargo gates
  and the Rust API matrix taken with a lockfile that resolves it; and a
  wider `tokenizers` edge than `^0.22.2` once that evidence exists for a
  0.23.x release.
- A patch-shaped native return for session appends, behind the
  `append_patch` surface.
- A pool entry point outside SGLang.
- Recording the loader faces under a second `transformers` release.
- A second cut mode at the edges of special-token strings.
- A bytes entry point for encode, with UTF-8 validation outside the GIL.
- A Unicode quick-check in front of the corrected CPU engine's
  normalization guard.
- Per-chunk guard judgement inside a plain `encode`, and forking and
  warming the batch path's workers at construction.
- For GPU-route serving integrations, in one place: the three things such
  an integration waits for (`ROADMAP.md`).
- Admitting the Rust GPU route by source identity under the CPU route's
  rule.
- The first read of `Session.revision` on a persistent session whose
  planned route puts the GPU ahead of the CPU.
- A `tokenizers==0.22.2` constraint carried by the `fastokens` extra
  itself, or a judgement of `toktier-fastokens` against the 0.23 line.
- Segmenting the serial fast route at added-token literals the way the
  chunked path does.
- Sizing the native chunk pool from the configured worker count.
- Deciding whether both faces reject `min_chunk=0`.
- Bringing the `toktier.chunked` module docstring up to date.
- A lockfile lookup that finds the consumer's lockfile when
  `CARGO_TARGET_DIR` is outside the consumer's tree.
- Chunked admission rows for the two carried artifacts,
  `deepseek_v4_1_flash` and `mimo_v2_6`, whose cut readings and adversarial
  battery are taken; the table generator first has to accept a carried
  record.
- Serving the default `add_special_tokens=True` on the corrected CPU
  engine, which the reference backend serves today at reference speed
  (the ids are unaffected): classifying
  post-processors, so that one which inserts no token takes the fast route,
  and inserting the template's tokens in the facade, with certified
  readings, for the artifacts whose template does insert them.

A change that touches a file in a certified identity's path set ships
as a release of its own, recertified against its own build. Several items
above touch the corrected CPU engine or the chunked path, which is why they
are not in this release.

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]" "tokenizers==0.22.2"` for the Python package with the
pinned Fastokens adapter and its exact-id assurance. On the Rust side,
`toktier = { version = "0.3.1" }`.

Served ids are unchanged on every artifact 0.3.0 packaged, and the new
artifacts are additions, so code that loads an artifact 0.3.0 served needs
no change. One thing does want a look before you upgrade.

**A persistent session store the Python facade wrote under 0.3.0 is not
opened by 0.3.1.** The rule 0.2.8, 0.2.9 and 0.3.0 stated for their own
upgrades holds again, for a different reason. The corrected CPU engine's
code does not change in this release, but such a store's semantic
fingerprint binds that engine's exact
source identity (`fast_cpu` v1), whichever backend the store's sessions
were planned on, and the exact identity moves with the package version,
because the workspace `Cargo.toml` and `Cargo.lock` are in its path set; the
version-normalized identity, which does not move, is not a component of the
fingerprint. A store whose fingerprint does not match is refused at open
with `SESSION_STATE_MISMATCH`, with `expected_fingerprint` and
`stored_fingerprint` in its `details`, and its bytes are left as they are.
It works in the other direction too, so 0.3.0 refuses a store that 0.3.1
wrote. The migration is the same as before: point `store=` at a directory
0.3.0 never wrote, and replay each session's text into it. In-process
session state is unaffected, and the store format does not move. The
artifact cache is not affected either: the fetch-manifest entries of the
artifacts 0.3.0 packaged are unchanged, so a cache 0.3.0 filled serves
them under 0.3.1, offline included.

Smaller things a consumer may notice. `toktier inspect` lists 21 artifacts,
all certified, and none as examined. `explain()["certification"]` for a
carried family carries a `carryover` block naming the anchor, the
divergence set and the certificate.

## Scope

The claims in this release are the claims of the certification registry
and the chunked admission table it ships: what was judged, on which
artifacts, against which oracle version, with which readings. A carried
record claims what its anchor's readings claim, for the face its
certificate and engine-parity reading cover. Nothing here widens what the
whole-document routes were certified for.
