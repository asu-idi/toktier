# TokTier 0.3.2

TokTier 0.3.2 is a code release about the prompts serving stacks really
send. A prompt rendered from a chat template, or any prompt that holds a
control token, now runs on the corrected CPU engine and on the GPU route:
the native router cuts the text at the added-token literals, emits each
literal's id itself and encodes the text between them on the accelerated
engine. `add_special_tokens=True` is served on the fast route too. On the
GPU side, `gpu_delivery="auto"` prefers the shipped prebuilt kernel,
`device="cuda:N"` selects one card, and the Rust crate admits its GPU
route by source identity. The chunk-parallel encoder's pool is sized by
configuration, and the two carried artifacts are now chunked.

Served ids do not change. On every artifact 0.3.1 packaged, with the same
`tokenizers` and `transformers` releases installed, every call returns
the ids it returned under 0.3.1; what moves is which engine computes
them. The engine core is the same code as in 0.3.0 and 0.3.1: the
vendored engine crate, the two repair tables, the engine patch and the
shipped fatbin are unchanged files. The routing layer around it changed,
so the version-normalized source identities of the corrected CPU engine
and of the native GPU request host (`fast_cpu` v2 and `native_host` v2)
move, and this release recertifies the roster against the 0.3.2 build
(Hardware readings of this release, below). The visible consequences for
an upgrade are listed under Upgrading.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.3.2. The public API version,
registry schema version, store format version, kernel ABI version and
certification suite version do not move. The support-registry schema
gains one optional member under schema version 1,
`backends.fast_cpu.engine_differential`, for a fast CPU entry judged
directly on its own artifact (`docs/contracts/registry.md` Section 3.0).

## Chat-shaped prompts on the accelerated routes

An added-token literal is a string the tokenizer treats as one token
whatever surrounds it: a chat role marker, a tool-call tag, an
end-of-turn token. Every prompt rendered from a chat template holds
several. On the serial routes such an input went whole to the reference
engine, at reference speed. The native router now segments it:

- The literals are found the way the reference library finds them:
  leftmost-longest, first over the raw text with the literals that match
  raw text, then inside each gap with the literals that match normalized
  text, the second pass only on a face whose normalizer is the identity.
  The two pattern sets and the match kind are the reference library's own.
- Each literal contributes the id the reference emits for it. Each text
  segment between literals is encoded as a document of its own on the
  route's engine: the corrected CPU engine on the CPU route, and on a
  GPU-headed route the GPU for segments at or above the crossover (in one
  batch call) and the next engine for the shorter ones.
- The ids are the concatenation, which is what the reference produces,
  because the reference also encodes every gap between literals
  independently. The segmenter checks itself at construction against the
  reference library's own extraction, and a face whose shape this argument
  does not cover keeps the whole-document reference path.

Segmentation serves the plain `encode` and `encode_batch` calls, the rows
of the native chunk encoder, session seeds and the default content lookup
(`lookup="auto"`, the state route). A face is outside it when one of its
added tokens sets `lstrip`, `rstrip` or `single_word`, when a literal that
matches normalized text sits on a face with an active normalizer, or when
the post-processor is not one of the plain shapes; such a face keeps
routing literal-bearing input to the reference engine, as before. Every
artifact this package ships is inside it.

What `explain()` shows. `runtime_policy.last_execution.path` reads
`gigatoken_segmented` for a literal-bearing document the corrected CPU
engine served by segments, and `gpu_segmented` for one served on the GPU
route. Beside it, a `segments` block names what the document consisted of:
`literals` and `text` (how many of each), `literal_bytes`,
`largest_text_bytes`, and `bytes`, the text bytes each engine produced
(`gpu`, `fast_cpu`, `hf`). The block is present for a segmented
document and for one recorded as `hf_segments_below_crossover` (below). `R_INPUT_ADDED_TOKEN` keeps its name and now means that a
literal-bearing input went to the reference engine because its face is
outside segmentation or a premise failed closed (path `hf_added_token`),
or because, on a route whose only backend after the GPU is the reference,
every text segment is below the GPU crossover (path
`hf_segments_below_crossover`, with the `segments` block)
(`docs/contracts/routing.md` Section 5.2). A face whose literals are long
enough that the construction's overlap reading would exceed its bound (the
sum of squared literal lengths above 2^26 bytes squared; no shipped face
comes near it) is kept outside segmentation, as is a face whose segmenter
self-check disagrees with the reference; the latter also turns session
repair off for that face.

Two things stay as they were. On a family whose loader face normalizes to
NFC, a text segment that is not already in NFC still takes the reference
engine (the engine's normalization guard; see Known differences). And an
artifact with no corrected CPU route keeps the reference engine on the
CPU route; on the GPU route it is segmented like the others.

## `add_special_tokens=True` on the fast route

`add_special_tokens=True` means the post-processor of the reference
document, the loader face the reference engine executes. Each face's
post-processor is classified once, at construction:

| Class | What the post-processor adds to one sequence | How `True` is served |
|---|---|---|
| `identity` | nothing (absent, `ByteLevel`, a template that is the sequence alone) | the core stream on the routed path |
| `prefix` | one special token in front | that id, then the core stream on the routed path |
| `reference` | anything else | the reference engine, as before |

The class is confirmed on the reference engine itself before it is used:
a handful of probes, including an added token alone and inside text and a
non-ASCII string, must satisfy `encode(p, True) == prefix + encode(p,
False)`, and any difference demotes the face to `reference`, which can
only cost speed. On the 21 packaged artifacts, 17 are `identity` and 4 are
`prefix`: `llama_3_1_8b` (`[128000]`), `ministral_3_8b` (`[1]`),
`step5_preview` (`[0]`) and `laguna_s_2_1` (`[2]`).

This covers `Tokenizer.encode(..., add_special_tokens=True)`,
`encode_batch(..., add_special_tokens=True)` and `Session.final_ids()`,
whose default is `True`; the last answers from the session's own stream
with no encode when the session runs on a path with the exact-ID
guarantee. `True` still does not combine with `session=` or
`lookup="auto"` (`UNSUPPORTED_CONFIG`): stores hold the core stream.
`explain()["special_tokens"]` reports `postprocessor_class`,
`document_class`, `prefix_ids`, `served_by` (`core_stream`,
`facade_prefix` or `reference`), the construction check and
`requests`, how many `True` requests the facade and the reference
answered. On the Rust face, `RoutePlan` carries the same class in
`postprocessor_class`, the ids in `special_token_prefix` and the check in
`postprocessor_self_check` (`docs/rust-api.md`).

A plain `Tokenizer.encode(text)` defaults to `add_special_tokens=False`
and was already on the fast route; the 0.3.1 notes described that default
as `True`, which was not accurate. The calls whose default is `True` are
`Session.final_ids()` and the SGLang adapter's Hugging Face-shaped
`encode` / `__call__`.

## GPU delivery and device selection

`gpu_delivery="auto"` takes the shipped prebuilt delivery whenever it can
serve the tokenizer on this machine, and the local JIT delivery only when
prebuilt cannot and the `gpu-jit` profile is installed. An importable
`ninja`, which serving environments often carry for their own extensions,
no longer selects JIT on its own, so a host with a supported GPU no longer
compiles the kernel on its first long request. A process that has already
loaded one delivery keeps it. `toktier doctor` reports the host default as
`automatic_gpu_delivery`, with `automatic_gpu_delivery_basis` saying how
it was reached (`docs/gpu-jit.md` Section 9). When `auto` finds neither
delivery able to serve and the JIT plan refused the toolchain,
`explain()["runtime_policy"]["gpu_delivery_jit_rejection"]` keeps that
refusal (its code and details; `null` otherwise), and under
`device="auto"` the warning 0.3.1 gave in that case is given again.

`device` accepts `"cuda:N"` beside `"auto"`, `"cpu"` and `"cuda"`. Like
`"cuda"` it requires an eligible GPU route, and the planner judges the
route on CUDA ordinal `N` alone, so another card on a mixed host cannot
open it. `N` is the index the CUDA runtime reports, which matches
`nvidia-smi`'s numbering only when `CUDA_DEVICE_ORDER=PCI_BUS_ID` is set.
A refusal names the requested ordinal and the visible devices in its
`details`.

The SGLang adapter passes both settings through: `TOKTIER_SGLANG_DEVICE`
(default `cpu`) and `TOKTIER_SGLANG_GPU_DELIVERY` (default `auto`), or the
matching `AdapterConfig` fields. The default keeps the adapter on the CPU
path, as before, and the adapter's scheduler workers receive both values
(`docs/integration/sglang.md`).

## Rust crate: the GPU route admitted by source identity

A Rust build from the judged sources whose Rust compiler or build flags no
judged row records now admits the GPU route under `Policy::Supported` (the
default) and `Policy::RequireAccelerated`, on judged devices too, labelled
`Supported`, or `LocallyVerified` once `toktier-rust verify-local` has
compared the route on this machine with this build. That is the rule the
fast CPU route has followed since 0.3.0. `Policy::Certified` keeps the GPU
route to the judged recipe and records the new
`ReasonCode::GpuBuildRecipeUnjudged` beside `GpuUncertified`. A build
whose reference library resolves outside its certified versions, or whose
dependency closure could not be compared (`unlocated`), keeps the GPU
route refused, as does a build whose sources are not judged. Each refusal
of an explicitly named CUDA device now says which of these held
(`docs/rust-api.md`, "Device and toolchain assurance").

`RoutePlan` gains `postprocessor_class`, `special_token_prefix`,
`postprocessor_self_check` and `literal_segmentation` (`None` when the
route segments the artifact's literals, otherwise why not), and `encode_with` / `encode_batch_with` with
special tokens follow the class above. Local verification records are now
filed under the build's Rust compiler and build flags as well, since a
comparison made with one build does not speak for another (Upgrading).

## Chunked path

**The native chunk pool is sized by configuration.** The native chunk
encoder runs its rows on a process-wide pool of its own. The first
`toktier.chunked.warm(tok, workers=N)` (or `Chunked::warm` on the Rust
face) builds it with `N` threads, a later larger `N` grows it, and without
a `warm` call the first chunked call builds it with the parallelism
available to the process (its affinity mask and CPU quota).
`RAYON_NUM_THREADS` no longer sizes it, so a serving process that sets that
variable to `1` for its other libraries still encodes chunks in parallel.
A call made from a thread of a Rayon pool the host built stays on that
pool. The Python chunked path (`native=False`) still runs on the engine's
batch workers, which follow the Rayon thread count. The SGLang adapter
starts the pool with a count of its own, `TOKTIER_SGLANG_CHUNKED_WORKERS`
(by default `RAYON_NUM_THREADS` when that is set, otherwise at most 4),
just before its first chunked request, or when it wraps the tokenizer
with `TOKTIER_SGLANG_CHUNKED_WARM=1` (`docs/integration/sglang.md`).
`warm(tok, workers=0)` does nothing and returns the pool's thread count,
as in 0.3.1. A process forked after the native pool was built builds a
pool of its own in the child.

**Thirteen admitted artifacts.** The chunked admission table now carries
certified rows for `deepseek_v4_1_flash` and `mimo_v2_6`, the two records
carried from a roster anchor, so `toktier.chunked` cuts them on both paths.
The admission roster is the certified repair roster plus the records
carried from one of its artifacts. A record judged directly on its own
artifact (the four faces below) is not on it yet.

## Persistent stores and the engine identity

A persistent session store the Python facade opens is keyed by a
fingerprint over everything that decides the ids it holds. For a store
owned by the native request runtime (the certified configurations), the
engine and host part of that key is now the version-normalized source
identity whenever the shipped registry binds it: such a store is refused
when the engine or host code, the reference library version, the build
toolchain or flags change, and not when only the package version does. A
store owned by the Python entry store (no native runtime) stays tied to
its exact build. Within one build, the native request runtime opens a
store the Python entry store wrote, under that store's own key; the
reverse is refused with a message of its own, because the Python entry
store's code is outside the identity the native key covers. A store
written by another release or build is refused with
`SessionStateMismatch` and left as it is. `explain()["store_fingerprint"]`
names the key's domain and, per opened store, the identity it carries.
What this means for a store 0.3.1 wrote is under Upgrading. The Rust
crate's store key now carries its build's exact source identity (the
crate and the routing and store sources it compiles), so a store another
release or build of the Rust crate wrote is refused with
`SessionStateMismatch` as well; releases 0.2.4 to 0.3.1 of the crate
shared one key.

## Packaging: the `fastokens` extra holds `tokenizers` at 0.22.2

`pip install "toktier[fastokens]"` now installs `tokenizers==0.22.2`

## Fixed

- **Device-seeded sessions over text that is not NFC-stable.** A session,
  or a repeated default call through the content store, seeded from a GPU
  row over text that NFC normalization changes could return ids different
  from the reference after an append, on four families whose loader face
  normalizes to NFC. A device row is now adopted into session state only
  when the text equals its normalization; other seeds take the reference
  path (`hf_span_guard`), and the Rust face refuses offsets over such text
  (`BackendExecutionFault`). An NFC-stable non-ASCII device seed pays one
  more normalization pass. Affected releases: 0.2.0 to 0.3.1, with the
  prebuilt GPU delivery, under the default policy too. On an older release
  any one of these avoids it: `gpu_delivery="jit"`, `device="cpu"`,
  `lookup="off"` on the call, normalizing the text and each appended
  delta to NFC before the call, or a `gpu_min_bytes` above the document
  size.
  <!-- TODO(fill: finding number of the device-seeded session defect) -->
- **A prebuilt-delivery tokenizer opened after a JIT kernel in the same
  process.** On a `[gpu, fast_cpu, hf]` family, a tokenizer opened with
  `gpu_delivery="prebuilt"` in a process where a kernel had already been
  loaded through the JIT delivery raised `RuntimeError: fast CPU backend
  lost its live tokenizer` on its first session, persistent-session or
  default call (ids were never wrong). Such calls are now answered by the
  reference engine and `explain()["session_repair"]` reads
  `reference_fallback` with the reason; keeping session repair needs a
  process where only one kernel delivery is loaded.

## Known differences

- **The Python planner is stricter than the Rust face on GPU admission.**
  On a host whose request-host toolchain or build flags differ from the
  judged ones, the Python facade refuses the GPU route under `certified`
  and under the default `supported` policy, while the Rust crate admits
  it under `Policy::Supported`, labelled `Supported`, as described above.
- **`qwen3_5_08b` is chunked on the Python face only.** Its chunked row
  was taken on the loader face the Python facade materializes, and the
  Rust crate reads the artifact file, so `Tokenizer::chunked()` refuses
  it (`loader_face_differs_from_chunked_evidence`) and encodes it
  serially.
- **`deepseek_v3` with `add_special_tokens=True` under a `transformers`
  4.57.x loader.** There `AutoTokenizer` builds `LlamaTokenizerFast`,
  which adds the beginning-of-sentence id `0` in front; the artifact's own
  post-processor adds nothing, and so do the `transformers` 5.x loaders
  (5.12.1, 5.19.0 and 5.22.2 checked) and toktier, on both faces. For
  example `encode("hello world", add_special_tokens=True).ids` is
  `[33310, 2058]` from toktier and from a 5.x `AutoTokenizer`, and
  `[0, 33310, 2058]` from a 4.57.x one. A caller who wants the leading
  id can put the beginning-of-sentence literal in front of the text, which
  encodes to `0` followed by the core stream, or prepend the id:

  ```python
  tok = toktier.load("deepseek_v3")
  bos = "<\uff5cbegin\u2581of\u2581sentence\uff5c>"
  ids = tok.encode(bos + text).ids          # [0, ...]
  ids = [0, *tok.encode(text).ids]          # the same ids
  ```

  The SGLang adapter takes its template from the tokenizer object it
  wraps, so beside a 4.57.x loader it adds the id, as that loader does.
- **Text that changes under NFC.** On a family whose loader face
  normalizes to NFC, a document (or a text segment) that is not already in
  NFC -- a decomposed accent, or a character such as U+09DF that NFC
  rewrites -- is served by the reference engine, with the same ids; on the
  chunked path only the chunk that holds it is. This is the corrected CPU
  engine's normalization guard, which fails closed.
- **Forking after the Python chunked path.** A process forked after the
  Python chunked path (`native=False`) or another Rayon-parallel call has
  run may wait forever on its first such call in the child. Build the pool
  after forking, or use the native chunked path, whose pool is rebuilt in
  the child. `warm(tok, workers=0)` forks nothing and builds no pool.
  Rebuilding the native pool in the child covers a fork made while no
  toktier call is running; a fork made while another thread of the parent
  is inside a toktier call can leave the child holding a lock that thread
  had taken (the chunk pool's, an encoder's worker list, an engine's), and
  the child's first call that needs it then waits. Fork from a thread
  while no other thread is encoding, or start the child with `spawn`.

## Registered for a later release

- Certified reference versions beyond the judged ones on the Rust side -- a
  `tokenizers` crate release other than 0.22.2 as the embedded reference,
  or the Unicode 17.0 property data -- each of which needs the cargo gates
  and the Rust API matrix taken with a lockfile that resolves it; and a
  wider `tokenizers` edge than `^0.22.2` once that evidence exists for a
  0.23.x release.
- The Rust GPU route on a build whose reference library resolves outside
  its certified versions.
- Binding the Rust crate's store key to a version-normalized source
  identity, as the Python facade's is; in this release it carries the
  exact one.
- A patch-shaped native return for session appends, behind the
  `append_patch` surface.
- A pool entry point outside SGLang.
- Recording the loader faces under a second `transformers` release.
- A second cut mode at the edges of special-token strings.
- A bytes entry point for encode, with UTF-8 validation outside the GIL.
- A Unicode quick-check in front of the corrected CPU engine's
  normalization guard.
- Per-chunk guard judgement inside a plain `encode`, and forking and
  warming the batch path's workers at construction.

The consumer-lockfile lookup for a `CARGO_TARGET_DIR` outside the
consumer's tree is not on this list. Cargo gives a dependency's build
script no fact that names the consuming workspace or says whether
`--locked` governs the build, so no lookup can find that lockfile reliably
in that layout; `TOKTIER_CARGO_LOCK` is the way to name it
(`docs/rust-api.md`).

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]"` for the pinned Fastokens adapter, which now brings
`tokenizers==0.22.2` with it. On the Rust side,
`toktier = { version = "0.3.2" }`.

Served ids are unchanged, so code that encodes with 0.3.1 needs no change.
Four things want a look.

**Persistent session stores the Python facade wrote under 0.3.1.** A
persistent store the Python facade wrote with 0.3.1 or earlier is not
opened by 0.3.2: the request fails with `SessionStateMismatch` saying the
store was written by another toktier release or build, with
`expected_fingerprint` and `stored_fingerprint` in its `details`, and the
store's bytes are left as they are. Remove the directory (it is rebuilt
on first use) or give the process another store directory; to keep the
sessions, replay each session's text into the new store. 0.3.1 does not
open a store 0.3.2 wrote either, so a store shared by both releases has
to stay on 0.3.1 or move to 0.3.2 as a whole. Within one 0.3.2 build, the
native request runtime opens a store the Python entry store wrote. In-process
session state is unaffected, the store format does not move, and the
artifact cache is not affected.

**Persistent session stores the Rust crate wrote under 0.3.1.** A
SQLite session store under `<home>/sessions/` that the Rust crate wrote
with 0.3.1 or earlier is not opened by 0.3.2: loading the family fails
with `SessionStateMismatch` ("persistent store does not contain this
tokenizer fingerprint") and the file is left as it is. Remove
`<home>/sessions/<family>.sqlite3` (it is rebuilt on first use) or give
the runtime another home; to keep a session, replay its text. The key
follows the exact sources of the build, so a build of the crate from
changed sources starts a new store too.

**Local verification records on the Rust face.** Records `toktier-rust
verify-local` wrote before 0.3.2 are filed under a key without the build's
Rust compiler and build flags, which this release does not look up. The
routes they described keep the label they have without a record; run
`toktier-rust verify-local` again to file one under the new key.

**`RAYON_NUM_THREADS` no longer sizes the native chunk pool.** A
deployment that used it to bound the chunk encoder's threads should call
`toktier.chunked.warm(tok, workers=N)` (or `Chunked::warm` on the Rust
face) at start-up, or limit the process's CPU affinity. The variable still
sizes the Python chunked path and the batch workers.

Smaller things a consumer may notice. `explain()` carries
`special_tokens` and `store_fingerprint` blocks, and the last execution of
a literal-bearing input reads `gigatoken_segmented` or `gpu_segmented`
with a `segments` block, where it read `hf_added_token`, and
`R_INPUT_ADDED_TOKEN` is counted only for the inputs that still go to the
reference engine (`hf_added_token`, or `hf_segments_below_crossover` on a
`[gpu, hf]` route). `runtime_policy` carries `gpu_delivery_jit_rejection`. Reading `Session.revision` on a fresh persistent
session whose plan puts the GPU ahead of the corrected CPU engine returns
the store's answer instead of raising `RuntimeError`.

## Scope

The claims in this release are the claims of the certification registry
and the chunked admission table it ships: what was judged, on which
artifacts, against which oracle version, with which readings. Literal
segmentation and the `True` prefix are exact by construction, and the
readings of the 0.3.2 build are what the certificate rests on. Nothing
here widens what the whole-document routes were certified for.
