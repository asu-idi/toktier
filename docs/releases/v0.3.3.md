# TokTier 0.3.3

TokTier 0.3.3 is a repair release of the Rust crate. Its session store no
longer keeps a record for every block of text it has stored, so the
memory of a long-lived Rust process now follows the sessions it holds;
`Tokenizer::lookup` is served by a small index of the live sessions
instead. And a Rust build whose lockfile resolves newer Unicode property
data than the judged one no longer returns ids that differ from the
reference engine: texts that the newer data classifies differently are
sent to the reference engine, and a build whose data the release does not
list, or whose lockfile it cannot read, does not get the fast CPU route. A
check at tokenizer construction declines the fast CPU route where the
lockfile that was read names the judged data but the engine does not
encode as the judged data would.
The SGLang adapter in the Python package receives a set of smaller
repairs and settings (Fixed and Changed, below).

Served ids do not change, except where 0.3.2 returned ids that differ
from the reference (the property-data item under Fixed). The engine core,
the routing layer, the two repair tables, the engine patch and the shipped
fatbin are the code 0.3.2 shipped, so the version-normalized source
identities of the corrected CPU engine and of the native GPU request host
(`fast_cpu` v2 and `native_host` v2) and the chunked identity do not move.
The changes sit in the Rust crate's own sources (the `rust_api` identity)
and in the Python package's SGLang integration, which is in no identity
set. The Python package's tokenizers, sessions and stores are otherwise
the code 0.3.2 shipped, and wheels were never affected by the
property-data item.

Version axes moved by this release (see `docs/contracts/versioning.md`):
the package version (axis 1) moves to 0.3.3. The public API version,
registry schema version, store format version, kernel ABI version and
certification suite version do not move. On the Rust surface,
`StoreStats` gains three fields, `RuntimeBuilder` one option,
`RuntimeBuildFacts` two fields and `ReasonCode` three variants; each of
these types is `#[non_exhaustive]`, so the additions are minor-release
changes (`docs/rust-api.md`).

## Fixed

- **The Rust crate's session store kept a record for every block of text
  it stored.** In the Rust crate 0.2.0 to 0.3.2, every session call that
  stored text (`seed`, `append`, `overwrite`, `encode_transcript`) and a
  `Tokenizer::lookup` hit whose remainder completed a block wrote one
  record per completed 4,096-character block, each holding a copy of the
  text from the session's last seal point to the block's end, and nothing
  removed one: `close()`, `delete()` and the eviction of a session at the
  capacity left the records. Measured on the 0.3.2 crate for ASCII text,
  one distinct text stored in one call and then deleted kept about 4.4 KB
  at 6,000 characters, 64.7 KB at 24,000, 328 KB at 50,000 and 570 KB at
  100,000. In durable mode the records were also written to the SQLite
  file and read back at start. In a router's shape (one tokenizer,
  sessions under conversation ids, 512 idle sessions kept, ten turns per
  conversation, each turn sending the whole transcript) the 0.3.2 crate
  kept about 108.5 KB per finished conversation of 50,000 characters, and
  about 94.5 KB per conversation of 35,500 characters that shares one of
  four 20,000-character system prompts, about 10.9 GB and 9.5 GB per
  100,000 conversations.

  In 0.3.3 the crate writes no such record. `Tokenizer::lookup` reads an
  index of the sessions stored now: one entry per completed
  4,096-character block of a live session's text, shared by the sessions
  that have that block, holding no text and no token ids, and released
  when the last session with the block is deleted, overwritten or dropped.
  `RuntimeBuilder::lookup_index_blocks(n)` caps the entries per tokenizer
  (default 262,144; `0` keeps no index and makes `lookup` return `None`).
  An entry takes a few hundred bytes by the crate's own estimate (136
  bytes for sessions stored in one call, about 330 in the router's shape),
  so the default cap stands for about 36 to 86 MB. At the cap a session
  whose next block would need a new entry stops adding blocks for the rest
  of its life (an `overwrite` gives it a new start), and
  `store_stats().index_blocks_declined` counts it; lookups keep working on
  what is indexed, and nothing is evicted to make room.

  Measured on the 0.3.3 sources (`qwen3_8b`, the same router shapes,
  100,000 conversations each): memory is flat, at +0.57 and -4.15 bytes
  per conversation over the last 50,000 (resident memory 263.7 MB after
  1,000 conversations and 264.4 MB after 100,000 in the first shape), and
  `store_stats().node_count` never exceeds the blocks of the live sessions
  (at most 6,144 and 2,064 entries), where on 0.3.2 it reached 121,428 and
  50,953 after 10,000 conversations against 6,144 and 4,096 live blocks. A
  durable store under 20,000 cycles of create, append and delete, reopened
  every 1,000 cycles, held no block row at any reopen, and its file stayed
  at 561 KB from the 4,000th cycle on. Token ids are unchanged: on all 17
  families with a corrected CPU route, 17,000,068 compared sequences of
  sessions and lookups (and 1,700,060 more with the store closed and
  reopened every 300 steps) equal both `Tokenizer::encode` and the
  reference library, `tokenizers` 0.22.2, with none differing; 62.5 to
  63.4 % of the lookup hits reused stored ids.

  What changes for a caller:

  - A lookup of text whose sessions were all deleted, overwritten or
    dropped is now a miss. A text whose first 4,096-character block is
    shared with a live session (a common system prompt) can still hit.
  - A lookup hit creates no session and writes nothing. On a full
    memory-mode store it no longer drops a session, and a durable store no
    longer keeps a slot free for it; the bound of 1,023 named sessions is
    unchanged. In memory mode, a hit that reuses a session's ids counts as
    a use of that session in the store's least-recently-used order.
  - A hit reuses ids only from a session that grew by appends past the
    shared blocks, up to a seal point certified before the shared block
    was completed; otherwise it encodes the whole text and is still exact.
    Text stored in one call (a system prompt sent with the first turn)
    therefore offers nothing to reuse, and on a family planned on the
    reference engine no session has a seal. `store_stats().lookup_reused_ids`
    beside `lookup_hits` tells the two apart. The index lists up to four
    sessions per block, the most recent ones: when those four are deleted
    while older sessions with the block live on, hits on that block stop
    reusing ids (in our readings a hit then cost about 345 us against about
    31 us with reuse, on a 21,500-character text).
  - After a durable store is reopened, the index is rebuilt from the
    stored transcripts: every stored session is found at once, and its ids
    are reused again once it completes its next 4,096-character block.
  - `store_stats().node_count` counts index entries and falls when sessions
    are deleted; `index_bytes` (an estimate of the index's size),
    `lookup_reused_ids` and `index_blocks_declined` are new, and
    `checksum_rejects` also counts listed sessions a lookup set aside
    because they no longer agreed with the store (it should read 0). A
    lookup no longer adds to `puts` or `appends`.
  - A name whose session was dropped at the memory-mode capacity is
    forgotten when the store drops it, so `fork()` into it succeeds.

  Lookups also became cheaper. Single-threaded, on `qwen3_8b` with a
  1,000,000-character stored session, a hit that adds 500 to 5,000
  characters took 0.93 to 1.05 ms against 4.6 to 4.9 ms on 0.3.2, and a
  miss 4.4 to 4.9 us against 1.13 ms; a plain `encode` took the same time
  on both. With two threads looking up and two appending for six seconds
  on four cores, on sessions that all share one prefix, appends ran 3.7 times (1,000 sessions, 20,000-character
  prefix) to about 600 times (600 sessions, 100,000-character prefix) as
  fast as on 0.3.2, lookups 1.6 to 4.4 times as fast, and the slowest
  single call took under 4 ms where it took 3.2 to 3.8 s on 0.3.2 with the
  long prefix.

  Affected releases: the Rust crate 0.2.0 to 0.3.2. The Python package
  stopped writing these records in 0.3.2. On an older release: drop every
  `Tokenizer` clone and session (or the process) on a schedule or when its
  memory passes a threshold; in durable mode remove
  `<home>/sessions/<family>.sqlite3` as well, which removes its sessions
  too. A durable store written by 0.3.2 is not opened by 0.3.3 (Upgrading).

- **Unicode property data on a consumer's lockfile in the Rust crate.**
  The corrected CPU engine takes its character classes from the
  `icu_properties_data` copy the build compiles, while the reference
  engine, which defines the ids, classifies by Unicode 16.0. In the Rust
  crate 0.3.0 to 0.3.2, a build whose lockfile resolved `icu_properties`
  2.1 or later ran the fast CPU route with that newer data and could
  return ids that differ from the reference engine's on a text holding a
  code point whose class moved: 4,804 code points for the data of
  `icu_properties` 2.1 to 2.3 (Unicode 17.0), and 17,811 for
  `icu_properties_data` 2.4.0, mostly code points assigned after Unicode
  16.0 (new scripts, recent emoji) and U+0295. For example
  `"1\u{11DE1}2345"` encoded to other ids on `llama_3_1_8b`. ASCII and CJK
  text was not affected, and neither were wheels, which are built from the
  judged lockfile. A consumer's fresh lockfile usually resolves the newest
  2.x, since the ICU4X crates arrive through common dependencies, and so
  does `cargo install` without `--locked`. To tell whether a build is
  affected, run `cargo tree -i icu_properties_data` (or look the two crates
  up in its `Cargo.lock`): anything other than `icu_properties` 2.0.2 with
  `icu_properties_data` 2.0.1 is newer data.

  In 0.3.3 the build script reads which copies of `icu_properties` and
  `icu_properties_data` the lockfile names; only copies of major version
  2, the one the engine links, count. It reads the lockfile above the
  build's output directory (a build with the default target directory
  inside the project), or the one `TOKTIER_CARGO_LOCK` names. **The
  variable must be the absolute path of the `Cargo.lock` of the build that
  consumes the crate**: an empty or relative value, a path inside the
  crate's own directory, a missing file and a lockfile that holds no
  `toktier` package are not read. What a build then does depends on what
  it read:

  - **The judged copies** (`icu_properties` 2.0.2, `icu_properties_data`
    2.0.1): nothing is added to any encode call. A check at tokenizer
    construction confirms the reading (below).
  - **A newer copy the release lists**: the fast CPU route stays, and a
    text holding one of the 17,811 listed code points goes to the
    reference engine. Such a call reports `Backend::HuggingFace` with
    `InputGuardRouted` (also the reason of the engine's own input guard),
    and `Runtime::doctor().runtime_build.property_data` says that the
    build is guarded. A session whose unsealed text holds such a code point
    re-encodes that text on the reference engine at every append, which
    grows with the session (in our readings about 220 times slower than
    the fast route over 300 appends of 200 characters, and 920 times over
    1,200).
  - **A copy the release does not list, a copy from another source, or
    `ICU4X_DATA_DIR` set at build time** (it replaces the compiled data
    whatever the lockfile says): the fast CPU route is not built, and every
    text goes to the reference engine, 27 to 162 times slower on a
    tokenizer without a normalizer. The plan lists `PropertyDataUntabled`.
  - **No lockfile read**: the same, with `PropertyDataUnread`. No lockfile
    is read for a target directory outside the project (`CARGO_TARGET_DIR`,
    `build.target-dir`, `--target-dir`, or Cargo's `build.build-dir`), for
    `cargo install` from crates.io or `git`, or for this project's own
    workspace built with such a directory.

  On the last two, `Policy::RequireAccelerated` refuses the tokenizer with
  a message that points at `Runtime::doctor()`, and the `property_data`
  line starts with `unread:` or `untabled:` and names the remedy: set
  `TOKTIER_CARGO_LOCK` to the absolute path of the build's own
  `Cargo.lock`, use a target directory inside the project, align the
  lockfile with the two `cargo update` commands it prints, or unset
  `ICU4X_DATA_DIR`. Each command names the copy it updates, so that Cargo
  can select it when the lockfile also holds a copy of another major
  version (an `icu_properties` 1.5 that another dependency brings in, for
  example): with a resolved copy known,
  `cargo update --package icu_properties@<resolved version> --precise 2.0.2`
  and `cargo update --package icu_properties_data@<resolved version>
  --precise 2.0.1`; with none known (an unread build),
  `cargo update --package icu_properties@2 --precise 2.0.2` and
  `cargo update --package icu_properties_data@2 --precise 2.0.1`. The bare
  form `--package icu_properties_data` is refused by Cargo as ambiguous
  when two major versions are present. A path
  dependency and this workspace's own builds also print a `warning:
  toktier: ...` line naming the reason; Cargo shows build-script warnings
  neither for `git` nor for registry dependencies, so a crates.io consumer
  sees the plan reason and the `doctor()` line at run time instead.
  `Policy::Experimental` keeps the fast route on untabled and unread builds
  and sends listed code points to the reference engine; the list was not
  made for such data, so the other ids are unchecked there.

  **Cost on a guarded build.** The scan reads 0.06 to 1.0 ns per byte by
  script (English 16.5 GB/s, Japanese 3.7, Korean 1.9, Hindi 1.4,
  Vietnamese 1.0). On a tokenizer without a normalizer it adds about 1 to
  3 % to English, Japanese and Korean text and 10 to 21 % to Hindi and
  Vietnamese when the words are new to the engine's word cache, and 8 to
  37 % when they are cached (English 8 %, Japanese 14 %, Hindi 21 %,
  Korean 23 %, Vietnamese 37 %, at 300 KB); on NFC tokenizers a few
  percent. Judged builds pay nothing per call (only the check at
  tokenizer construction, below), and aligning the lockfile with the
  printed commands makes a build judged.

  **The check at tokenizer construction.** On a build whose property data
  reads `judged`, constructing a tokenizer with a fast CPU engine
  (`Runtime::load` and the other constructors, under every policy but
  `Policy::Reference`) first encodes four short probe texts on the fast
  CPU engine and on the reference engine, and the id sequences must be
  equal. The texts hold code points
  that are unassigned in the judged data and assigned in every listed
  later copy (U+11DE1, U+323B0, U+1E6E0 and U+20C1, in number, contraction
  and symbol contexts), so a build that compiled other listed property
  data than its lockfile names gives different ids on at least one of
  them. The check runs before the tokenizer is returned, so no request
  reaches a fast route that has not been confirmed. Builds that read
  `guarded`, `untabled` or `unread`, tokenizers without a fast CPU engine,
  and `Policy::Reference` run nothing.

  If any probe differs, or cannot complete, the fast CPU route is dropped
  for that tokenizer and for every later construction on the same
  `Runtime`, under every policy, `Policy::Experimental` included. The plan
  lists `ReasonCode::PropertyDataContradicted`, and the tokenizer runs on
  the reference engine and returns the reference ids. Under
  `Policy::RequireAccelerated` a family with no other accelerated route
  fails to load with `UncertifiedTokenizer`, and the message names the
  property data. `Runtime::doctor()` does not run the check itself:
  before any construction `runtime_build.property_data` reads `judged`,
  and after a construction that found a contradiction it reads

  ```
  untabled: judged property-data reading contradicted by an encode check: family llama_3_1_8b, probe "1\u{11de1}2345": fast and reference ids differ; the fast CPU route is declined, including under Policy::Experimental; rebuild with the consuming build's actual lockfile (TOKTIER_CARGO_LOCK must be absolute), use --locked with cargo install --path, or align the actual property data with the judged copies
  ```

  A match keeps the standing the lockfile gave and nothing more: a
  `judged` build stays `judged`, and `unread` or `untabled` builds are
  neither checked nor raised to `judged` or `guarded` by it. A match is not
  evidence that the data is the judged data, since the fast engine's own
  reference fallback can also answer a probe. The check runs once per
  tokenizer construction on a judged build: in our readings (one CPU core,
  medians of nine processes, timed apart from the first encode) 0.54 ms on
  `llama_3_1_8b`, 0.59 ms on `qwen3_8b` and 1.24 ms on `deepseek_v3` for
  the first tokenizer of a process, and 0.18 to 0.90 ms for a second one;
  whole loads took 440 to 560 ms, with and without the check alike.
  Because the probes warm the engine, the first ordinary encode afterwards
  is faster (about 14 us instead of 20 to 30 us). Nothing is added to an
  encode call, a batch, a session or a lookup.

  **The ids are correct whenever the lockfile that is read is the one that
  governed the build.** The build script cannot prove that, and some
  layouts read a file that does not describe the build:
  `cargo install --path` without `--locked` (Cargo resolves again and the
  lockfile beside the project no longer describes the build), a
  `TOKTIER_CARGO_LOCK` that names another checkout's lockfile, or a hard
  link or copy of one, an outside target directory placed under another
  project's tree, a target directory inside a checkout used by path (it
  reads that checkout's lockfile), and a lockfile left from an older
  version of this crate. When such a file reads judged but the build
  compiled a later listed property-data copy, the check at tokenizer
  construction sees the difference: the fast CPU route is declined with
  `PropertyDataContradicted`, the ids are the reference engine's, and
  `doctor()` names the contradiction and the remedy after the first
  construction. In our readings this held in each of these layouts, built
  with the copies 2.3.0 and 2.4.0, and on all 17 families with a fast CPU
  route. A finite set of probe texts cannot prove exactness on arbitrary
  data: a build whose lockfile was read wrongly and whose data differs
  from the judged data only outside the probe texts is not detected; none
  is known among the released data versions. Use `--locked` with
  `cargo install --path`, name the consuming build's own lockfile by
  absolute path, and keep an outside target directory out of other
  projects' trees. A target directory or build cache copied into another
  checkout keeps the first reading until `cargo clean -p toktier`.

  The guard and the check are part of the Rust crate; the Python
  package's native module does not include them.

  Affected releases: the Rust crate 0.3.0 to 0.3.2. On 0.3.2 today, any
  one of these avoids it: align the lockfile with
  `cargo update --package icu_properties@2 --precise 2.0.2` and
  `cargo update --package icu_properties_data@2 --precise 2.0.1` where the
  dependency graph allows it, build with `--locked` from the published
  lockfile (`cargo install --locked toktier`), or use `Policy::Reference`,
  which encodes every text on the reference engine. A durable session
  store written by an affected build may hold ids from before the repair
  for texts with such code points; remove its file, or seed those sessions
  again.

- **`load_local` on a path that is a symbolic link.** A path given to
  `Runtime::load_local` may now be, or lead through, a symbolic link, as a
  model-hub snapshot directory is. The link is followed once at load, the
  bytes verified then are the ones served, and errors name the path as
  given. The default cache entry is still required to be a regular file.

- **Closing the SGLang adapter's worker pool could wait forever.** In
  0.3.2, closing the wrapper or its scheduler while the pool was saturated
  with long prompts could block for good: a task larger than the pipe
  could be dispatched after the stop message, and `close()` then waited
  for a feeder thread nobody read from. The same `close()` serves the
  wrapper's exit hook. In 0.3.3 the scheduler uses bounded joins also when
  the pool is saturated: nothing is dispatched once the pool is closed,
  and the workers' last answers are read off their pipes while they stop
  (in our readings a pool of two workers with twelve 2 MB requests queued
  closed in 0.3 to 0.6 s). A worker that does not stop within five seconds
  is terminated, and one that still runs five seconds later is killed.
  These joins do not put a deadline on the wrapper's close, an in-process
  encode or a hook the caller provides. Once the workers are stopped,
  `close()` also releases a transfer that a stopped worker left half
  done, and the pool's queues, feeder threads and process handles are
  released (readings on CPython 3.12 on Linux; the release relies on
  CPython multiprocessing queue internals for this). If termination fails
  or a worker is still alive after the last timed join, `close()` can
  return with a live worker and feeder; complete cleanup is not
  guaranteed in that case. Closing the scheduler while the wrapper stays
  open answers in process, with the same ids, the requests waiting in the
  pool and those that had chosen the pool but not yet reached it.
- **Pool workers outlived the server.** The adapter's pool workers now
  leave when the process that started them is gone, whatever ended it: a
  normal exit, SIGTERM, SIGKILL or `os._exit`. On Linux the kernel sends
  them SIGKILL when the parent exits (armed when the pool is started from
  the parent's main thread, as SGLang does), which ends a worker in the
  middle of an encode; on every platform an idle worker also checks its
  parent once a second, between tasks, and a busy one finishes its task
  first. With a store directory, what the store had not yet written may be
  lost, as it is when the server itself is killed.
- **Requests in flight when the supplied tokenizer changes.** When the
  tokenizer SGLang supplied is changed after the wrap and the wrapper
  switches to passthrough, a completed accelerated result whose acceptance
  check runs after the switch is now replaced by an answer from the
  supplied tokenizer. Acceptance is per text, in batches and in the pool
  helper too: results accepted before the switch may still be returned
  afterwards, and a concurrent batch may hold rows from both sides of the
  switch, so this is not an atomic snapshot of a whole batch. In 0.3.2
  some in-flight requests could fail with `AttributeError`.
- **A wrap that fails left workers running.** If the wrap fails after
  something has started (during the pool's start, after it, or during
  eager chunk warming), the pool's workers, the toktier tokenizer, the
  shadow thread and the timing log are now closed before the error is
  raised. The native chunk threads belong to the process and are shared
  by every tokenizer in it; they stay, as in 0.3.2.

## Changed

- **A tokenizer toktier cannot resolve is served in passthrough.** When
  nothing names the tokenizer for toktier (no `TOKTIER_SGLANG_FAMILY`, no
  `TOKTIER_SGLANG_REPO`) and toktier finds no artifact for it -- a local
  model directory, a repository without `tokenizer.json`, a tokenizer with
  no `name_or_path`, or a hub id whose files are not cached on an offline
  host -- the wrap no longer raises: the wrapper serves every call with the
  supplied tokenizer (`identity["status"] == "unresolved"`, the reason
  beside it) and logs one warning on the logger
  `toktier.integrations.sglang`. A `TOKTIER_SGLANG_FAMILY` or
  `TOKTIER_SGLANG_REPO` that is set and does not resolve still raises
  `ArtifactNotFound`, naming the setting, its value and the remedy.
  `TOKTIER_SGLANG_REQUIRE_ARTIFACT=1` restores the 0.3.2 behaviour, a raise
  whenever no artifact resolves.
- **`accelerates`.** The wrapper has a boolean `accelerates`: true when an
  admitted accelerated route is available, false in passthrough and for a
  tokenizer toktier knows only as external. Short requests are answered
  by the supplied tokenizer even when it is true. It appears in `repr`
  (the line SGLang logs at start-up), in `stats()` and in the timing log's
  `init` record. On 0.3.2 the same fact is
  `wrapper.planned_backend not in (None, "hf")`.
- **`encode_texts_with_pool(tokenizer, texts, key=...,
  add_special_tokens=True)`**, a pool entry point that takes the tokenizer
  and the texts, returns the rows when `tokenizer` is the wrapper with a
  running pool and `None` otherwise, so a caller can make the pool one
  branch of its own encode step. `tokenize_texts_with_pool` stays and now
  calls it.
- **The per-request check is cheaper.** Before every accelerated encode
  the wrapper checks that the encode-affecting surface of the supplied
  tokenizer is still the one it admitted. The check now costs about half
  of what it did, growing with the number of added tokens (4.92 against
  9.23 us on Qwen3-8B, 44.75 against 100.52 us on Llama-3.1-8B, 253.92
  against 562.82 us on DeepSeek-V4-Flash).
- **Short requests are answered by the supplied tokenizer.** The rule is
  on by default. Once the wrapper has completed one encode on its
  accelerated route, a string shorter than `TOKTIER_SGLANG_SHORT_CHARS`
  characters is answered by the supplied tokenizer on the calling thread,
  without the per-request check, and counted as
  `stats()["how"]["short"]`. With the variable unset the threshold is the
  number of added tokens of the tokenizer (26 on Qwen3-8B, 256 on
  Llama-3.1-8B, 1,283 on DeepSeek-V4-Flash);
  `TOKTIER_SGLANG_SHORT_CHARS=0` turns the rule off and restores the 0.3.2
  routing. On tokenizers with many added tokens it removes most of the
  check's cost from short requests (a 40-character request took 17.35 us
  with the rule on against 45.72 off on Llama-3.1-8B, and 22.14 against
  203.32 us on DeepSeek-V4-Flash). In the measured Qwen3-8B requests of 1
  to 25 characters the accelerated route was the cheaper one, so the
  default cost a little there (at most 5.74 us per request in that run),
  and `TOKTIER_SGLANG_SHORT_CHARS=0` is a choice for such workloads. Until
  the first accelerated encode has completed, every call takes the route
  it took in 0.3.2, so a start-up probe still opens the engine and the
  session store. A short text does not enter the session store and does
  not go to the pool; `accelerates` is not affected.
- **The session store's directory is created when the wrapper is built**,
  so a path that cannot be created stops the wrap at once instead of
  failing every request.
- **Gemma 4 in the support matrix.** The `google/gemma-4-*` line under
  "Documented exclusions" now says what holds: its pipeline provides no
  pre-tokenization boundaries, but its vocabulary does, and on the full
  certification corpus the engine equals the reference under that rule.
  Gemma 4 is still not admitted for session repair or chunking and is not
  a certified artifact in this release (`docs/support-matrix.md`).

## Known issues

None of these affects token ids, and none is new in 0.3.3.

- **The Rust crate executes `tokenizer.json` alone.** Special tokens
  declared only in `tokenizer_config.json` are not added tokens to this
  crate. Among the packaged artifacts this concerns `qwen3_5_08b`, whose
  seven such literals (`<|audio_start|>`, `<|audio_end|>`, `<tts_pad>`,
  `<tts_text_bos>`, `<tts_text_eod>`, `<tts_text_bos_single>`,
  `<|audio_pad|>`) the crate encodes as ordinary text, while a loader that
  merges the config file, as the Python package does since 0.2.8, encodes
  each as one id. The certified corpora hold none of the seven
  (`readings/corpus_absence_qwen3_5_08b.json`). A Rust host whose own
  reference tokenizer merges `tokenizer_config.json` should keep that
  artifact on its own tokenizer, or send the prompts that hold one of the
  seven literals to it.
- **One `Tokenizer` serves one single-text encode or session call at a
  time.** The engine's state and the session store each sit behind one
  lock, so threads that share one tokenizer queue, and the wait is uneven:
  in one reading on `qwen3_8b` (100,000-character texts, four threads on
  one tokenizer) the slowest of 240 encodes took 61.5 ms and the slowest of
  160 seeds 178 ms, against 9.2 and 16.9 ms with one tokenizer per thread.
  For requests without sessions use `encode_batch` or `ServingPool`, which
  encode a batch on parallel states; for sessions, use one `Tokenizer` per
  worker thread and pin each conversation to one of them by its session
  key. An extra tokenizer costs about 120 MiB and 0.9 s to load on
  `qwen3_8b`, and in durable mode each tokenizer needs a home of its own
  (`docs/rust-api.md`, "Concurrency").
- **The corrected CPU engine's word cache.** The corrected CPU engine
  keeps every word (pre-token) it has encoded in a cache for the life of
  the tokenizer, with no upper bound, on stateless calls too
  (`lookup="off"`, the SGLang adapter's stateless mode). It costs about
  70 bytes per word not seen before and stays flat while the input's
  vocabulary repeats; on random base64 text, where few words repeat, it
  kept about 7 bytes per input byte. 0.3.2 measures the same. A long-lived
  worker on open-vocabulary input, such as identifiers or encoded data,
  should have its memory watched or be recycled; in the Rust crate, watch
  the memory or load the tokenizer again.
- **Two smaller structures** (read from the code). With the `diagnostics`
  setting on (`TOKTIER_DIAGNOSTICS`, off by default) the router's event
  list grows by one entry per recorded routing event, on a GPU-headed
  route one for every request below the crossover, and `explain()` copies
  it whole. The index of the Python package's persistent store directory
  (`index.json` under `store=`) lists every named session ever written to
  it, and every write rewrites the whole index.

## Registered for a later release

- The engine core building its character classes from an embedded judged
  table, after which no resolved property data, lockfile or layout can
  change ids and the property-data guard of this release can be removed.
- An option of the Rust crate that serves the loader face (the artifact
  file merged with the special tokens of `tokenizer_config.json`).
- A pool of encoder states inside one tokenizer for single-text and
  session calls, and encoding outside the session store's lock.
- A bound inside the corrected CPU engine's word cache.
- A bound on the diagnostics event list; the Python directory store's
  index growth and a delete call for Python sessions.
- Improvements of the lookup index: an index kept across durable
  restarts, an entry for a session's whole text, seal points inside a text
  stored in one call, and more than four listed sessions per block.
- A configurable session capacity, a dedicated error code for a full
  store, and `overwrite` dropping the old state before the new one is
  stored.
- A clearer `device="cuda"` error under a loader-face mismatch.
- Certified reference versions beyond the judged ones on the Rust side --
  a `tokenizers` crate release other than 0.22.2 as the embedded
  reference, or the Unicode 17.0 property data -- each of which needs the
  cargo gates and the Rust API matrix taken with a lockfile that resolves
  it; and a wider `tokenizers` edge than `^0.22.2` once that evidence
  exists for a 0.23.x release.
- The Rust GPU route on a build whose reference library resolves outside
  its certified versions.
- Binding the Rust crate's store key to a version-normalized source
  identity, as the Python facade's is; in this release it carries the
  exact one.
- The reference route's behaviour under `transformers` 5.x.
- In the SGLang adapter: placing keyless requests by their first 4,096
  characters, recognising a local model directory by the content of its
  `tokenizer.json`, and a design for the passthrough that follows the
  first media request on a multimodal model.
- Admitting Gemma 4 (`google/gemma-4-*`) on the fast CPU route, and then
  for session repair and chunking under its vocabulary's boundary rule.
- A patch-shaped native return for session appends, behind the
  `append_patch` surface.
- A pool entry point outside SGLang.
- Recording the loader faces under a second `transformers` release.
- A second cut mode at the edges of special-token strings.
- A bytes entry point for encode, with UTF-8 validation outside the GIL.
- A Unicode quick-check in front of the corrected CPU engine's
  normalization guard.
- Per-chunk guard judgement inside a plain `encode`, and forking and
  warming the batch path's workers at construction.

The consumer-lockfile lookup for a `CARGO_TARGET_DIR` outside the
consumer's tree is still not on this list. Cargo gives a dependency's
build script no fact that names the consuming workspace or says whether
`--locked` governs the build, so no lookup can find that lockfile reliably
in that layout; `TOKTIER_CARGO_LOCK` is the way to name it
(`docs/rust-api.md`).

## Upgrading

`pip install --upgrade toktier`, or `pip install --upgrade
"toktier[fastokens]"` for the pinned Fastokens adapter. On the Rust side,
`toktier = { version = "0.3.3" }`.

Apart from the property-data correction under Fixed, served ids are
unchanged, so code that encodes with 0.3.2 needs no change. Four things
want a look.

**Durable session stores the Rust crate wrote under 0.3.2.** A SQLite
session store under `<home>/sessions/` that the Rust crate wrote with
0.3.2 or earlier is not opened by 0.3.3: loading the family fails with
`SessionStateMismatch` ("persistent store does not contain this tokenizer
fingerprint") and the file is left as it is, and 0.3.2 refuses a file
0.3.3 wrote in the same way. The store key carries the crate's exact
source identity, which this release moves. Remove
`<home>/sessions/<family>.sqlite3` (it is rebuilt on first use) or give
the runtime another home; to keep a session, replay its text. A file 0.3.3
writes holds the sessions and their transcripts and no block records.

By the 0.3.2 rule (store key of the native request runtime = version-normalized identities, which do not move; Python entry store = exact build, which moves with the version) the first kind should open under 0.3.3 and the second should be refused. No reading of either is on file; take one, then state it here. -->

**Rust builds on newer property data, or with an outside target
directory.** A build whose lockfile resolves `icu_properties` 2.1 or later
now sends some texts to the reference engine (listed data) or plans the
reference engine for everything (data the release does not list). A build
with a target directory outside the project, `cargo install` from
crates.io or `git`, and this workspace built with `CARGO_TARGET_DIR`
outside the tree read no lockfile and no longer get the fast CPU route;
the plan names `PropertyDataUnread`, and `Policy::RequireAccelerated`
refuses the tokenizer. Set `TOKTIER_CARGO_LOCK` to the absolute path of
the build's own `Cargo.lock`, or build with a target directory inside the
project. `toktier-rust` installed with `cargo install --locked toktier`
therefore serves every family on the reference engine; installed with
`cargo install --locked --path <unpacked crate>` it reads the package's
lockfile and keeps the fast CPU route. A build that reads judged data runs
the check at tokenizer construction (Fixed): where the plan of a
tokenizer names `PropertyDataContradicted`, the lockfile that was read
does not describe the build; rebuild with `--locked` for
`cargo install --path`, or with `TOKTIER_CARGO_LOCK` naming the consuming
build's own lockfile by absolute path.

**`Tokenizer::lookup` in the Rust crate.** A lookup of text whose sessions
are all gone is now a miss, a hit creates no session, and
`store_stats().node_count` counts index entries and falls on delete (Fixed).
A caller that relied on a lookup finding deleted content, or on reuse right
after a durable restart, should keep the session alive or seed it again.

**The SGLang adapter.** Three defaults differ from 0.3.2, by intent: a
tokenizer toktier cannot resolve, when nothing names it, is served in
passthrough instead of raising (`TOKTIER_SGLANG_REQUIRE_ARTIFACT=1`
restores the raise); once one encode has completed on the accelerated
route, short requests are answered by the supplied tokenizer
(`TOKTIER_SGLANG_SHORT_CHARS=0` restores the 0.3.2 routing); and a session
store directory that cannot be created makes the wrap raise at
construction instead of failing every request. `planned_backend`,
`encode_async`, `scheduler`, `tokenize_texts_with_pool` and
`wrap_tokenizer` keep their 0.3.2 signatures, and on an admitted wrapper
that has not switched to passthrough, modeled string calls after
`close()` raise `RuntimeError('backend is closed')` as in 0.3.2 (delegated
calls keep the supplied tokenizer's behaviour); `repr` gains
`accelerates=`, and `stats()` gains `accelerates` and `short_chars`
(`docs/integration/sglang.md`).

## Scope

The claims in this release are the claims of the certification registry
and the chunked admission table it ships: what was judged, on which
artifacts, against which oracle version, with which readings. The lookup
index and the property-data guard decide which engine answers and which
stored ids are reused, never what the ids are, and the readings named
above are the evidence for them. Nothing here widens what the routes were
certified for.
