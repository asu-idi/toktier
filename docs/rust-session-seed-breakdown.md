# Rust `Session::seed` latency breakdown

> **Status (0.2.0).** This page is the retained breakdown study of a
> pre-0.2.0 certified tree from an earlier stage of the 0.2.0 release
> preparation, since superseded by the release recertification; it motivated
> the 0.2.0 seed-path work and its numbers describe that tree. On the
> recertified 0.2.0 tree, measured with the same hosts, tool, and
> protocol (31 fresh processes per cell, post-timing exact-ID checks),
> the public in-memory 4 MiB seed is **11.145 ms p50 / 12.010 ms p95**
> on the RTX 5090 host (was 59.739 / 67.717 ms) and **26.465 ms p50**
> on the EPYC host (was 67.395 ms); the explicit offsets contrast is
> 15.820 ms against the former 39.047 ms span-bridge contrast. The
> current machine-readable reading is
> [`readings/rust_zero_copy_seed_w5.json`](../readings/rust_zero_copy_seed_w5.json);
> the release notes are [`docs/releases/v0.2.0.md`](releases/v0.2.0.md).

The historical Rust lifecycle reading reported one 68.980 ms CPU observation
for `Session::seed` on a 4 MiB Qwen3-8B transcript. A 31-process reproduction
on the same 2x AMD EPYC 9115 host gives a 67.395 ms median (69.046 ms p95), so
the original observation is representative. Most of that time is the complete
corrected-Gigatoken encode; state construction is material but smaller.

This workload is exactly 4,194,304 ASCII characters generated by repeating
`agent-history-0123456789\n`. Qwen3-8B produces 2,348,809 IDs for it. It is not
the separate approximately-one-million-token corpus used by the headline
single-request figure.

## Timed boundary

Each retained observation runs in a fresh process with one Rayon thread. The
timer starts immediately before the operation named in the table and stops as
soon as it returns. For the public seed cell, this means immediately before
`Session::seed(text)` through return of its complete Rust `Encoding`.

Runtime/tokenizer construction, artifact verification, session opening,
process startup, compilation, and the independent HF correctness encode are
outside the timer. Every result is compared after timing with the frozen
`tokenizers==0.22.2` reference. All 899 primary/supplementary observations
matched exactly.

The profiler does not insert clocks into product source. Those source files
participate in CPU/GPU certification digests; changing them would measure a
different build that correctly fails closed. The standalone profiler instead
uses direct observations and controlled counterfactuals outside the certified
source sets. A difference of independent medians is labelled as an estimate,
not an exclusive internal timer.

The outer-call distributions are:

| Host / store | min | p50 | p95 | p99 | max | MAD |
|---|---:|---:|---:|---:|---:|---:|
| EPYC / memory | 63.393 ms | 67.395 ms | 69.046 ms | 69.306 ms | 69.396 ms | 1.044 ms |
| EPYC / SQLite | 113.759 ms | 115.325 ms | 119.625 ms | 121.477 ms | 121.581 ms | 0.831 ms |
| RTX 5090 host / memory | 47.727 ms | 59.739 ms | 67.717 ms | 69.397 ms | 69.946 ms | 2.840 ms |
| RTX 5090 host / SQLite | 81.678 ms | 98.309 ms | 106.929 ms | 110.174 ms | 111.013 ms | 3.487 ms |

## Certified CPU seed

The CPU route is `gigatoken_full` under `Policy::Certified`. The five rows
below close algebraically to the 67.395 ms public median.

| Component | p50 | Share | Observation |
|---|---:|---:|---|
| Corrected-Gigatoken full encode with spans | 47.454 ms | 70.41% | direct engine timer |
| Native routing, execution ledger, and routed ID copy | 1.285 ms | 1.91% | `router_encode - fast_cpu_encode` |
| Populate an empty store tail | 4.074 ms | 6.04% | `router_append - router_encode` |
| Store boundary, integrity, commit, and insertion after append | 13.754 ms | 20.41% | exact precomputed-store counterfactual |
| Lock/name, complete-ID return, and public wrapper remainder | 0.828 ms | 1.23% | algebraic closure residual |
| **Public in-memory `Session::seed`** | **67.395 ms** | **100%** | direct, 31 processes |

As a cross-check, directly timing the real router inside `SessionStore::put`
gives 68.099 ms p50. That is 0.704 ms above the earlier public-seed median and
well within the two independent distributions' approximately 0.8-1.0 ms MAD.
It is retained as a validation cell, not subtracted into a negative facade
cost. The counterfactual store contrast is the stable closure used above.

The exact precomputed append closes independently: cloning the 2.35-million-ID
encoding and its spans costs 1.131 ms; moving it into `TailState` while copying
4 MiB of text and splitting span pairs into store arrays costs 3.621 ms; the
combined append is 4.754 ms, leaving 0.001 ms residual.

### Store and adjacent return work

The store path and the adjacent complete-ID return expose these directly
checkable terms:

| Store operation | p50 / net contrast | Meaning |
|---|---:|---|
| Content digest and 10 geometric checkpoints | 5.064 ms direct; 5.147 ms on/off contrast | incremental content lookup/TKFR state |
| Certified boundary search | 0.608 ms direct | cut at char 4,193,789 / token 2,348,517 |
| Complete-ID materialization | 0.220 ms direct | copy 2,348,809 `u32` IDs (~9.4 MB) |
| Block chain only | +0.451 ms net | 16 nodes, then chain detach; no boundary certificate |
| Boundary/seal only | -0.630 ms net | search costs time but shrinks later commit/hash input |
| Production block + boundary/seal | -0.400 ms net | combined end-to-end post-text contrast |
| Factorial interaction | -0.220 ms | block and seal effects are not additive |

The complete-ID row belongs to the 0.828 ms public-wrapper remainder, not the
13.754 ms store-after-append estimate. It leaves about 0.608 ms in that outer
remainder for locking, name/handle bookkeeping, and wrapping the result.

Negative net contrasts are expected here. Sealing has a positive search/copy
cost, but it moves 2,348,517 IDs into the stable prefix and leaves only 515
text bytes in the tail; later commit/hash work becomes cheaper. The four-cell
factorial keeps that interaction visible instead of assigning a fictitious
exclusive cost to `seal_tail`.

After the 5.147 ms content contrast, about 8.606 ms remains for append-shape
verification, block/seal interaction, record/link hashing, session insertion,
and small accounting. Splitting those private functions with clocks would
change the certified source identity, so this study does not claim a finer
exclusive division.

For context, the frozen HF reference `encode_core` on the same host and input
has a 2,108.082 ms p50. The corrected CPU engine's 47.454 ms is 44.42x lower
for this synthetic workload while producing exactly the same IDs and spans.

## RTX 5090 prebuilt seed

The GPU study uses a GeForce RTX 5090 (`sm_120`, driver 595.84) with an Intel
Core Ultra 9 285K host. All 124 observations used the shipped prebuilt route;
none fell back. Because the CPU and GPU data use different host CPUs, their
absolute totals are context rather than a controlled device-only speedup.

| Component | p50 | Share of memory seed | Observation |
|---|---:|---:|---|
| GPU ID-only route | 5.181 ms | 8.67% | public `encode`, `gpu_full` |
| Reconstruct 2,348,809 HF character spans from known IDs | 39.047 ms | 65.36% | `encode(offsets) - encode` |
| Populate state, run store work, and return complete IDs | 15.511 ms | 25.97% | `seed - encode(offsets)` |
| **Public in-memory `Session::seed`** | **59.739 ms** | **100%** | direct, 31 processes |

The GPU kernel/ID path is therefore not the seed bottleneck. Stateful repair
needs character spans so it can prove safe BPE boundaries; the current GPU
seed reconstructs those spans on the host. Quoting the 5.181 ms ID-only number
as complete session creation would omit 91.33% of the observed seed latency.

The store ledger records `gpu_full` for every seed. In that earlier certified
tree, the returned seed `ExecutionFacts` summarizes the session's CPU repair
capability rather than proving which full-seed backend ran, so this study uses
the store path ledger as the route assertion.

## Durable sessions

SQLite-backed seed includes the same exact in-memory work plus recovery SHA,
a retained 4 MiB plaintext transcript, record/sidecar/binding export, and an
atomic full-store transaction.

| Host/path | Memory seed p50 | SQLite seed p50 | Increment |
|---|---:|---:|---:|
| EPYC 9115 / corrected CPU | 67.395 ms | 115.325 ms | 47.930 ms |
| RTX 5090 host / prebuilt GPU | 59.739 ms | 98.309 ms | 38.570 ms |

On the EPYC host, the recovery SHA-256 is 2.066 ms direct (2.047 ms store
contrast), the SQLite save is 41.573 ms, and opening/loading/verifying the
saved session is 17.273 ms. The representative database is 14,213,120 bytes.
All 62 durable public observations reopened in a new `Runtime` and returned
the exact pre-save snapshot.

## Optimization implications

For CPU seed, corrected full encode remains the largest target at 70.41%.
Within state work, content-checkpoint construction is the largest isolated
term at about 5.1 ms; fusing it with an existing input scan could remove a
pass only if it preserves the exact personalized-BLAKE2b checkpoints. Complete
ID copying is only 0.220 ms and is not a useful first target.

For GPU seed, the 39.047 ms known-ID span bridge is the clear target. A native
GPU/host engine that emits or reconstructs the same character spans more
directly could approach ID-only latency, but boundary certification and exact
HF offsets must remain unchanged. Durable latency is dominated by the
synchronous full-store SQLite transaction; an incremental transaction format
would need the same atomic restart and TKFR verification guarantees.
