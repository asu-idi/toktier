# Pinned Fastokens provenance

TokTier's explicit experimental session adapter can run on
[Fastokens](https://github.com/Atero-ai/fastokens) (earlier published under
`crusoecloud/fastokens`, the same project). From 0.2.7 the `toktier[fastokens]`
extra installs **toktier-fastokens**, a pinned build of fastokens 0.3.1 with
the toktier patch series applied, published by the toktier project on PyPI as
its own distribution. It is not bundled in the toktier wheel, keeps the
upstream import name `fastokens`, and is not affiliated with or endorsed by
the upstream project.

This directory is the source of everything that distribution carries besides
the upstream code:

| File | Role |
|---|---|
| `LICENSE-fastokens` | upstream Apache-2.0 text, verbatim (terminal newline normalized) |
| `NOTICES-fastokens-upstream.txt` | upstream `NOTICES.txt`, verbatim |
| `NOTICE-fastokens-pinned` | the distribution's `NOTICE`: upstream notices plus the Apache-2.0 section 4(b) statement of modification |
| `PATCHES/0001..0005` | the code patches (F040, F041, F042, F045, F046) |
| `PATCHES/0006` | one notice comment line at the top of each modified file; changes no code |
| `CHANGES-toktier.md` | what each patch does, how it was bounded, the readings taken on the published wheel |
| `README-dist.md` | the distribution's long description (PyPI page) |
| `build_pinned.sh` | the recipe: clean upstream checkout, patch series with digest and tree-hash checks, pinned rustc/cargo/maturin |
| `fastokens.cyclonedx.json` | the CycloneDX SBOM maturin embedded in the published wheel |
| `THIRD_PARTY_LICENSES-fastokens.txt` | license texts of the compiled dependency closure, generated by `generate_license_bundle.py` |
| `SHA256SUMS` | digests of the published distribution files (the first lines) and of the files above; `.github/workflows/publish-fastokens.yml` checks release assets against it before uploading them |

## Which bytes are certified

The readings behind `engine_assurance: certified_pinned` were taken on one
wheel, the one published on PyPI as `toktier-fastokens` 0.3.1.1 (the sdist
published beside it is `toktier_fastokens-0.3.1.1.tar.gz`, sha256
`7c275f907d26107d2f4605821372e9104c6679e240f88b41f22a521445b86969`):

| Item | Value |
|---|---|
| file | `toktier_fastokens-0.3.1.1-cp39-abi3-manylinux_2_28_x86_64.whl` |
| wheel sha256 | `b99f2765fa1b900afe181844a85ed8eb784ba87972ac92e22cc924322d9c5468` |
| engine digest | `0bcf3ada9268e5aef1c9da515555f5e2ea6fc8d7a8accfbc444789853edfdfec` |
| source tree | `aa1924284ec4abaedcc8ed5823ee17e7959c55c5` (patches 0001 to 0005 on `fe854299`) |
| build | manylinux_2_28 host, rustc 1.93.1, maturin 1.14.1, fixed build root |

The engine digest is what the adapter computes over the installed
`fastokens/` package (`src/toktier/repair/fastokens.py`); the shipped support
registry lists the published wheels under `engine_distributions.fastokens`,
and `tools/fastokens_binding.json` is the hand-written source of that node.
A wheel with any other digest, including one built from the sdist on another
host or toolchain, reports `unrecognized_build`; the upstream wheel reports
`upstream_build`.

One copy of patch 0001 in the published wheel's `dist-info/licenses/PATCHES/`
differs from the copy here in its `From:` header line only (the one here reads
like the other four); the diff body is identical and applies to the same
tree. The digests the recipe checks are those of the copies in this
directory.

The published 0.3.1.1 artifacts were built before patch 0006 existed and
before the texts in this directory took their final form: their
`dist-info/licenses/` carry `NOTICE`, `CHANGES-toktier.md` and the
distribution README as they stood at build time (five patches listed, the
upstream reports described as prepared rather than submitted, no
`THIRD_PARTY_LICENSES-fastokens.txt`). The files here are the source for the
next build; the bytes that were certified are the bytes that were published.

## Two trees

Patch 0006 was added after the 0.3.1.1 wheel was built. It changes no code,
but the compiled extension differs between the five-patch tree and the
six-patch tree (`aaa5fb94ea62b9379d03074640e267c8d837d649`) because source
line numbers reach the binary through diagnostics metadata. `build_pinned.sh`
applies the full series by default and checks for the six-patch tree;
`APPLY_NOTICE_PATCH=0` stops after 0005 and checks for the five-patch tree
the published wheel came from. Either way, the engine bytes of a fresh build
reproduce only when the dependency source root is the same absolute path as
the build being reproduced (`BUILD_ROOT`).

## Rebuilding

```bash
TOKTIER_FASTOKENS_BUILD_ROOT=/tmp/tkfb2 \
  packaging/fastokens-pinned/build_pinned.sh
```

The script refuses to run with any other `rustc`, `cargo` or `maturin` than
the pinned ones, checks every patch digest before applying it, and stops if
the resulting tree hash is not the expected one. Offline hosts pass
`SOURCE_TARBALL`, `VENDOR_TARBALL` (or `VENDOR_DIR`), `MATURIN_BIN` and
`INTERPRETER`; see the script header.

## Regenerating the license bundle

```bash
cargo metadata --offline --locked --format-version 1 \
    --manifest-path python/Cargo.toml > metadata.json   # in the patched checkout
python3 packaging/fastokens-pinned/generate_license_bundle.py \
    metadata.json packaging/fastokens-pinned/THIRD_PARTY_LICENSES-fastokens.txt
```
